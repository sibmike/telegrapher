\section{Introduction}\label{sec:intro}

The standard mental model of a system built on a large language model (LLM) is the model. Pre-training fixes the weights, fine-tuning nudges them, and deployment wraps a thin layer of prompts and tools around the result. Production in 2025 and 2026 has stopped behaving this way. Frontier weights change on a cycle of months; the systems built on them change daily, in instruction files checked into repositories, memories that persist across sessions, skills loaded on demand, registered tools, evaluation suites that block a merge, agent topologies, and pull-request gates on shared rule repositories. A growing share of the adaptation that makes a deployed system reliable now happens outside the weights, in a fast-changing local scaffold wrapped around a slow-changing frontier model.

Read one at a time, these artifacts look like unrelated engineering. A skill file is a procedure the model did not have; a repository rule is a convention for one project; a retrieval connector is memory access for one workflow; a tool registry provisions a capability the base model cannot reach; a pull-request review against a shared rule repository is a promotion gate. Read together, they are one adaptation surface, the non-model part of what has been called a compound AI system \cite{zaharia2024compound}. This survey asks what optimization discipline that surface needs, and finds that the field has built the layer and, as far as public evidence shows, not the optimizer that should govern it. Most deployments maintain the layer as patchwork: a failure happens, someone adds a rule, the pile grows, nobody knows which addition helped, and fixes leak into contexts that never validated them.

The disciplined alternative is one loop with two halves. The first half turns a recurring failure into one tested edit to the scaffold and keeps the edit only if the deployment's own failure rate falls. The second half decides how far the edit may travel, to a team, to an organization, or to every customer, and lets it travel only as far as evidence supports. The first half is routine: in most research systems and a growing number of production ones it closes under an automatic gate. The second half, governed by versioned lineage, access control, and rollback, appears in none of the 256 systems surveyed. What separates the two halves is the feedback the gate receives. A test or an observed outcome can gate an edit automatically; a judgment can only once the judge is calibrated against people; a reward that arrives months later cannot gate edits one at a time. The class of the signal decides which half of the loop a deployment can close.

This article makes five contributions.

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  The loop that turns patchwork into optimization, in plain language and as a gated update rule, with the five conditions under which it is an optimizer (Section~\ref{sec:loop}).
\item
  Four classes of feedback signal, from an exact check to a delayed reward, each fixing what the gate can be and which failure dominates (Section~\ref{sec:signal}).
\item
  A survey of 256 production and research systems, scored on six substrates against a published rubric, with the scores released (Sections~\ref{sec:method} and \ref{sec:findings}).
\item
  A design space indexed by the gate on each half of the loop, and the convergence of five research families on the same loop (Sections~\ref{sec:design} and \ref{sec:families}).
\item
  A four-property audit criterion for governed cross-organization scaffold optimization, which no surveyed system meets, with the failure surface its absence leaves open and the open problem each signal class poses (Sections~\ref{sec:gap} to \ref{sec:open}).
\end{enumerate}

The survey runs no experiments. Its evidence is the published behavior of 256 systems, scored on a released table.

\section{Why adaptation lives outside the weights}\label{sec:why}

\subsection{Breadth in the weights, depth in the scaffold}\label{breadth-in-the-weights-depth-in-the-scaffold}

Frontier training optimizes for breadth. The weights are tuned to generalize across millions of unseen deployments, and the objective smooths over exactly what one deployment cares about: local naming conventions, contradictory preferences between customers, rare workflow-specific failures. Reinforcement learning from human feedback reduces output diversity and homogenizes preferred style across users \cite{kirk2024understanding, padmakumar2023diversity}, and instruction-tuning data rewards patterns that generalize across the annotator pool, so the frontier model is trained to disfavor one customer's idiosyncrasies. Tiwari et al. \cite{tiwari2026fastandslow} reach the same place from the optimization side: in-context adaptation is cheap but capacity-bounded, in-weights adaptation is expressive but induces forgetting and loss of plasticity \cite{dohare2024loss}, so a system that learns slowly in the weights needs a cheap outer layer that learns fast outside them.

Production reliability is won in depth, inside one deployment, and it turns on what global training had to smooth away. Encoding every deployment in the weights is ruled out three times over: fine-tuning per customer multiplies the training, evaluation, and serving lifecycle by the number of deployments; weights ship quarterly at best, while the deployment wants daily updates; and overfitting the weights to one customer degrades the neighbors whose preferences contradict. Per-customer adapters \cite{hu2021lora}, distilled models, and learned routing could absorb some of the residual, the failures that remain after training, but in practice they are rare. Adaptation lands in the scaffold, the one substrate that is cheap, inspectable, reversible, scoped to one customer, and updatable daily.

\subsection{Why the scaffold is the right architecture: the two earlier results}\label{why-the-scaffold-is-the-right-architecture-the-two-earlier-results}

The case for learning outside the weights does not rest on cost alone. The two papers that precede this one in the series supply the hypothesis that explains the pattern the corpus shows, and each states the scope on which it rests. \emph{Beyond Exponential Decay} \cite{arbuzov2025beyond} argues, from a direct measurement of long-range dependence on one natural-text corpus and from the accuracy that majority voting recovers on reasoning benchmarks, that long outputs do not fail at the rate a uniform per-token error model predicts: reliability hinges on a sparse set of key decisions, under a tenth of tokens in that measurement, and the argument stops where the number of decisions grows with the task, as in long-horizon agentic work. \emph{The Architecture of Errors} \cite{arbuzov2026architecture} argues, for a deployment that operates inside a bounded slice of recurring tasks, tools, and evaluator expectations, that those decisions fail in a small recurring catalogue of modes whose size grows only slowly with the number of observed failures, so a targeted intervention budget that grows polylogarithmically in sequence length, and becomes constant once the catalogue saturates, covers the residual; its negative result marks the limit, that no finite catalogue covers an unbounded domain.

If those results hold in general, a deployment's errors are few enough to fix one at a time, and a small catalogue of fixable modes is exactly what a cheap, inspectable, reversible artifact layer is for. This article asks where the fixes live, and the corpus answers: in persistent artifacts outside the weights, one recurring mode at a time, which is the pattern the hypothesis predicts. On that hypothesis the gated and scoped layer is not a workaround for an inadequate model. It is the architecture the error structure calls for: a frontier model that generalizes, a local scaffold that specializes, and reliability that comes from governing the specialization. The survey's own findings, in Sections~\ref{sec:findings} to \ref{sec:gap}, stand without it.

\subsection{Relation to existing surveys}\label{relation-to-existing-surveys}

\section{The loop: artifact-layer descent}\label{sec:loop}

\subsection{The loop in plain language}\label{the-loop-in-plain-language}

We call the disciplined version of scaffold maintenance artifact-layer descent. It is one loop with two halves, run again and again over the life of a deployment: Loop 1 fixes a recurring failure inside one deployment, and Loop 2 decides how far the fix may travel. Fig.~\ref{fig:descent} draws the first half. The deployment runs and logs what goes wrong: failed outputs, user corrections, rejected answers, evaluation regressions, tool-call errors. The loop does not react to single failures. It clusters the log into recurring modes and takes up the ones that matter most, ranked by how often each recurs and how badly it fails. For such a mode it locates the scaffold coordinate responsible, which may be a stale memory entry, an under-specified instruction, a missing tool argument, a brittle retrieval rule, or a misrouted agent edge, and it proposes one candidate edit to that coordinate.

Then it measures. A deployment serves one \textbf{patch}: the slice of users, tasks, and conventions it handles. The failure rate on that patch's recurring tasks is the \textbf{patch loss}. A gate accepts the edit if the patch loss falls and rejects it otherwise. An accepted edit stays in the scaffold, versioned; one that a later check shows made things worse is rolled back. That is the whole of Loop 1, and it is what most research systems and a growing number of production systems now do.

\caption{Loop 1, the local half of artifact-layer descent. A recurring failure is traced to one scaffold coordinate, one edit is proposed, and a gate keeps the edit only if the deployment's patch loss falls. An accepted edit then enters Loop 2 (Fig.~\ref{fig:scope}).}
\label{fig:descent}
\end{figure*}

Loop 2 is the step most systems skip. An engineer notices that a coding agent keeps misnaming a class in one repository. The fix is a one-line rule in that repository's instruction file. The same rule could be promoted to a team-wide template, to the company's core instructions, or to a skill registry shared across companies. The edit did not change; its scope did. And the gate that should let it through gets stricter at each step, because the loss it is tested against is now an average over more deployments, and a fix that helps one repository can hurt another.

The scopes nest (Fig.~\ref{fig:scope}). USER is one person's account or fork; PROJECT is one repository, workflow, or product workspace; STACK is a curated bundle of projects under one team; a \textbf{tenant} is one organization or customer; CORE is the scope every tenant shares. Each level's loss is the average failure rate over the deployments it contains. Promotion that reaches CORE crosses tenants, and we call it cross-tenant promotion. Loop 2 promotes an edit upward only as far as the evidence reaches; we call that limit the edit's \textbf{evidence radius}. The check that belongs at each rung is \textbf{receiving-side evaluation}: a check run where the edit arrives, not where it was made. In optimizer terms, Loop 1 sets the step, how much one accepted edit changes the local scaffold, and Loop 2 sets the target, which average failure rate the scaffold is tuned to reduce. Governance is therefore not administrative overhead. It is the regularization that keeps a small fix from being aimed at the wrong target.

\subsection{When the loop is an optimizer}\label{when-the-loop-is-an-optimizer}

The loop is an optimization process, rather than a description of good practice, when five conditions hold:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  a measurable patch loss, such as a failure rate, a correction rate, or an evaluation score;
\item
  captured residuals, so that failures are logged rather than lost;
\item
  credit assignment, so that a failure can be traced, at least sometimes, to the scaffold coordinate that caused it;
\item
  a synthesized candidate edit to that coordinate; and
\item
  a gate that checks whether the edit lowers the loss before the edit is kept or promoted.
\end{enumerate}

The conditions presuppose frozen frontier weights, edits that persist as inspectable artifacts rather than transient prompts, and promotion that widens an artifact's scope under a gate rather than averaging comparable updates as weight-space federated learning does.

Written out, the patch loss of deployment \(D\) is \[L_D(\theta_s) = \mathbb{E}_{x \sim D}\!\left[\ell(\pi(\theta_M, \theta_s, x))\right],\] where \(\theta_M\) are the frontier weights, fixed during deployment, \(\theta_s\) is the scaffold, a structured object over the six substrate coordinates of Section~\ref{sec:method}, and \(\ell\) is an operational loss. A failure yields no analytic gradient. It yields a candidate edit \(z_t\), proposed by reflecting over the accumulated failure history. The gate accepts the edit when its noisy estimate of the change in loss clears a margin, \[G_t(z_t) = 1 \iff \widehat{\Delta}_{z_t} L_D(\theta_s^t) + \lambda\,\Omega(z_t) \le -\tau_t,\] where \(\Omega \ge 0\) penalizes the complexity of the edit and the breadth of its promotion, and \(\tau_t \ge 0\) is the required margin. Production systems implement this inequality without writing it: an evaluation blocks a merge on regression, a reviewer rejects a vague rule, a governance system holds an artifact back until evidence accumulates. Under a bounded-bias assumption on the gate the update satisfies a one-step descent inequality, and when that bias is summable over the run, the loss converges and improving edits stop clearing the gate: the scaffold becomes gate-stable, which is a statement about the gate, not about optimality (Appendix~\ref{app:formal}). Where a condition fails, the picture is an analogy, and the survey marks which systems meet which conditions.

Each half of the loop has a gate, and we name three kinds by who decides. A gate is \textbf{Auto} when a program applies a check before the edit goes through: an evaluation score, a verifier, a reinforcement-learning threshold, or a language-model judge \cite{zheng2023judge} with a quantified agreement rate. It is \textbf{Human} when a person decides. It is \textbf{None} when nothing decides, either because that half of the loop is absent or because the step runs unchecked, as when a system pushes every edit to its neighbors without a test. Who writes the candidate, an agent reflecting over failures, an engineer at a desk, or a contributor registering an artifact, is recorded separately and is not a gate. We write a system's two gates as a pair, Loop 1 first: {[}Auto × Human{]} means an algorithmic local gate and a human promotion gate. These pairs index the design space of Section~\ref{sec:design}.

Condition 1 says the loss must be measurable. It does not say what measures it, and that turns out to be the question that sorts the corpus.

\subsection{From patchwork to descent}\label{from-patchwork-to-descent}

Three stages of scaffold maintenance recur across the corpus, and the five conditions separate them. At the first stage, patchwork, edits are made by intuition after a failure, credit assignment is implicit, nothing is promoted on evidence, and the scaffold bloats. At the second stage, random artifact search, many variants are tried under an evaluation and the best is merged; the evaluation is the only signal, no failure is traced to a coordinate, and the dominant failure is overfitting to the in-distribution patch. At the third stage, artifact-layer descent, a residual is traced to a coordinate, one edit is made, promotion is bounded by evidence radius and reversible, and the dominant failure becomes evaluation fragility, because the suite that gates the edits is itself a scaffold artifact that drifts and can be gamed (Section~\ref{sec:failure}). A loop reaches the third stage once the five conditions hold. Production deployments that reach it on Loop 1 promote either behind a human gate, as Spotify \cite{palumbo2026spotify} and SkillForge do, or, in one case, by an ungated push that carries lineage but no evaluation, as Letta's Context Repositories do.

\section{Where the signal comes from: four classes of feedback}\label{sec:signal}

Four scaffolds all run the loop of Section~\ref{sec:loop}. A coding agent changes one line in its repository rule file; the test suite runs and reports pass or fail within seconds. A scheduling assistant changes how it phrases a booking request; the appointment either appears on the calendar or it does not, and the system learns which an hour later. A marketing assistant changes the tone rule in its instructions; nobody can say whether the next draft is better, only whether a reviewer prefers it. A research assistant changes how it chooses which direction to pursue; whether the choice was good becomes visible months later, after many other edits have landed. All four produce a candidate edit. They differ in what the gate can know about it.

That difference is the whole of this section. The gate needs an estimate of one quantity, whether the edit lowered the patch loss, and the estimate comes from a feedback signal. Signals differ in three ways: how soon they arrive, how exact they are, and whether there is a fact of the matter at all. Those three differences sort every surveyed system into four classes (Table~\ref{tab:IV-1}), and the class fixes what the gate can be, which half of the loop can close automatically, and which failure dominates.

The classes are a partition, not three independent axes: a system is assigned by the property that binds its gate first. Delay binds before anything else, so an outcome that arrives months later is C4 even when it is objective; the absence of ground truth binds next, so an immediate judgment is C3; and among signals that are prompt and objective, exactness separates C1 from C2.

\textbf{C1, exact.} A deterministic checker returns pass or fail, or an exact score, immediately and repeatably: unit tests, compilers, type checkers, exact-match answer keys, proof checkers, schema validators. DGM accepts a self-modification only after it passes in a sandbox on coding benchmarks \cite{zhang2025darwin}; AlphaEvolve scores candidate programs with a cascade of exact evaluators \cite{alphaevolve2025}; SkillOpt gates a skill edit on a held-out exact-match split of a math benchmark \cite{yang2026skillopt}. The check is exact for the artifact and the test it runs, and repeating it returns the same answer, so one run of the check settles the checked case. What the check does not settle is the patch loss: the suite is a sample of the patch's task mix, and the agent that runs under the edited scaffold is stochastic, so the gate's estimate of the loss change still carries sampling error. The gate can be a program and its margin can be small, but the margin absorbs sampling error, not error in the check. Two things stay hard. A failing test localizes the output, not the scaffold coordinate that caused it, so credit assignment remains open; and a checker that is also the training target can be gamed. The dominant failures are test overfitting and scaffold bloat, because cheap acceptances accumulate.

\textbf{C2, observable outcome.} The environment or the user emits an outcome after an episode: a booked appointment, a closed ticket, a merged pull request, a tool call that returns without error, a retrieved document that contains the answer. The signal is real but one episode late, noisy, and confounded, since a user can accept a wrong answer and reject a right one. Devin's merged pull requests \cite{cognition2025devinreview}, SAGE's task success on AppWorld \cite{wang2025sage}, SkillRL's success-rate threshold \cite{skillrl2026}, and PACE's failure signals from a deployed small model \cite{ling2026pace} are gates of this class. The gate can still be a program, a reinforcement-learning threshold or a held-out task suite, but it needs a positive margin, and it absorbs the noise by batching episodes or by requiring agreement across samples (Appendix~\ref{app:gates}). Credit assignment takes its hardest form: the outcome says \emph{that} the episode failed, not \emph{why}. Most production deployments live in this class, and its signal arrives through a channel an attacker can control, which is why poisoned memory and tool-output injection dominate.

\textbf{C3, judged.} There is no fact of the matter. An essay, a marketing page, a design, a pitch deck, or a code review for style can be scored only by a judge: a human rater, a language-model judge, a rubric, or a comparison against references. SkillForge accepts a skill diff when its judge agrees with human engineers more than nine times in ten \cite{skillforge2026}; CASCADE consolidates memory under a human-and-agent gate \cite{huang2025cascade}; Anthropic's skills repository promotes a skill when a reviewer approves the pull request. The gate can be a program only after the judge has been calibrated against people, because the judge's bias is now the estimator's bias; and residuals are captured only when someone objects, so condition 2 depends on complaint channels rather than instrumentation. The dominant failure is Goodhart's law in the form measured for reward models: optimizing a proxy past a point lowers the true score \cite{gao2023overoptimization}. Once the judge is the target, the scaffold learns the judge. Nor is a human judge stable; evaluators' criteria drift as they grade more outputs \cite{shankar2024validators}.

\textbf{C4, delayed and sparse.} The outcome arrives after weeks or months, once per many edits, in a world that has moved on. Research programs, product strategy, and open-ended discovery are of this kind; the clearest instances are automated research pipelines such as the AI Scientist, which generates ideas, runs experiments, and writes the paper \cite{lu2024aiscientist}. NanoResearch merges candidate skills by semantic compatibility rather than by a measured loss change \cite{xu2026nanoresearch}, and CORAL promotes findings into shared memory on a heartbeat rather than on an evaluation \cite{qu2026coral}. AlphaEvolve's evolutionary database is not an instance, although it can look like one: it balances improving the best programs against diversity only after every candidate has been scored by its exact evaluators, so it is a search strategy inside the exact class, not a gate for a delayed signal \cite{alphaevolve2025}. With no per-edit estimate to gate on, the gate degenerates to proposal pruning plus proxy milestones, and the descent argument covers only the composition of pruning and whatever gate exists at the horizon (Appendix~\ref{app:gates}). Temporal credit assignment across many edits is open. The dominant failure is drift: the scaffold ages faster than the signal that would correct it. An optimizer in this class also cannot be told from random search by its outcomes alone; Ong et al. \cite{ong2026harnesseval} report the same indistinguishability for harness optimizers.

\textbf{The judge is part of the scaffold.} One feature of the judged class deserves its own paragraph, because it returns in the findings and in the open problems. The rubric that sets the loss is itself a scaffold coordinate. Suppose a pitch-review system keeps overrating decks that claim a large market without numbers. It traces the failure to its rubric and edits ``evaluate market size'' into ``require a numeric estimate and a source''. That edit changes the gate that will judge the next edit. We call this the \emph{reflexive gate}, and nothing in the corpus calibrates one: three scaffold systems report judge calibration \cite{skillforge2026, hu2026skillchain, zhu2026skillcoach}, and none calibrates a judge that is itself being edited. The weight side faces the same question. Reinforcement learning from verifiable rewards lies outside the scored corpus, but pushing it into writing and other open-ended tasks has forced the construction of judged gates. One group holds the gate fixed while the policy learns, as a checklist, a pairwise judge, a reference-anchored judge, or a fixed rubric \cite{gunjal2025rubrics, jia2025writingzero, shi2026references, jin2026rlaes}; a second group lets the gate move with the policy, scoring by the policy's own probability of a reference or updating the rubric or judge during training \cite{yu2025rlpr, xu2026rubricarm, ding2026evorubrics, zhu2026score, li2026rubricem}. Fixed versus co-evolved is exactly the reflexive-gate question, and of the co-evolving methods only RLPR, whose reward is a probability rather than a rubric, reports agreement with human labels (Supplementary Material S6).

\textbf{What the class decides.} Read down the table and three consequences follow. First, which half of the loop can close automatically. An exact check or an observed outcome can gate a local edit by program, a judgment only once the judge is calibrated, and a delayed reward not edit by edit at all; and only the exact class can gate promotion by program without a person on the receiving side, and only when the receiving side runs the same check, because only then does the sending side's evidence mean the same thing on arrival; otherwise the receiving-side evaluation of Section~\ref{sec:loop} is still owed. Second, which gate pairings a deployment can reach. {[}Auto × Auto{]} belongs to exact signals and simulated outcomes; {[}Auto × Human{]} belongs to observed outcomes and judgments, where the person on Loop 2 does the work the missing exact signal cannot; and the delayed class has no per-edit gate on either half. Third, which failure dominates, as the last column of the table records and Section~\ref{sec:failure} develops. Each consequence is a prediction about the corpus, and Section~\ref{sec:design} checks all three.

\section{The survey: substrates, corpus, and scoring}\label{sec:method}

To see which half of the loop the field has built, we scored 256 systems on where their scaffold adapts, whether a loop closes there, and under what gate.

\subsection{Six substrates}\label{six-substrates}

A deployment's scaffold is composed of six substrates (Table~\ref{tab:V-1}). They are the coordinates of \(\theta_s\), and each can be edited independently of the others; the three kinds of memory on the memory substrate follow the cognitive-architecture taxonomy of Sumers et al. \cite{sumers2023coala}. Other partitions are possible, for instance separating evaluation suites from governance. The argument of Section~\ref{sec:loop} is invariant to the partition so long as the coordinates stay independently editable, and this one recurs in practice, since every integrated system in the corpus has a recognizable instance of each substrate under some name.

Every substrate is scored on the same 0 to 5 scale: 0, ephemeral; 1, persistent and local; 2, persistent with tool attachment but no feedback; 3, multi-scope or feedback-driven but without automated promotion; 4, automated feedback updates the scaffold, so one half of the loop is closed; 5, the substrate's own top mark in Table~\ref{tab:V-1}. Systems that adapt several substrates at once receive an additional integrated row. The top mark means different things on two kinds of substrate. On those that hold adaptable content (S1, S2, S5) it requires both halves of the loop. On those that hold governance machinery (S3 provenance and correction, S4 evaluation-gated tool versions, S6 evaluation-gated promotion with audit and rollback) it requires the machinery a second loop would need, not the loop itself. That is why tool registries and the prompt-management platforms of Section~\ref{sec:findings} can score 5 with no inner loop at all and still sit outside the two-loop cells of the design space.

\subsection{How the corpus was assembled}\label{how-the-corpus-was-assembled}

The corpus holds systems that either wrap a foundation model with at least one persistent artifact updated from deployment signal or are described in public as self-improving, scaffolded, or agentic, found in arXiv, vendor documentation, and public repositories between January 2023 and the October 2026 cutoff. It was assembled in two passes, the second adding 126 systems up to the cutoff, and each system was scored from its own method section or documentation, never from a secondary summary (Supplementary Material S2). Two kinds of system are excluded: those whose only update mechanism is weight-level fine-tuning or reinforcement learning, which are model-side and belong to the self-evolution literature this survey positions against, and those with no public evidence of deployment or release.

Two filters structure the corpus (Fig.~\ref{fig:corpus}). The patch-local discriminator admits a system to the core corpus when it scores at least 3 on at least one substrate, that is, when some artifact persists across scope or is updated from feedback; systems that carry the labels but fail it form a contrast corpus, kept so that the boundary can be audited rather than asserted. Of the 256 systems, 204 form the core corpus and 52 the contrast corpus. A stricter composite two-loop audit then asks two questions of each core system: does Loop 1 modify a persisted artifact from session signal, and does Loop 2 have an explicit mechanism that promotes the artifact beyond the deployment that produced it, with versioning or lineage? The audit was applied to the 204 core systems and to ten further systems that the text treats at mechanism level, which were classified from their papers after the released table closed and are not rows of it, so the corpus counts above exclude them (Supplementary Material S2). It admits 14 research systems, 13 of them rows of the released table and the fourteenth SkillOpt from that mechanism-level group, and 3 industry exemplars: Sierra Agent OS 2.0, Cognition Devin, and Letta's Context Repositories. Only these are placed in the design space. Passing the audit is a weaker thing than having the governed second loop of the thesis: every passing system promotes across users, teams, or repositories inside one operator, none reaches another organization, and one of them, Letta, promotes with no gate at all (Section~\ref{sec:gap}).

\subsection{Evidence and scoring discipline}\label{evidence-and-scoring-discipline}

Every classification rests on public evidence of uneven strength and on one rater. Each system carries one or more evidence tiers (T1 to T5 in the released table: peer-reviewed publication, arXiv preprint, production claim with metrics, open-source artifact, industry blog or interview). Peer-reviewed papers and open-source artifacts weigh most in cluster-level statements; a production claim counts when it names a benchmark or integration target; a blog post or interview counts only when a higher tier corroborates it; and production claims are never pooled with peer-reviewed evidence in a cluster-level statistic. Industry systems evaluated from vendor documentation rather than a paper are flagged wherever they appear. One author scored every system, used half-scores only when one criterion was clearly met and another partially, and rounded ambiguous cases down; the scores have not been independently re-rated, and that check is future work. The complete score table, with a one-line justification per row, is released so that every scored classification can be re-derived (Supplementary Material S1). The counts move under natural relaxations of the composite audit, such as counting rollback alone as Loop-2 governance, asking for a promotion mechanism with no governance at all, or admitting a Loop 1 that persists only optimizer state, and the qualitative findings survive every one of them (Supplementary Material S2).

\section{What the field has built}\label{sec:findings}

The corpus answers the question of Section~\ref{sec:intro} in one sentence: the local half of the loop is routine, and no surveyed system documents the governed second half. This section gives the evidence in three cuts. Per substrate, where the top mark is reached and where it is not; per missing piece, which parts of the second half are absent and in which signal class; and per cluster, which kinds of system have which half.

On the three substrates that hold adaptable content, only two systems reach the top mark, and both reach it inside one research environment. Instruction files persist across IDEs and agents (Claude Code, Cursor, AGENTS.md \cite{agentsmd2025}, Windsurf, Continue.dev) and appear in a fifth to a quarter of coding-agent projects \cite{robbes2026agenticmuch, galster2026harnessconfig}, yet in a controlled study they raise inference cost by about a fifth without raising task success \cite{gloaguen2026agentsmd}. Skills are the most active research substrate: SAGE and COSPLAY close both halves of the loop \cite{wang2025sage, wu2026cosplay}, Loop 1 is routinely automated, and SkillChain's judge-approved edits pass a human reflection gate before they enter its skill bank, a two-stage local gate rather than a promotion loop \cite{hu2026skillchain}. Eleven skill systems treat retirement as a gated operation \cite{zhang2026librarydrift, wei2026skillsmith, pu2026skillops, wang2026assay}, and the public skill repositories are merged by hand \cite{shen2026whomaintains}. On orchestration, automated workflow search came first, in optimizable agent graphs \cite{zhuge2024gptswarm} and tree search over code-represented workflows \cite{zhang2024aflow}; topologies evolve under evaluation \cite{cheng2026optimas, chu2026agentgrad, chen2026harnessforge}, TOCOMAS alone keeps a topology change only when it satisfies a structural invariant \cite{zhao2026tocomas}, and Evo2Team promotes routing skills across teams \cite{wang2026evo2team}.

Memory carries lineage without enforced correction. Production memory records its own history, in Letta's git-backed Context Repositories \cite{letta2026memfs}, Mem0's per-memory history \cite{mem02026history}, and Zep's bitemporal facts \cite{zep2026facts}. Research memory splits into write-gating and provenance on one side \cite{wang2026toki, xu2026ppmf, margalit2026governed} and verifier-gated failure loops on the other \cite{yu2026recuris, wang2026memguard, sun2026vermem}. Among the memory systems that gate writes or correct from failures, only Cuadros et al.~does both, which is why it alone reaches the top mark.

Tools and governance hold the machinery of a second loop without the first, which is how they reach the top mark with no inner loop (Section~\ref{sec:method}). MCP registries split into catalogues, with namespaces and version records but no scanning, and control planes, with scanning, access control, and quarantine \cite{agenticcommunity2026mcpgateway, microsoft2026apicentermcp, truefoundry2026mcpgateway}; none has evaluation-gated promotion. The governance registries bring lineage and rollback \cite{kang2026registry, quessadavial2026acm, qin2026governed}, and none of them has an inner loop.

No system matures all six substrates at once. Research systems learn fast and lack enterprise governance; production systems govern well and learn slowly; open standards solve artifact portability but not adaptation. This pattern is not a quirk of the corpus: it tracks which constraints each kind of system was built to satisfy.

\subsection{Where the second loop should be, five pieces are missing}\label{where-the-second-loop-should-be-five-pieces-are-missing}

Walk the second half of the loop from the failure that starts it to the promotion that ends it, and five pieces are missing or rare across the core corpus. Each is missing in a particular feedback-signal class, which is the first sign that the gap is not one gap but several.

\begin{itemize}
\tightlist
\item
  \textbf{Failures are not captured} (C2). Deployed memory systems record preferences and successful facts, not residuals, so the loop has nothing to cluster. The one field report of stores written from dead-ends to prevent recurrence describes a single, self-reported deployment \cite{helwig2026memory}.
\item
  \textbf{Which sessions inform the next edit is left to chance} (C2). Nearly every system takes failures in the order they arrive. Task-CoEvolve's variance-weighted task sampling and AutoSaddler's mini-batch failure signals are the exceptions \cite{miyai2026taskcoevolve, park2026autosaddler}.
\item
  \textbf{Memory is versioned, but correction is not enforced} (C2, C3). Git-backed and bitemporal memory ship in products, and five production backends still return facts that were revoked \cite{shen2026revoked}.
\item
  \textbf{Promotion is rarely checked where the edit arrives} (C1, C2). ShareMem gives evaluation tasks to a different user, XRepoSkill verifies in at least two repositories, Evo2Team confirms at the target team, and VACE evaluates the candidate with the receiving model held fixed \cite{qi2026vace}; even Evo2Team's confirmation lets nearly a fifth of its transfers fail on new graphs. EvolveNet has no such check, and the federated optimization framework that proposes a receiving-client gate has not implemented it \cite{yang2026fao}.
\item
  \textbf{No promotion crosses an organization} (all classes). ShareMem, EvolveNet, XRepoSkill, and RASO promote across users, clients, or repositories inside one operator \cite{hu2026sharemem, nie2026evolvenet, guo2026xreposkill, chu2026raso}. No system promotes across customers or organizations with evidence.
\end{itemize}

The last piece is the thesis of this article. The four before it are the reasons a system that tried to add it would have little to promote and no way to check what it promoted.

\emph{Research full-auto} systems show that the architecture works when both gates are algorithmic \cite{xu2026nanoresearch, wang2026autoagent, romeraparedes2024funsearch, alphaevolve2025, zhang2025darwin, hu2024adas, wang2023voyager}. AlphaEvolve is the clearest case: it pairs an evaluator with an evolutionary archive, as FunSearch did before it, and reports production gains at Google. EvolveNet, Evo2Team, and XRepoSkill extend the loop from a single deployment to a federation of deployments. What every member lacks is governance: no access control and no audited promotion.

\emph{Production hybrid} systems show that the production-viable pairing is an algorithmic gate on Loop 1 with a reviewer on Loop 2. SkillForge illustrates it most plainly: a judge that agrees with people more than nine times in ten passes each skill diff, and support engineers decide whether it ships \cite{skillforge2026}. Sierra routes agent-generated insights through human-authored expert answers \cite{sierra2025os20}, Devin's merged pull requests are its promotion step \cite{cognition2025devinreview}, and Spotify launches automatically optimized prompts and plans only behind an online A/B test. In every member the human on Loop 2 does the work that the missing exact signal cannot.

\emph{Governance-first} systems automate Loop 2 alone. The prompts-as-code platforms \cite{braintrust2026docs, vellum2026docs, langsmith2026hub} and the governance registries \cite{kang2026registry, quessadavial2026acm, qin2026governed} keep immutable versions, evaluation thresholds, and rollback, but they have no Loop 1: engineers author the candidates, and session feedback never triggers one. This is MLOps for scaffolds, distinct from MLOps for weights.

\emph{Open standards and registries} converge across vendors on format and attachment. Claude Agent Skills, Cursor Rules, GitHub Copilot instructions, Windsurf, Continue.dev, Zed, and Replit all keep a git-tracked markdown artifact attached to a workspace with an MCP-style tool layer \cite{galster2026harnessconfig, barbaste2026harnessengineering}, a convergence that Section~\ref{sec:families} reads as evidence that the architecture is real. What the cluster lacks is adaptation: its registries govern admission and access but do not evaluate, and in the repositories that run autonomous loops, the runtime state of those loops sits outside version control \cite{lulla2026loopengineering}.

\section{The two-loop design space}\label{sec:design}

Index each system by the gate on each half of the loop and the field collapses into two gated cells, one half-cell, and one ungated passer (Fig.~\ref{fig:design}).

\centering
\includegraphics[width=0.9\columnwidth]{fig3_design_space_ieee}

{[}Auto × Auto{]} holds the research full-auto systems, machine-evaluated on both loops. {[}Auto × Human{]}, the production-viable cell, holds SkillForge, CASCADE, Sierra Agent OS 2.0, and Cognition Devin: Loop 1 fires at machine speed under an algorithmic criterion, and Loop 2 waits for a person. {[}None × Auto{]} holds the governance-first platforms, which gate promotion on evaluation but generate no candidates from failures; they pass only the Loop-2 half of the audit and enter the matrix as contrast entries (Supplementary Material S4).

One audit passer sits in neither gated cell. Letta's Context Repositories push shared memory across agents automatically, with git lineage and no evaluation of any kind, so the audit admits them on lineage and the matrix places them in {[}Auto × None{]}: a local loop with a gate, and a promotion with none. The cell makes the point the pair notation exists for. A push that carries every edit is not a gate, and the column records that nothing decides.

Seven systems promote across users, clients, teams, or repositories with no versioning or lineage on what they promote, and fail the audit on that alone. If the audit asked for a promotion mechanism and nothing more, six of them would enter, all in {[}Auto × Auto{]} except Spotify's production loop, which would land in {[}Auto × Human{]}; none would open a new cell. The seventh, Future AGI's prompt lifecycle, rests on a vendor blog alone, which the tier rule does not count, and is not admitted under any rule (Supplementary Material S2).

The human-gated row holds only curation. In {[}Human × None{]} an agent drafts and a person decides what is kept: VerificAgent's agent-drafted memories pass a human fact-check and are frozen \cite{nguyen2025verificagent}, and SkillChain's judge-approved skill edits re-enter a human reflection gate before they are deployed. Nothing in the row promotes. {[}Human × Auto{]} and {[}Human × Human{]} are empty: no surveyed system puts a person on the local gate of a failure-driven loop and then promotes the result, by program or by person. The systems that look like human-gated promotion on a first reading are registries, in which a person registers an artifact and a person, or an admission scan, approves its use, and no failure-driven loop runs at all. They sit in {[}None × Human{]}: the MCP registries and a community hub \cite{agenticcommunity2026mcpgateway, microsoft2026apicentermcp, truefoundry2026mcpgateway, jiang2026buildrix}, and, in practice, the five public skill repositories of one field study, where every substantive edit is human-authored and human-merged and one deprecation appears in 254 edits \cite{shen2026whomaintains}.

The occupancy bears out the three consequences of Section~\ref{sec:signal}. Every {[}Auto × Auto{]} system whose gate estimates the loss change per edit runs on an exact signal or a simulated outcome, and those that work on delayed signals prune proposals instead. {[}Auto × Human{]} holds only systems whose signal is an observed outcome or a judgment; no exact-signal system sits there. And no system in the matrix calibrates a judge that is itself under edit.

Two further patterns cut across the cells. The newer systems batch evidence before acceptance, where earlier ones accepted an edit on one evaluation and absorbed estimator noise through the per-edit margin alone: a paired per-item test commits an edit only when its wins are reliable \cite{wang2026sagegate}; a merge is accepted only when it fixes at least as many held-out items as it breaks \cite{nie2026evolvenet}; three heterogeneous critics must all pass \cite{shang2026vag}; mini-batch failure signals feed validation-based selection \cite{park2026autosaddler}. Requiring agreement among independent proposals and averaging over them are different operations that reduce error at different rates (Appendix~\ref{app:gates}). Multi-layer hierarchies remain rare: AlphaEvolve is the only system that combines a cascade evaluator with a diversity archive, and the other systems that keep archives use them for lineage, not for staged evaluation.

\section{Five research families converge on the loop}\label{sec:families}

The loop is not a prescription the field has yet to adopt. Five research families, starting from different substrates and under different names, have arrived independently at parts of it, which we read as evidence that the loop is a shared attractor rather than one group's local optimum. The vendors' convergence on one artifact format and tool attachment (Section~\ref{sec:findings}) is independent evidence of the same kind. Convergence does not show that the design is optimal, only that the same constraints keep producing the same shape.

The clearest single instance is SkillOpt \cite{yang2026skillopt}. It treats one markdown skill document as the trainable external state of a frozen agent and edits it with explicit optimizer controls: rollout and reflection batches, add/delete/replace edits, a bounded textual learning rate with cosine decay, a held-out selection gate that accepts only a strictly better score, a rejected-edit buffer kept as negative feedback, and an epoch-wise slow update. Across six benchmarks, seven target models, and three harnesses it is best or tied on every cell its authors evaluate, and it reports transfer across models, harnesses, and benchmarks, which reads as an empirical measurement of evidence radius rather than as a governance mechanism. Its own follow-up, SkillOpt-Lite \cite{shen2026skilloptlite}, removes the buffer, the slow update, and the schedule, keeps the held-out gate and a consensus filter across rollouts, and matches or beats it. The gate and a consensus form of credit assignment are load-bearing; the rest are stabilizers.

The five families instantiate complementary parts of the loop (Table~\ref{tab:VIII-1}), and each was pushed into its part by the constraint it started from. Reflective evolution started from trajectories and proposes edits by reflecting over them, with a two-timescale argument for keeping those edits outside the weights \cite{agrawal2025gepa, tiwari2026fastandslow}. Reflective context learning, the most direct independent formalization, started from the observation that credit assignment, overfitting, forgetting, and high-variance signals persist whether the learned object lies in parameter space or context space; its generalization penalty is the complexity term \(\Omega\) of the gate \cite{vassilyev2026rcl}. Harness optimization started from orchestration rather than skills and names credit assignment as its bottleneck; it is the largest family in the corpus, with roughly two hundred papers citing its founding entries and a dozen scored here \cite{lee2026metaharness, lin2026ahe, cai2026moss, zehle2026cantante, nguyen2026harnessevo, chen2026harnessforge, li2026growingharness}. The lifecycle family started from artifact pools that bloat and found hygiene to be a precondition for descent \cite{zhang2026ratchet}: the complexity penalty becomes a constraint frontier once platform limits bind \cite{tanjim2026mocha}, each outcome is attributed to skill, exploration, or environment before an update is admitted \cite{liu2026skillsvote}, and eleven systems make retirement a gated operation \cite{zhang2026librarydrift, wei2026skillsmith, pu2026skillops, wang2026assay}. The transfer family started from how far an edit travels and instruments Loop 2, from measuring evidence radius one task at a time to federating skill patches across clients or deployments \cite{shalev2026ict, li2026combee, qu2026coral, ling2026pace, yang2026federatedskill, nie2026evolvenet}.

Read against the loop, the families support four conclusions. The scaffold-versus-weights decomposition is independently confirmed: GEPA, Meta-Harness, MOSS, RCL, PACE, and the harness-optimization papers all begin from the observation that weights and the external artifact layer are distinct adaptation surfaces with different cost, reversibility, and scope, and a system that updates both keeps them as separate levers \cite{hebbar2026sia}. Credit assignment is the central engineering bottleneck: AHE, CANTANTE, Meta-Harness, HARNESSEVO, SkillsVote, and the harness-optimizer evaluation of Ong et al. \cite{ong2026harnesseval} all name the same step as what separates descent from trial-and-error, attributing a system-level failure to one scaffold coordinate, and that step remains unsolved in the general multi-substrate case. Lifecycle hygiene is a precondition for descent, not an alternative to it: a dirty artifact pool starves the gate of signal (Table~\ref{tab:X-1}), gated retirement is the field's answer, and the one negative result cuts deeper, since once a contaminated skill has descendants, rolling it back recovers little, so gating must happen before commit \cite{shang2026vag}. And no family has built the governed second loop: FederatedSkill and EvolveNet each narrow the gap on different properties, and neither meets the four that Section~\ref{sec:gap} sets out.

No system rolls back a promotion that has crossed an organization boundary, because none makes such a promotion (Supplementary Material S4).

In machine-learning terms, what is missing is a cross-tenant aggregator with an automated evaluation gate at the scaffold layer. It would carry five parts: per-tenant artifact pools, each tagged with provenance; an aggregation step across tenants that respects tenant isolation; a held-out evaluation at the receiving tenant that blocks a promotion whenever it does not lower that tenant's patch loss; versioned lineage with access control; and a rollback envelope on every promoted artifact. The federated-learning analogy \cite{mcmahan2017fedavg, mcmahan2018dpfedavg, kairouz2021federated} is useful only in the limit where artifacts are mergeable update representations; federated prompt tuning, in which participants learn a shared prompt rather than shared weights \cite{guo2022promptfl}, is the weight-side precedent closest to that limit. In surveyed practice Loop 2 is selection and merge, and the nearest systems aggregate program edits with a language model, not by averaging.

Whether the architecture \emph{should} be built depends on the feedback-signal class, not on the application domain (Section~\ref{sec:signal}). Where the signal is exact, automatically gated cross-tenant promotion of a test-validated skill would be low-risk, and receiving-side evaluation is cheap to add. Where it is an observable outcome, the sending side's outcome does not transfer, so promotion should be automated only behind receiving-side evaluation, the check that would catch a scaffold over-fitted to one deployment before it propagates to another. Even that check is necessary rather than sufficient: some of Evo2Team's transfers still fail on new graphs after target-side confirmation \cite{wang2026evo2team}. Where it is judged, a human gate on Loop 2 is a design feature, and governance means lineage and rollback around a human decision. Where it is delayed, property (a) cannot be met, and what remains is lineage and rollback without an automatic gate. Safety-critical domains, the usual case for human gates, are judged or delayed domains with high stakes. Naming the four properties turns a vague gap into an audit criterion that any future system can be measured against; naming the signal class says which of the four a given deployment should expect to meet.

Bloat is a signal-quality problem as well as a latency problem. Ratchet reports that LLM-authored skills gain nothing over a no-skill baseline while human-curated ones show a double-digit gain, and it attributes the gap to lifecycle management \cite{zhang2026ratchet}. In the vocabulary of Section~\ref{sec:loop}, that means residual capture and mode discovery cannot work on a messy artifact pool.

Evaluation fragility compounds because the evaluation suite is itself a patch-local artifact rather than a fixed instrument. It is optimized against: once a metric becomes the target, it is gamed. It is read non-independently, because the gate scores path-dependent agent trajectories whose readings do not compose like ordinary test-set statistics. It goes stale, because the suite adapts on the same cadence as the scaffold it gates. And because failures concentrate in a finite catalogue of recurring modes, a suite that samples tasks at random under-weights exactly the families that drive the failure rate. The response in the table follows from those four facts: held-out and scoped, mode-weighted, re-read, and checked against attribution rather than only against score.

The failure surface is real, quantified in the cited measurements, and largely unmitigated in production. Every row names a piece of the optimizer that current systems do not yet have.

\section{Open problems and conclusion}\label{sec:open}

Five open problems follow from the survey, one per feedback-signal class and one for the architecture.

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Exact signals: credit assignment from a failing check to a scaffold coordinate.} A test tells the loop that an output failed, not which instruction, skill, or tool binding caused it. Slot attribution \cite{nguyen2026harnessevo}, intervention-based attribution \cite{chu2026agentgrad}, and contrastive multi-agent attribution \cite{zehle2026cantante} each solve one substrate's case; a general method is the bottleneck the harness-optimization family names.
\item
  \textbf{Observable outcomes: receiving-side evaluation before promotion.} The outcome that justified an edit on the sending side does not transfer, and even where a promoted edit is checked on arrival, some transfers still fail (Section~\ref{sec:findings}). The gate a federated scaffold optimizer needs, a held-out test at the receiving tenant, has been proposed but not built \cite{yang2026fao}.
\item
  \textbf{Judged signals: calibrating a gate that is itself being edited.} When the rubric is a scaffold coordinate, each accepted edit to it moves the instrument that judges the next edit. No method that co-evolves a rubric or judge reports agreement with human judgment, and no scaffold system calibrates a judge under edit (Section~\ref{sec:signal}); the nearest measurement is on the human side, where evaluators' criteria drift as they grade \cite{shankar2024validators}.
\item
  \textbf{Delayed signals: telling descent from search.} Where the outcome arrives after many edits, an optimizer's gains cannot be distinguished from trial-and-error by outcome alone \cite{ong2026harnesseval}; evaluating harness optimizers against their attribution claims rather than their scores is the open method.
\item
  \textbf{The governed cross-organization loop.} The architecture of Section~\ref{sec:gap}, properties (a) through (d), is documented by no surveyed system; the receiving-side gate of problem 2 is the piece that would make cross-organization promotion safe in the two classes where it should be automatic.
\end{enumerate}

The field has built an external adaptation layer for language models and, as far as public evidence shows, not the optimizer that should govern it. The two earlier papers of this series supply the hypothesis for why the layer belongs where it is: errors concentrate in a few key decisions; inside a bounded deployment, those decisions fail in a small and recurring catalogue of modes; and such a catalogue can be fixed one mode at a time in a persistent, inspectable, reversible artifact outside the weights. The corpus is consistent with that hypothesis, and on it the gated and scoped artifact layer is the architecture the error structure calls for, not a workaround.

The survey shows how far practice has come toward that optimizer, and the distance is uneven. The local loop closes automatically in most research systems and in a growing number of production ones; evidence is batched before acceptance; retirement and expiry are first-class operations; production memory carries lineage. What has not moved is the second loop. No surveyed system promotes a validated edit across an organization boundary under an automatic gate with lineage, access control, and rollback. The signal-class analysis says this is not one gap but four, each with its own reachable answer. The frontier model generalizes. The local scaffold specializes. Reliability comes from governing that specialization. Because the instruments that judge each edit are themselves part of the moving scaffold, the same evidence-radius and lifecycle discipline the optimizer needs must extend to the gates that judge it.

\subsection{Setup}\label{setup}

Let the frontier model have fixed parameters \(\theta_M\) and let the scaffold be a structured object \(\theta_s \in \Theta_s = \Theta_1 \times \cdots \times \Theta_6\) over the six substrate coordinates of Section~\ref{sec:method}; \(\Theta_s\) is discrete, symbolic, and versioned. For a deployment \(D\), \(L_D(\theta_s) = \mathbb{E}_{x \sim D}[\ell(\pi(\theta_M, \theta_s, x))]\). A candidate edit \(z_t \sim Q_t(z \mid H_t, \theta_s^t)\) is drawn from a proposal process conditioned on the accumulated history \(H_t\) of failures, corrections, rejected outputs, evaluation regressions, and prior accepted edits. \(Q_t\) is not uniform: for a mode \(m\) that recurs with frequency \(f_m\) and carries per-occurrence loss \(s_m\), its expected contribution to the failure rate is \(f_m s_m\), so high-frequency or high-severity modes are proposed first. The finite directional difference is \(\Delta_z L_D(\theta_s) = L_D(\theta_s \oplus z) - L_D(\theta_s)\); the gate sees only a noisy estimate \(\widehat{\Delta}_z L_D\). The update is \[\theta_s^{t+1} = \theta_s^t \oplus z_t \text{ if } G_t(z_t) = 1, \quad \theta_s^{t+1} = \theta_s^t \text{ otherwise.}\]

\subsection{Descent inequality}\label{descent-inequality}

Assume (A1) positive descent bias on accepted edits, \(\mathbb{E}[\widehat{\Delta}_{z_t} L_D \mid G_t = 1, \theta_s^t] \le -\gamma_t - \tau_t\) for some \(\gamma_t > 0\), and (A2) bounded estimator bias on accepted edits, \(|\mathbb{E}[\Delta_{z_t} L_D - \widehat{\Delta}_{z_t} L_D \mid G_t = 1, \theta_s^t]| \le \varepsilon_t\). With \(p_t = \Pr(G_t = 1 \mid \theta_s^t)\), \[\mathbb{E}[L_D(\theta_s^{t+1}) \mid \theta_s^t] \le L_D(\theta_s^t) - p_t(\gamma_t + \tau_t) + p_t\,\varepsilon_t.\] Per-step expected improvement is the gate's margin minus its estimator bias, weighted by acceptance probability. In the feedback-signal classes of Section~\ref{sec:signal}, \(\varepsilon_t\) is near zero for the check itself in C1, with the sampling error of a finite suite over the patch remaining, bounded by batching for an observable outcome (C2), equal to the judge's bias and bounded only by calibration for a judged signal (C3), and unavailable per edit for a delayed signal (C4).

\subsection{Convergence (informal)}\label{convergence-informal}

Add (A3) proposal coverage with acceptance: at every non-gate-stable scaffold, \(Q_t\) places probability at least \(q > 0\) on an admissible edit with \(\mathbb{E}[\Delta_z L_D] \le -\delta\), and the gate accepts such an edit with probability at least \(q' > 0\), so that \(p_t(\gamma_t + \tau_t) \ge q q' \delta\) there; (A4) effective compactness of the reachable orbit; and (A5) summable bias, \(\sum_t p_t \varepsilon_t < \infty\); and let \(0 \le L_D \le B\). The one-step inequality is then of the Robbins--Siegmund form, a non-negative process that decreases in expectation up to a summable perturbation \(p_t \varepsilon_t\), so \(L_D(\theta_s^t)\) converges almost surely and \(\sum_t p_t(\gamma_t + \tau_t) < \infty\) almost surely \cite{robbins1971convergence}. The finite sum carries the content: a bounded loss cannot pay for infinitely many accepted edits with a positive expected margin, so under (A3) the process visits non-gate-stable scaffolds only finitely often, and with (A4) the limit set of \(\{\theta_s^t\}\) is gate-stable: no admissible edit clears the gate with negative expected directional loss in the limit. This is convergence of the loss and stability of the gate decision, not convergence to an optimum; a globally suboptimal gate-stable scaffold is consistent with the result, because \(Q_t\) may never propose the improving edit or \(\widehat{\Delta}\) may be biased to reject it. In a non-stationary deployment (\(D = D_t\)) the same mechanism tracks a moving optimum rather than converging once, which is why recency weighting, pruning, expiry, and rollback are the scaffold-level analogues of continual-learning machinery rather than optional hygiene.

\subsection{Correspondence}\label{correspondence}

Table~\ref{tab:A-1} pairs each optimization concept with its scaffold analogue. Credit assignment here is attribution, not backpropagation. Scaffold systems do not differentiate through instruction files; they trace an output error to an upstream coordinate, manually or with a judge or verifier. The descent argument needs only that this attribution succeeds with non-zero probability per failure, which is the credit-assignment condition of Section~\ref{sec:loop}.

\subsection{Worked cases}\label{worked-cases}

\emph{Retrieval.} Failures recur because retrieved context omits the decisive clause. Attribution traces the error to the retrieval coordinate: chunking, query rewriting, metadata filter, embedding model, reranker, or context-packing rule. The candidate edit tightens chunk boundaries or adds a metadata constraint, and the gate checks that recall and answer accuracy improve on the patch evaluation without degrading adjacent cases. Signal class C1 or C2.

\emph{Pitch review.} The system repeatedly overrates decks that claim a large market without numbers. The failure cluster points at an under-specified rubric coordinate. The edit changes ``evaluate market size'' into ``require a numeric estimate and a source; if absent, cap the score''. The gate runs the revised rubric against held-out decks with human scores. The edit changed the gate that will judge the next edit: the reflexive gate of Section~\ref{sec:signal}, class C3.

\emph{Tool use.} Calls fail because optional parameters are under-specified. The responsible coordinate may be the tool schema, the call policy, or the clarification rule. The edit adds required fields or a pre-call uncertainty check; the gate checks that tool-call failures fall without raising refusals or latency. Class C2.

\emph{Memory.} A stale customer preference is repeatedly retrieved and causes bad decisions. The responsible coordinate is a memory entry together with its provenance, priority, and expiry policy. The edit corrects, expires, or version-tags the entry; the gate checks that future behavior improves without erasing useful history. Class C2, with the correction itself observable only when a later outcome reveals it.
