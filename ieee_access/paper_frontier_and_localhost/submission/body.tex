\section{Introduction}\label{sec:intro}

A coding agent repeatedly uses the wrong naming convention in a repository. An engineer adds a line to its instructions, and the next session follows the convention. The model has not changed, but the deployed system has. Similar changes happen when an assistant corrects a stored preference, acquires a reusable skill, or learns which tool to call. Much of the experience that makes an AI system useful in one setting now accumulates in these persistent artifacts outside the model's weights.

We call this layer the \textbf{scaffold}. It includes instructions, skills, memory, tools, orchestration, and the evaluation and governance rules that control their use. In the language of compound AI systems \cite{zaharia2024compound}, it is the part surrounding the model that a deployment can inspect and revise without retraining it. The distinction matters because the two parts change on different schedules. A team can revise an instruction or tool binding as soon as a problem is understood, while a new model requires a separate training, evaluation, and release process.

The ease of making a change also makes it easy to accumulate changes whose value is unknown. A rule added after one incident may prevent a recurring error, conflict with another rule, or merely make the prompt longer. A corrected memory may remain in the history while the system continues to retrieve the outdated entry. Even a demonstrably useful change can become harmful when copied into a deployment with different tasks or conventions.

These situations raise two questions. What evidence justifies keeping a local change? What additional evidence justifies sharing it? This survey uses those questions to examine 256 public production and research systems. The first defines a \textbf{local loop}: identify a recurring failure, propose a change to the responsible artifact, and test whether the change helps. The second defines a \textbf{promotion loop}: decide whether the change should be adopted by another project, team, or organization, and preserve enough history to reverse that decision.

The systems surveyed have developed these loops unevenly. Automatic tests for accepting a local edit are present in nearly every recently added system that has a local loop: 89 of 96. The steps that should supply those tests with well-founded candidates are weaker: failures are often not retained in a usable form, and a failed output rarely identifies which instruction, memory, skill, or tool binding caused it. Meanwhile, production platforms have built substantial versioning and release machinery without any process that proposes changes from deployment experience.

Sharing adds a further limitation. A change that improves one deployment has been evaluated against that deployment's tasks and measure of success. Another deployment may need different behavior. Shared formats and registries make artifacts portable, but they do not establish that an artifact will help its recipient. Some surveyed systems check transferred changes within one operator. None documents an automatic local improvement loop connected to promotion across organizations with versioned lineage, access control, and rollback.

The feedback available to each system helps explain these differences. A compiler or test suite can check a candidate immediately. A booked appointment provides a later, noisier outcome. A writing task may depend on a judge, whose preferences can drift. A research decision may take months to evaluate. These signals support different kinds of automation, and none establishes an improvement beyond what it actually measures.

The survey develops a framework for reading this evidence. We first define the two loops and the conditions under which artifact maintenance constitutes optimization. After describing the corpus and scoring method, we examine local adaptation, the feedback that constrains it, and the evidence needed for promotion. The later sections consider failures that arise when these checks are missing, specify the unassembled architecture for governed sharing, and connect the findings to the research lines that produced its components. The evidence consists of published methods and public documentation; the survey introduces no new experiments. Its scores and classifications are released for inspection.

\section{From a local fix to a measured improvement}\label{sec:loop}

Adding a naming rule after an error is a reasonable response. To learn whether it works, however, the team must run the agent again on relevant tasks and compare the results. If the change helps, it should persist. If it causes regressions, the team needs a way to reject or reverse it. Repeating this process turns a growing collection of fixes into a procedure for improving the deployment.

\subsection{The local loop}\label{the-local-loop}

The procedure starts with a record of failures: rejected answers, user corrections, failed tool calls, evaluation regressions, or unsuccessful tasks. Repeated failures are grouped into modes and prioritized by frequency and severity. For each selected mode, the system tries to identify the artifact responsible. A stale memory entry calls for a different intervention from a missing tool argument or an ambiguous instruction.

We call this step \textbf{credit assignment}. It links an observed failure to an editable part of the scaffold, or \textbf{coordinate}. The system then proposes a candidate edit and evaluates it against the current scaffold. The acceptance test is the \textbf{gate}. An accepted edit is retained as a versioned artifact; subsequent evidence of regression can trigger rollback. Fig.~\ref{fig:descent} shows the complete local loop.

The evaluation must be tied to the deployment's actual workload. A deployment serves a particular distribution of users, tasks, and conventions, which we call its \textbf{patch}. Its \textbf{patch loss} measures failure on that distribution. Depending on the application, this may be a task-failure rate, correction rate, retrieval error, or another operational measure. A gate can establish an improvement only to the extent that its evaluation estimates this loss.

\subsection{The second decision: whether to share the fix}\label{the-second-decision-whether-to-share-the-fix}

Suppose the naming rule improves the original repository. The team may now consider adding it to a shared template. That decision changes the population on which the rule will act. Other repositories may follow a different convention, and the local evaluation says little about them.

The promotion loop therefore asks for evidence at the receiving scope. We call this \textbf{receiving-side evaluation}: a check conducted on the tasks of the deployment that would adopt the edit. The \textbf{evidence radius} is the scope for which the available evaluation supports the change. A local success does not automatically enlarge that radius. Section~\ref{sec:design} develops the scopes and examines systems that already transfer artifacts between them.

\subsection{Five conditions for artifact-layer optimization}\label{five-conditions-for-artifact-layer-optimization}

We use \textbf{artifact-layer descent} for the form of maintenance that connects recurring failures to measured improvements through five conditions:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{A measurable patch loss:} the deployment has a defined measure of success or failure.
\item
  \textbf{A failure log:} relevant failures are retained as evidence for later changes.
\item
  \textbf{Credit assignment:} failures can, at least sometimes, be traced to the scaffold coordinates responsible.
\item
  \textbf{A candidate edit:} the process proposes a change to those coordinates.
\item
  \textbf{An acceptance gate:} an edit is retained or promoted only after a check of whether it lowers the relevant loss.
\end{enumerate}

The model weights remain fixed during this process, and the edits persist beyond the current interaction. These conditions distinguish three recurring forms of maintenance. In \emph{patchwork}, an engineer adds a rule after an incident without measuring the result. In \emph{random artifact search}, a system tests many variants and keeps a winner without tracing failures to their causes. Artifact-layer descent uses that trace to direct the proposed change and tests it before acceptance. Where the conditions are only partly met, the optimization interpretation is correspondingly limited.

For deployment \(D\), write the patch loss as \[L_D(\theta_s)=\mathbb{E}_{x\sim D}\!\left[\ell(\pi(\theta_M,\theta_s,x))\right],\] where \(\theta_M\) denotes the fixed model weights, \(\theta_s\) the editable scaffold, and \(\ell\) the operational loss. A proposal process uses the failure history to produce an edit \(z_t\). There is no analytic gradient through an instruction file or memory entry. Instead, the gate estimates the change in loss and accepts when that estimate clears a required margin: \[G_t(z_t)=1\iff\widehat{\Delta}_{z_t}L_D(\theta_s^t)+\lambda\Omega(z_t)\leq-\tau_t.\] Here \(\Omega\geq0\) penalizes edit complexity and promotion breadth, and \(\tau_t\geq0\) is the acceptance margin. An evaluation that blocks a regressing merge is a practical instance of this rule. A reviewer or governance process can also instantiate the gate by requiring stronger evidence for a broader or more complex change.

Appendix~\ref{app:formal} gives the update rule and a one-step descent inequality under assumptions on the gate's estimation bias. With additional coverage, compactness, and summable-bias assumptions, improving edits eventually stop clearing the gate. This is \textbf{gate stability}, not a claim of global optimality. A limited proposal process or biased evaluator can leave useful changes undiscovered or rejected.

\subsection{Who proposes and who decides}\label{who-proposes-and-who-decides}

The author of an edit and the authority that accepts it are separate. An agent may draft a revision that a person approves; an engineer may write a revision that an automatic evaluation rejects. We classify the gate by who makes the acceptance decision:

\begin{itemize}
\tightlist
\item
  \textbf{Auto:} a program applies a check, including a verifier, evaluation threshold, or language-model judge \cite{zheng2023judge}. Whether that judge has been calibrated against people is a separate question, which Section~\ref{sec:signal} takes up.
\item
  \textbf{Human:} a person decides whether to accept the change.
\item
  \textbf{None:} no acceptance decision is made, either because the loop is absent or because every proposed edit is retained.
\end{itemize}

A pair such as {[}Auto × Human{]} denotes an automatic local gate followed by a human promotion gate. These labels describe the decision mechanism. They do not, by themselves, establish that the decision is well supported.

The loss definition imposes two limits on every such loop. First, an accepted edit is evidence of improvement only on the measure and tasks evaluated. Promotion must preserve that meaning or establish the improvement again. Second, the loop optimizes a defined objective. It does not discover a better objective simply by accumulating edits. Revising the evaluator changes the objective itself, a complication we return to in Section~\ref{sec:reflexive}.

\section{Corpus and method}\label{sec:method}

We read each system's public method or documentation for four things: the persistent artifact it changes, the feedback that prompts the change, the decision that accepts it, and the scope in which the result is used. This allows systems with different names and application domains to be compared by their behavior.

\subsection{Scope and selection}\label{scope-and-selection}

The corpus contains 256 unique systems from January 2023 through the October 2026 cutoff. The first search pass identified 130 systems by May 2026; the second added 126. Sources include research papers, public repositories, product documentation, and supported production reports; the search families, evidence tiers, and inclusion rules are recorded with the released data (Supplementary Material S2).

A system enters the survey if it adapts a foundation model through a persistent artifact updated from deployment signal, or if it is publicly described as self-improving, scaffolded, or agentic. Including the latter group provides a contrast set: the survey can test whether those descriptions correspond to persistent adaptation. Systems whose only update mechanism is weight-level training are excluded, as are systems without public evidence of release or deployment.

We apply two filters. The first admits a system to the \textbf{core corpus} if it scores at least 3 on at least one scaffold substrate under the rubric below. Of the 256 systems, 204 form the core corpus and 52 the contrast corpus. A system may have one integrated row or several substrate-specific rows, so the 256 systems occupy 269 scored rows.

The second filter is a \textbf{two-loop audit}. It asks whether session feedback changes a persistent artifact and whether that artifact is subsequently promoted beyond the deployment that produced it, with versioning or lineage. Applied to 202 of the 204 core systems and to 4 research systems classified from their papers alone (SkillOpt, FederatedSkill, SkillClaw, and ChronoMem), it admits 11 research systems and 3 industry exemplars; the eight systems without an audit are listed with the contrast set (Supplementary Material S4). Fig.~\ref{fig:corpus} summarizes the selection.

The research systems passing the audit are NanoResearch, SkillOpt, AlphaEvolve, ADAS, DGM, Voyager, SAGE, EvolveR, CoEvoSkills, AutoManual, and CASCADE. The industry exemplars are Sierra Agent OS 2.0, Cognition Devin, and Letta's Context Repositories. SkillOpt is classified from its paper and is not a row in the 256-system score table. The remaining paper-based systems are identified in the data notes (Supplementary Material S2) and the audit's boundary cases in the contrast set (Supplementary Material S4).

Passing this audit does not establish governed sharing across organizations. All passing systems promote within one operator, into a shared bank or archive that later runs draw from, or across the agents and sessions of one deployment. Letta passes on the lineage of its shared-memory updates even though those updates have no acceptance gate. Six further systems promote across contexts without lineage on the promoted artifact; their treatment under relaxed audit rules is reported separately.

\subsection{Evidence and limitations}\label{evidence-and-limitations}

The evidence ranges from peer-reviewed studies and open-source artifacts to vendor claims. Every row of the released table carries its source and a one-line justification, and the rows for the 126 most recently added systems also carry an evidence tier. Peer-reviewed papers and open-source artifacts receive the greatest weight. A production claim must name a benchmark or integration target, and a blog or interview is counted only when stronger evidence corroborates it. Production claims are not pooled with peer-reviewed evidence in corpus-level statistics; vendor-based exemplars are identified as such.

One author scored all systems. Ambiguous cases were rounded down, and half-scores were used only when one criterion was clearly met and another partly met. Independent re-rating remains future work. The classifications should be read as an auditable interpretation of public evidence, not a complete inventory of private production behavior.

We also test the audit under alternative boundaries: counting rollback as sufficient promotion governance, allowing promotion without governance, and admitting loops that persist only optimizer state. Membership changes under these relaxations, but the principal structural findings remain: {[}Auto × Auto{]} stays well populated, the human-local cells hold only curation and registries, Letta alone passes with an ungated promotion, and no relaxation adds governed promotion across organizations (Section~\ref{sec:gap}). The sensitivity analysis is released with the data notes (Supplementary Material S2) and the full score table with the released table (Supplementary Material S1).

\section{What local adaptation actually closes}\label{sec:findings}

A system can detect a failure, explain it, and write a plausible correction without ever establishing that the correction helps. SkillForge illustrates this distinction. Its judge agrees with people more than nine times in ten and identifies replies that should be rewritten. Those replies drive updates to the skill, but the updated skill is committed without an acceptance test \cite{skillforge2026}. The calibration concerns which replies are inadequate. It does not measure the effect of the resulting skill changes.

SkillRL exposes the same separation through a different mechanism. A success-rate threshold triggers proposals for new skills, and the skill bank accepts each proposal unconditionally \cite{skillrl2026}. Both systems respond to experience, yet neither has the local acceptance gate defined in Section~\ref{sec:loop}. This is why the survey records who accepts an edit separately from who generates it or which signal triggers it.

Among the 105 core systems most recently added to the corpus, 96 have a local loop, and automatic acceptance is nevertheless the dominant pattern among them: 89 use a program to retain or reject changes. Looking inside those loops reveals a less even picture. Evaluation is comparatively mature, while the failure record and the link from a failure to the responsible artifact are often incomplete.

\subsection{Finding the right thing to change}\label{finding-the-right-thing-to-change}

A useful failure history must retain what went wrong in a form that supports later comparison. Production memory more often records preferences, successes, or conversation history. Only one field report in the corpus describes a store of dead ends intended to prevent their recurrence, and that evidence comes from a single self-reported deployment \cite{helwig2026memory}. The persistent store may therefore be extensive while the particular record needed for failure-driven adaptation is missing.

Even when failures are retained, nearly every system uses them in arrival order. Few explicitly choose which recurring modes deserve attention. Task-CoEvolve's variance-weighted task sampling and AutoSaddler's mini-batch failure signals are exceptions \cite{miyai2026taskcoevolve, park2026autosaddler}. They weight the experience used for the next update rather than letting the most recent session determine it. The general loop described earlier would prioritize both recurrence and severity; this remains uncommon in the surveyed implementations.

The next step is harder. A failed output does not reveal whether its cause was an instruction, a retrieved memory, a skill, or the route through a group of agents. Harness-optimization papers repeatedly identify this attribution problem as the bottleneck \cite{lin2026ahe, zehle2026cantante, lee2026metaharness, nguyen2026harnessevo, liu2026skillsvote}. An evaluation of harness optimizers reaches the same conclusion: by downstream score alone, a harness optimizer cannot be told from trial and error \cite{ong2026harnesseval}.

Existing solutions usually operate within one substrate. Meta-Harness preserves candidate harnesses and the record of which edits helped \cite{lee2026metaharness}. SkillsVote attributes outcomes to the skill, exploration, or environment before admitting an update \cite{liu2026skillsvote}. SkillOpt-Lite keeps only the attributes that recur across rollouts, and its ablation finds this consensus mechanism load-bearing \cite{shen2026skilloptlite}. These methods give the proposal process more useful evidence. None solves the general attribution problem across all six scaffold substrates.

\subsection{Testing the candidate}\label{testing-the-candidate}

Research systems commonly generate candidates by reflecting on trajectories. In production prompt platforms, an engineer writes the candidate and session feedback never triggers one, while public skill repositories depend on contributors. A field study of five such repositories finds that every substantive edit was committed under a named human account and merged by a person, most carrying an AI co-author trailer \cite{shen2026whomaintains}. Where proposal generation depends on a person noticing a problem, the evaluation machinery can run automatically while the improvement process itself remains intermittent.

On skills, SAGE and COSPLAY close both local and promotion loops inside a research environment \cite{wang2025sage, wu2026cosplay}. SkillChain adds a human reflection decision after the judge, on which refined skills are deployed \cite{hu2026skillchain}. SkillRL and SkillForge, described above, leave the proposed changes unchecked. These differences would be obscured by classifying all three simply as systems that learn from feedback.

Orchestration has followed a similar progression. Early systems searched for agent topologies under an evaluation score \cite{zhuge2024gptswarm, zhang2024aflow}. More recent systems evaluate proposed topology changes before keeping them; TOCOMAS also requires a structural invariant \cite{chu2026agentgrad, chen2026harnessforge, zhao2026tocomas}. OptiMAS is an exception: its optimizer reads trajectories and validation scores to write the next configuration, but the score informs the edit rather than supplying a keep-if-better decision \cite{cheng2026optimas}. No orchestration system closes both loops with lineage on the promoted artifact.

The most widely deployed artifact remains a useful counterpoint. Instruction files are present across Claude Code, Cursor, AGENTS.md \cite{agentsmd2025}, Windsurf, and Continue.dev, and adoption studies find them in roughly a fifth to a quarter of coding-agent projects \cite{robbes2026agenticmuch, galster2026harnessconfig}. Their prevalence does not settle their effectiveness. One controlled study reports higher inference cost without improved task success \cite{gloaguen2026agentsmd}. Another toggles the root AGENTS.md in paired runs on 124 pull requests and reports about 29\% lower median wall-clock time and 17\% fewer median output tokens, with total tokens approximately unchanged; it does not measure correctness \cite{lulla2026empirical}. The studies measure different outcomes and disagree on cost. Neither establishes a general task-success benefit from accumulating instruction files.

Human local gates appear only in curation. VerificAgent uses fact-checked, frozen memories \cite{nguyen2025verificagent}, and in SkillChain a person decides, at a reflection gate, which refined skills are deployed. Prompt platforms and registries without a failure-driven proposal process have no local gate in this classification. Their checks act on release or admission to a shared pool, which belongs to promotion.

\subsection{Gathering enough evidence to accept}\label{gathering-enough-evidence-to-accept}

An acceptance test can itself be too noisy to support a decision from one run. Several newer systems address this directly. SAGE-gate, a statistical acceptance method unrelated to SAGE, uses paired per-item comparisons before committing an edit \cite{wang2026sagegate}. VaG requires three heterogeneous critics to pass \cite{shang2026vag}. AutoSaddler uses mini-batch failure signals in validation-based selection \cite{park2026autosaddler}.

These mechanisms should not be conflated. Averaging \(k\) independent noisy scores reduces the variance of their mean by a factor of \(1/k\). Requiring agreement among \(k\) independent checks, each with false-acceptance probability \(p\), gives the idealized probability \(p^k\). The independence assumptions matter, and actual critics need not satisfy them. Appendix~\ref{app:gates} distinguishes the gate families and their roles. The shared development is that acceptance increasingly depends on a body of evidence rather than one favorable observation.

\subsection{Maintaining the artifacts that survive}\label{maintaining-the-artifacts-that-survive}

The evaluation of a new edit also depends on the artifacts already present. Stale or conflicting skills can cause failures that obscure the effect of the candidate under test. Ratchet reports no gain from model-written skills over a no-skill baseline until lifecycle hygiene is applied, while human-curated skills provide a double-digit gain \cite{zhang2026ratchet}. Eleven surveyed skill systems now treat removal as an operation that must pass a check, just as admission does \cite{zhang2026librarydrift, wei2026skillsmith, pu2026skillops, wang2026assay} (Supplementary Material S6).

Memory products have made substantial progress on a different part of maintenance: recording an entry's history. Letta's Context Repositories use git, Mem0 retains per-memory history, and Zep represents facts bitemporally \cite{letta2026memfs, mem02026history, zep2026facts}. These records can explain what the system remembers and how that state arose.

History does not guarantee correction. A study of five production backends finds that all five still return facts that were revoked \cite{shen2026revoked}. The record contains the change, but retrieval does not reliably enforce it. Research systems likewise divide between provenance and write controls \cite{wang2026toki, xu2026ppmf, margalit2026governed, sun2026vermem} and verifier-gated failure correction \cite{yu2026recuris, wang2026memguard}. Cuadros et al.'s governed collaborative memory combines provenance, versioning, and correction, earning the top memory score \cite{cuadros2026governed}.

Reversal has its own limits. SkillSmith and SkillAudit support edit-level rollback \cite{wei2026skillsmith, gao2026skillaudit}, and EvoUndo rejects edits that cannot be undone \cite{sah2026evoundo}. VaG finds that reversing a contaminated skill recovers little once other skills have been derived from it \cite{shang2026vag}. The consequences of an edit may therefore outlast the edit itself. Section~\ref{sec:failure} returns to this problem when considering promotion and artifact descendants.

\subsection{A complete local example}\label{a-complete-local-example}

SkillOpt provides a concrete instance of all five conditions \cite{yang2026skillopt}. Its persistent state is one markdown skill document used by a frozen agent. Rollout and reflection batches supply the failure evidence. A consensus filter helps attribute recurring errors, and bounded add, delete, and replace operations propose changes. A held-out exact-match split supplies the loss, and a candidate is accepted only when its score strictly improves.

Across six benchmarks, seven target models, and three harnesses, SkillOpt is best or tied in every cell reported by its authors. Its follow-up, SkillOpt-Lite, removes a rejected-edit buffer and slow update schedule while retaining the held-out gate and consensus filter; it matches or exceeds the original \cite{shen2026skilloptlite}. This comparison supports the importance of the gate and this form of credit assignment in that setting, while identifying the removed controls as stabilizers rather than necessities.

SkillOpt also evaluates transfer across models, harnesses, and benchmarks. Those experiments measure how far the learned artifact remains useful. They are distinct from the acceptance decision that admits an edit to the shared skill bank. This distinction becomes central once the same local procedure is used in settings where correctness is harder to measure.

\section{What the feedback allows a gate to know}\label{sec:signal}

A coding agent changes a repository rule and receives a test result within seconds. A scheduling assistant changes its booking procedure and learns later whether an appointment was made. A marketing assistant changes its tone instructions and receives a reviewer's preference. A research assistant changes its strategy and may wait months to learn whether the direction was productive.

All four systems can propose a persistent edit. What differs is the evidence available for accepting it. The signal's timing, exactness, and dependence on judgment determine how well a gate can estimate the change in loss. We divide the surveyed systems into four feedback classes, summarized in Table~\ref{tab:IV-1}.

The classes are assigned by the constraint that binds first. A long delay makes a signal C4 even when the eventual outcome is objective. Among timely signals, the absence of an independent ground truth makes the signal C3. Among timely objective signals, repeatable exact checks distinguish C1 from noisy observed outcomes in C2. A system may use several signals, but its operative acceptance decision must be read against the signal that supports it.

\subsection{Exact checks: C1}\label{exact-checks-c1}

A compiler, proof checker, schema validator, or exact-match answer key can decide a specified property immediately and repeatably. This makes an automatic gate straightforward to implement. AlphaEvolve scores candidates through a cascade of exact evaluators \cite{alphaevolve2025}, and SkillOpt uses held-out exact-match evaluation \cite{yang2026skillopt}. DGM makes a narrower acceptance decision: it retains self-modifications that pass a sandboxed compile-and-edit functionality check on ten benchmark tasks. The broader benchmark score weights parent selection from the archive rather than determining retention \cite{zhang2025darwin}.

Exactness applies to the check, not to the deployment as a whole. Repeating a deterministic check on the same output yields the same answer, but an agent produces stochastic outputs, and a finite suite samples only part of the task distribution. Estimating the change in patch loss still requires accounting for that variation. Passing the suite also establishes only the properties the suite tests.

Two problems remain even with a reliable checker. A failed test may not identify the instruction or skill that caused the failure, and repeated optimization against the same suite can overfit it. Cheap acceptance can also allow the artifact pool to grow without sufficient pruning. Exact feedback makes evaluation easier; it does not supply attribution or lifecycle management.

\subsection{Observed outcomes: C2}\label{observed-outcomes-c2}

A booked appointment, closed ticket, merged pull request, or successful tool call provides an observable result after an episode. The result is meaningful but may be noisy or confounded. A user can accept an incorrect answer or reject a correct one, and a merged pull request reflects more than the agent's technical performance.

Devin reads merged pull requests as feedback \cite{cognition2025devinreview}. SAGE measures task success in AppWorld \cite{wang2025sage}, and PACE uses failure signals from a deployed small model \cite{ling2026pace}. SkillRL uses a success-rate threshold only to trigger proposals, without testing whether the proposed skills should remain \cite{skillrl2026}. The same kind of outcome can therefore support different operations in different systems.

Simulated outcomes, such as those in Voyager's game world or SAGE's AppWorld, remove the user confound and can be sampled repeatedly. They are treated as a distinguishable case within C2. For observed outcomes more generally, an automatic gate needs a positive margin and enough episodes or independent evidence to absorb noise. Even then, the result usually reveals that the task failed more readily than why it failed.

Promotion is harder because another deployment may differ in users, tasks, and acceptance behavior. A sender's successful outcome is not an evaluation of the recipient. This class also depends on channels that can carry poisoned memories or injected tool instructions, connecting the reliability of feedback to the integrity of its source.

\subsection{Judgments: C3}\label{judgments-c3}

For style, persuasion, design, or other preference-dependent tasks, a gate relies on a person, rubric, reference comparison, or model judge. There is no independent exact answer to the preference being measured. CASCADE uses a human-and-agent gate for memory consolidation \cite{huang2025cascade}, and a reviewer approves promotion into Anthropic's skills repository. SkillForge uses its calibrated judge earlier in the process, to identify replies that motivate a rewrite \cite{skillforge2026}.

A program can make these decisions, but its score must be calibrated against the human judgment it is intended to represent before the score is treated as evidence of that preference. The gate labels deliberately do not record this distinction: an uncalibrated model judge is still an Auto gate, though the meaning of its acceptances is less established. SkillForge, SkillChain, and SkillCoach report calibration measurements \cite{skillforge2026, hu2026skillchain, zhu2026skillcoach}; no other surveyed judge does.

Optimization introduces another risk. A scaffold can become better at satisfying the judge while becoming worse at the underlying task. Reward-model research measures this form of proxy overoptimization \cite{gao2023overoptimization}. Human evaluation is not fixed either: Shankar et al.~find that evaluators' criteria change as they grade more outputs \cite{shankar2024validators}. If the system also edits the rubric, it changes the instrument used to assess subsequent edits. This \textbf{reflexive gate} is developed in Section~\ref{sec:reflexive}.

\subsection{Delayed and sparse outcomes: C4}\label{delayed-and-sparse-outcomes-c4}

Research programs and open-ended discovery may produce meaningful outcomes only after weeks or months and many intervening edits. The AI Scientist illustrates the broad setting by generating ideas, conducting experiments, and writing a paper \cite{lu2024aiscientist}. The eventual outcome cannot usually be assigned to each preceding scaffold change.

Systems in this class consequently use intermediate decisions. NanoResearch merges skills by semantic compatibility \cite{xu2026nanoresearch}. CORAL promotes findings into shared memory on a heartbeat \cite{qu2026coral}. These operations can prune or consolidate proposals, but they do not estimate each edit's contribution to the eventual loss. AlphaEvolve's archive diversity does not make it a delayed-signal example: its candidates have already been scored by exact evaluators, so archive selection is a search strategy within C1 \cite{alphaevolve2025}.

For C4, the descent interpretation applies only to whatever proxy gate is available or to an evaluation at the longer horizon. Temporal credit assignment remains unresolved, and the environment can change before the result arrives. Outcome gains alone are also insufficient to distinguish directed improvement from a successful search, a limitation emphasized in the evaluation of harness optimizers \cite{ong2026harnesseval}.

\subsection{Consequences for the two loops}\label{consequences-for-the-two-loops}

The classification yields three expectations that can be checked against the corpus. First, local automatic acceptance is most directly supported by exact checks and observed outcomes. Judged acceptance depends on calibration, while delayed feedback cannot evaluate edits individually until the outcome arrives. Second, automatic promotion that estimates a loss change should occur only where a comparable check can be applied at the recipient, in exact and re-runnable simulated settings, and human promotion should hold the observed outcomes and judgments. Delayed feedback supports no immediate per-edit gate on either half. Third, the main failure risks should differ: overfitting to a suite and bloat under exact feedback, corrupted outcome channels under C2, proxy optimization under C3, and drift under C4.

These are expectations about the evidence a gate can establish, not restrictions on whether software can execute a decision. A program can merge two judged artifacts or prune a delayed proposal without estimating a loss change. Section~\ref{sec:design} makes this qualification explicit in the gate grid. In every class, sharing remains an additional empirical question: even the same exact checker must be applied to the recipient's relevant cases before broader performance is established.

\section{When a local improvement is shared}\label{sec:design}

A rule can be useful in one repository and inappropriate in the next. Copying the file transfers the instruction, but not the evidence that justified it. The recipient must either share the relevant evaluation conditions or test the change on its own workload. This is the additional decision that separates local adaptation from promotion.

\subsection{Scope and receiving-side evaluation}\label{scope-and-receiving-side-evaluation}

We distinguish five nested scopes. \textbf{USER} covers one person's account or fork. \textbf{PROJECT} covers a repository, workflow, or product workspace. \textbf{STACK} is a team's curated bundle of projects. A \textbf{TENANT} is an organization or customer, and \textbf{CORE} is the scope shared by all tenants. A wider scope aggregates the losses of the deployments it contains. Promotion changes which population the edit is intended to improve, as shown in Fig.~\ref{fig:scope}.

The nesting makes an important limit visible. A lower average loss at a broad scope can conceal harm to an individual recipient. The proposed architecture in Section~\ref{sec:gap} therefore includes a held-out check at the receiving tenant. Versioning and access control govern whether an edit may be delivered and reversed; receiving-side evaluation tests whether it should be used there.

Several systems already evaluate transfers within one operator. ShareMem consolidates memories from one user for another and evaluates them in the receiving context \cite{hu2026sharemem}. XRepoSkill verifies a rule in at least two repositories \cite{guo2026xreposkill}. Evo2Team promotes routing skills between teams and confirms them at the target \cite{wang2026evo2team}. These are concrete instances of evidence being gathered beyond the source deployment.

Federated systems place the check elsewhere. EvolveNet merges a shared harness only when the merge fixes at least as many held-out items as it breaks, but that check occurs at the aggregator \cite{nie2026evolvenet}. FederatedSkill's server agent applies, adapts, or rejects each client's edit and records the decision \cite{yang2026federatedskill}. Their clients are partitions or agent instances under one operator, not independently governed customer organizations. They do not instantiate a receiving-organization gate.

The location of the evaluation matters, and its coverage still matters after it is correctly located. ShareMem, XRepoSkill, and Evo2Team check the receiving context; EvolveNet checks the shared merge; FederatedSkill records a server decision. Even in Evo2Team, nearly a fifth of confirmed transfers fail on graphs not covered by confirmation. A receiving-side check provides necessary evidence for adoption, but finite evaluation does not guarantee performance on all future tasks.

\subsection{Automatic, human, and unchecked promotion}\label{automatic-human-and-unchecked-promotion}

Research systems often promote by admitting a candidate to a bank or archive that later runs reuse. SkillOpt, DGM, ADAS, Voyager, and SAGE apply programmatic decisions within this shared environment \cite{yang2026skillopt, zhang2025darwin, hu2024adas, wang2023voyager, wang2025sage}. AlphaEvolve and its predecessor FunSearch score candidates before archive admission \cite{alphaevolve2025, romeraparedes2024funsearch}. AlphaEvolve has produced gains used within Google, but it is a research loop within one operator, rather than a product for governed sharing between organizations. That pool is as far as any of them travels, and none has access control, audited promotion, or a gate at a receiving organization.

Not every automatic admission has the same evidentiary meaning. NanoResearch's semantic merge, AutoManual's judged rewriting and consolidation, and ShareMem's judged consolidation are programmatic decisions, but none of them estimates a candidate's reduction in patch loss. The distinction anticipated by the feedback classes is therefore essential: an automatic promotion decision can exist where a per-edit improvement estimate does not.

Production systems more often retain a person at the promotion decision. Sierra routes generated insights through human-authored expert answers \cite{sierra2025os20}. In Devin, the same pull-request merge serves two roles: it supplies an observed outcome to local adaptation and records the reviewer's approval for the persistent repository \cite{cognition2025devinreview}. Spotify's optimized prompts and plans enter production after online A/B testing and a launch decision \cite{palumbo2026spotify}. CASCADE also combines human and agent approval for memory consolidation \cite{huang2025cascade}. In each, the person at the promotion gate stands in for the exact signal production lacks, which makes a program on the local gate with a person on the promotion gate the production-viable pairing rather than a compromise.

Letta's Context Repositories take a different path. Locally, background reflection writes memory edits and merges them back automatically; the only check on a local edit in the released evidence is an optional agent review before the edit is applied, which is the basis for its Auto local gate, and with that option off the system would sit in {[}None × None{]}. Shared-memory changes are then pushed with git lineage but without an acceptance check. The record explains what was shared, while leaving whether it should have been shared unresolved. In many other systems, promotion is absent altogether. AutoAgent, for example, revises the tool and peer descriptions of one agent without propagating those revisions to another deployment \cite{wang2026autoagent}. Both cases receive None at the promotion gate, but for different reasons: one shares without checking; the other does not share.

\subsection{What formats, registries, and release platforms provide}\label{what-formats-registries-and-release-platforms-provide}

Much of the infrastructure needed for sharing already exists independently of these learning loops. Claude Agent Skills, Cursor Rules, GitHub Copilot instructions, Windsurf, Continue.dev, Zed, and Replit use git-tracked markdown artifacts attached to workspaces, with a tool layer organized around MCP-style interfaces \cite{galster2026harnessconfig, barbaste2026harnessengineering}. This convergence makes artifacts easier to carry between runtimes. A study of repository-level loops nevertheless finds that the runtime state of the adaptation process remains outside version control \cite{lulla2026loopengineering}. The portable file does not necessarily carry the history that produced it.

Public repositories provide a shared scope with human admission. In a study of five skill repositories, every substantive change was committed under a named human account and merged by a person; only one of 254 edits deprecated a skill \cite{shen2026whomaintains}. MCP registries provide namespaces and version records, while control planes add scanning, access control, or quarantine \cite{agenticcommunity2026mcpgateway, microsoft2026apicentermcp, truefoundry2026mcpgateway}. Governance registries add lineage and rollback \cite{kang2026registry, quessadavial2026acm, qin2026governed}. EDDOps gates promotion on evaluation thresholds before a human sign-off, but none of these registries generates candidate artifacts from failures.

Braintrust, Vellum, and LangSmith Hub likewise provide immutable versions, evaluation thresholds, and rollback \cite{braintrust2026docs, vellum2026docs, langsmith2026hub}. Engineers author the candidates, and evaluations can block a regressing release. In the surveyed descriptions, session feedback does not trigger candidate generation or the release process. These platforms supply much of the machinery for controlled change without closing the failure-driven local loop.

\subsection{Accumulation and contamination}\label{accumulation-and-contamination}

As instructions accumulate, following them becomes harder and latency increases \cite{jaroslawicz2025ifscale}. Ratchet's finding that model-written skills need lifecycle hygiene before producing gains makes the consequence visible at the system level \cite{zhang2026ratchet}. Conflicting or obsolete artifacts also complicate attribution: an evaluation may detect failure without revealing whether the cause is the new candidate or an older artifact. Gated retirement, pruning, and expiry preserve the conditions under which a new edit can be meaningfully assessed.

Persistent memory creates another route to lasting error. PoisonedRAG demonstrates attacks on retrieved knowledge \cite{zou2024poisonedrag}, AgentPoison plants backdoors in long-term memory or knowledge bases \cite{chen2024agentpoison}, and memory control-flow attacks operate across major agent frameworks \cite{xu2026mcfa}. Tool outputs and connected servers can also insert instructions into the model's context \cite{greshake2023injection, debenedetti2024agentdojo}. In CVE-2025-54136, a previously approved MCP configuration could be changed without renewed approval \cite{checkpoint2025mcpoison}.

These failures motivate provenance, write gating, and reversible memory changes \cite{su2026chronomem, yu2026rollbackrepair}, together with restricted tool permissions and an instruction privilege hierarchy \cite{wallace2024hierarchy}. The tool binding itself must be subject to controlled revision. Checking only the initial registration leaves later changes outside the decision that authorized it.

Rollback also needs to account for derivation. If a contaminated skill has been used to create other skills, restoring its earlier version does not remove those descendants. VaG's limited recovery after such rollback \cite{shang2026vag} supports checking contamination before commitment and tracking consequences after it. A version history is a prerequisite for this work, but it does not perform the recovery by itself.

\subsection{When the evaluator changes}\label{sec:reflexive}

Consider a pitch-review assistant that consistently overrates decks claiming a large market without supporting numbers. The team revises its rubric from ``evaluate market size'' to ``require a numeric estimate and a source.'' The edit may improve reviews, but it also changes the standard used to evaluate subsequent behavior. If the same rubric judges future rubric revisions, the improvement process is modifying its own measuring instrument.

This is the reflexive-gate problem introduced with C3 feedback. The survey finds three scaffold systems reporting calibration of a judge against people: SkillForge, SkillChain, and SkillCoach \cite{skillforge2026, hu2026skillchain, zhu2026skillcoach}. SkillCoach also evaluates a judge after editing it: offline, it compares its initial and evolved rubrics against human-gold references on 50 paired instances from 10 held-out task families, and trajectory-filtering consistency rises from 82\% to 96\%, an audit its authors describe as judge-assisted rather than a new human annotation study \cite{zhu2026skillcoach}. No surveyed system reports calibration maintained across continuing rubric revisions and deployment drift. The missing result is therefore more specific than an absence of calibrated judges. It concerns keeping calibration while the criterion keeps changing.

Weight-level reinforcement learning has encountered a related problem in extending verifiable rewards to open-ended tasks. Some methods hold the judge fixed, using checklists, pairwise preferences, references, or rubrics \cite{gunjal2025rubrics, jia2025writingzero, shi2026references, jin2026rlaes}. Others update the reward, rubric, or judge alongside the policy \cite{yu2025rlpr, xu2026rubricarm, ding2026evorubrics, zhu2026score, li2026rubricem}. Among the co-evolving methods reviewed, only RLPR reports agreement with human labels, and its reward is a probability rather than a rubric. The comparison is tabulated in the audit notes (Supplementary Material S6); these weight-side methods are not included in the scaffold scores.

Even a fixed evaluator can become unreliable through repeated use. Optimizing a proxy beyond a point can reduce the underlying quality \cite{gao2023overoptimization}. Unequal exposure to evaluation data can create apparent performance gains \cite{singh2025leaderboard}. Evaluations of agent trajectories are also path-dependent, and deployment tasks drift while the suite remains fixed. Human criteria themselves can shift during grading \cite{shankar2024validators}. Consequently, a gate needs its own held-out checks, calibration where judgment is involved, and revision history.

The failure-mode hypothesis discussed in Section~\ref{sec:why} adds a conditional implication: if deployment failures concentrate in recurring modes, uniformly sampled tasks may underrepresent the modes that most need correction. Evaluation should then include those modes while preserving a held-out assessment. The requirement is broader than improving a benchmark score: score alone cannot tell a harness optimizer from trial and error \cite{ong2026harnesseval}, so the evaluation must also test the claimed link between failures and edits.

\subsection{Scope, coordination, and drift}\label{scope-coordination-and-drift}

Some failures arise from the structure of the deployment. A study of multi-agent systems identifies fourteen failure modes, prominently including role confusion and context lost between agents \cite{cemri2025mast}. Treating routing and role assignments as editable scaffold coordinates makes them subject to evaluation and rollback alongside instructions and skills.

Specialization creates a related boundary. A scaffold adapted to one deployment can degrade another because the tasks and preferred behavior differ. Receiving-side evaluation limits this risk at promotion; the evidence radius records where the improvement has been tested. This does not eliminate uncertainty outside the evaluated cases.

Finally, the scaffold can become less adaptable as old rules, polluted memories, and drifting tool versions accumulate. Long-context degradation \cite{liu2023lostmiddle} provides one related mechanism. Expiry, pruning, and rollback must remain available throughout the system's lifetime, especially when delayed feedback arrives too slowly to keep the artifacts current.

The feedback classes help organize these risks without making them exclusive to one class. Exact checks invite suite overfitting and cheap accumulation; observable outcomes depend on channels vulnerable to poisoning and injection; judged feedback is exposed to proxy optimization and moving criteria; delayed feedback makes drift difficult to correct promptly. Production systems provide individual controls, but the surface stays largely unmitigated because no surveyed system runs them together.

\section{What governed sharing would require}\label{sec:gap}

The evidence so far identifies a practical integration problem. Local optimizers can propose and test changes. Release platforms can version artifacts and reverse deployments. Registries can govern admission and access. The surveyed systems do not connect these capabilities into a process that learns in one organization and shares the resulting improvement with another under equivalent controls.

We audit that missing combination through four properties:

\begin{enumerate}
\def\labelenumi{(\alph{enumi})}
\tightlist
\item
  \textbf{An auto-gated local loop:} an algorithmic acceptance criterion tests a proposed artifact change.
\item
  \textbf{Cross-organization promotion:} artifacts can be promoted between independently governed organizations or customers.
\item
  \textbf{Versioned lineage with access control:} a promoted artifact carries its history and audit trail, with policies controlling who may access it.
\item
  \textbf{Rollback:} a harmful promotion can be reversed without redeploying the whole system.
\end{enumerate}

The terms \emph{cross-tenant} and \emph{cross-organization} refer to the same boundary here. Sharing among agents, users, or benchmark partitions within one operator does not establish property (b).

Table~\ref{tab:IX-1} compares the closest systems. FederatedSkill combines local adaptation with semantic skill exchange and an auditable server decision log \cite{yang2026federatedskill}. EvolveNet evaluates shared merges and can return to the previous shared harness \cite{nie2026evolvenet}. Both remain within one operator. Governance registries supply lineage and rollback without a local learning loop, and MCP control planes supply access control alone. Rollback exists inside one federated round and inside single deployments; no system rolls back a promotion that has crossed an organization boundary, because none makes such a promotion.

Receiving-side evaluation is an additional requirement on the promotion decision. It is kept separate from the four-property audit, which records loop, scope, and governance capabilities. A system could satisfy those capabilities while still making an unsupported decision about whether an artifact benefits its recipient.

An architecture that addresses both would contain five connected parts: per-tenant artifact pools with provenance; an aggregation or selection process that respects tenant isolation; held-out evaluation at the receiving tenant; versioned lineage and access control; and a defined reversal path for each promoted artifact. The recipient's check would reject a promotion that does not lower its own patch loss. VaG's result (Section~\ref{sec:findings}) suggests that the rollback envelope would also need to track an artifact's descendants.

Federated learning offers a useful comparison, but the representation being shared is different. FedAvg combines comparable numeric updates, and its privacy and deployment problems have been extensively studied \cite{mcmahan2017fedavg, mcmahan2018dpfedavg, kairouz2021federated}. Federated prompt tuning moves the learned object to a shared prompt \cite{guo2022promptfl}. The nearest scaffold systems instead select, revise, or merge symbolic edits, often through a language model. Averaging is an appropriate analogy only where the artifact updates have a mergeable representation.

The extent of automation should depend on the feedback. Exact checks provide the most direct setting for testing a transferred skill, although the recipient still needs relevant test cases. Observed outcomes require evaluation on the recipient's workload because the sender's outcome is not portable evidence of success. Where quality is judged, a human promotion gate is a reasonable design choice, supported by lineage and rollback. Delayed outcomes cannot support an immediate per-edit automatic local gate of the kind property (a) describes; those systems still benefit from provenance and reversibility around proposals and milestones.

Thus the four properties define a target for the settings that can support an automatic local gate. They should not be interpreted as a requirement to automate every decision in every domain. The common requirement is that the evidence attached to an edit remain meaningful where it is used, and that the system preserve the ability to inspect and reverse its adoption.

The lifecycle literature starts from a different constraint: skill pools can become too large or internally inconsistent to remain useful. This history helps explain why evaluation and proposal mechanisms are more developed than failure capture. Each research line inherits its loss from its benchmark and begins with available trajectories. Building a record of recurring failures was none of their starting problems. Attribution receives substantial attention, but usually within the substrate a particular line studies. The local loop has consequently developed from evaluation backward toward the evidence needed to choose a useful edit.

The convergence supports a shared decomposition of the system into weights and editable artifacts. GEPA, Meta-Harness, MOSS, RCL, PACE, and the harness-optimization papers all use it. A system that updates both, SIA, still treats them as separate levers \cite{hebbar2026sia}. The convergence does not establish that one architecture is optimal, and none of these lines documents the complete cross-organization process. It shows that different starting problems repeatedly lead to comparable mechanisms for proposing, testing, retaining, and reusing changes.

\subsection{Why specialization remains outside the weights}\label{sec:why}

A general model and a particular deployment face different requirements. The model must work across many settings. A deployment must follow its own conventions, honor its users' preferences, and avoid failures that may be rare globally but frequent locally. The scaffold provides a place to encode those requirements with a scope narrower than the model's entire user population.

Work on reinforcement learning from human feedback reports reduced output diversity and more homogeneous preferences \cite{kirk2024understanding, padmakumar2023diversity}. This helps motivate the distinction between broad model behavior and customer-specific requirements. Tiwari et al.~approach it from adaptation cost: in-context changes are cheap but capacity-bounded, while in-weight adaptation is more expressive and can introduce forgetting and loss of plasticity \cite{tiwari2026fastandslow, dohare2024loss}.

Per-customer adapters \cite{hu2021lora}, distilled models, and learned routing can absorb some local requirements. They also introduce separate training, evaluation, and serving lifecycles. Persistent artifacts offer the cheaper path: they are inspectable, reversible, scoped to one customer, and updatable daily.

Two earlier papers in this series offer a hypothesis for why targeted artifact changes may be effective. \emph{Beyond Exponential Decay} argues that long-output reliability depends on a sparse set of key decisions rather than a uniform error probability at every token \cite{arbuzov2025beyond}. Its evidence includes long-range dependence measured on one natural-text corpus, where fewer than a tenth of tokens depend on distant context, and the accuracy recovered through majority voting on reasoning benchmarks. Its argument is limited when the number of consequential decisions grows with the task, as in long-horizon agentic work.

\emph{The Architecture of Errors} considers a bounded deployment with recurring tasks, tools, and evaluator expectations \cite{arbuzov2026architecture}. It argues that failures there fall into a catalogue of modes whose size grows slowly with observed experience. Under its assumptions, the intervention budget grows polylogarithmically with sequence length and becomes constant once the catalogue saturates. Its negative result is equally relevant: a finite catalogue cannot cover an unbounded domain.

If these hypotheses generalize, a deployment may be improved through a manageable set of targeted interventions. Persistent rules, memories, skills, and tool changes provide an inspectable representation for those interventions. On that hypothesis the gated and scoped artifact layer is not a workaround for an inadequate model but the architecture the error structure calls for: a frontier model that generalizes, a local scaffold that specializes, and reliability that comes from governing the specialization. The survey does not test the hypotheses; its findings about acceptance gates, feedback, and promotion follow from the corpus independently of them.

\section{Open problems and conclusion}\label{sec:open}

The remaining problems become more specific when expressed in terms of the decisions a deployment must make.

\textbf{Attributing a failure to an editable cause.} An exact check can establish that an output failed without identifying the instruction, memory, skill, or tool binding responsible. No surveyed method solves this across all substrates. Slot attribution \cite{nguyen2026harnessevo}, intervention-based attribution \cite{chu2026agentgrad}, and contrastive multi-agent attribution \cite{zehle2026cantante} provide narrower starting points. Observed outcomes make the problem harder because their causes are more confounded.

\textbf{Establishing improvement at the recipient.} A transferred artifact must be evaluated against the receiving deployment's tasks and measure. Existing receiving-side checks show that this is feasible in selected settings, while Evo2Team's failures on unseen graphs show its coverage limits. Federated Agent Optimization proposes a receiving-client gate but does not implement it \cite{yang2026fao}. Connecting such checks to provenance, access control, and reversal remains an architectural problem.

\textbf{Maintaining calibration while the criterion changes.} For judged tasks, the open question is how to keep a judge aligned with people across continuing revisions of the rubric it applies. SkillCoach shows that an evolved rubric can be audited offline against human-gold references \cite{zhu2026skillcoach}; no surveyed scaffold system reports calibration maintained through repeated revisions in deployment. The neighboring reward literature also lacks a reported human-agreement result for a co-evolving rubric or judge, with RLPR's probability-based reward a distinct case. A useful solution must evaluate the moving criterion as well as the outputs it scores.

\textbf{Evaluating improvement with delayed outcomes.} When many edits occur before a meaningful result arrives, immediate per-edit acceptance is unavailable. Proxy milestones and proposal pruning may still be useful, but downstream gains alone do not establish successful attribution. Harness optimizers should therefore be assessed against their claims about why particular edits help, as well as their final scores \cite{ong2026harnesseval}.

\textbf{Connecting local learning to governed sharing.} No surveyed system combines automatic local acceptance, promotion across organizations, versioned lineage with access control, and rollback. The components exist in different systems. Their integration must preserve tenant isolation, evaluate the recipient, and account for artifacts derived from a change that is later withdrawn. Where feedback cannot support automatic acceptance, the design must retain the corresponding human decision or delayed evaluation.

The survey's central observation is that persistent changes outside the weights have become an important form of adaptation, while the evidence supporting those changes remains fragmented. Many systems can test a local candidate. Fewer can reliably explain which recurring failure it addresses, and the machinery for transferring the resulting improvement to another organization has not been assembled in the public systems examined here.

The frontier model generalizes. The local scaffold specializes. Reliability comes from governing that specialization: knowing what each change improved, where that evidence applies, and how the change can be reversed. That discipline must extend to the evaluations themselves when they become part of the adapting system.

\subsection{Setup}\label{setup}

Let the frontier model have fixed parameters \(\theta_M\) and let the scaffold be a structured object \(\theta_s \in \Theta_s = \Theta_1 \times \cdots \times \Theta_6\) over the six substrate coordinates of Section~\ref{sec:method}; \(\Theta_s\) is discrete, symbolic, and versioned. For a deployment \(D\), \(L_D(\theta_s) = \mathbb{E}_{x \sim D}[\ell(\pi(\theta_M, \theta_s, x))]\). A candidate edit \(z_t \sim Q_t(z \mid H_t, \theta_s^t)\) is drawn from a proposal process conditioned on the accumulated history \(H_t\) of failures, corrections, rejected outputs, evaluation regressions, and prior accepted edits. \(Q_t\) is not uniform: for a mode \(m\) that recurs with frequency \(f_m\) and carries per-occurrence loss \(s_m\), its expected contribution to the failure rate is \(f_m s_m\), so high-frequency or high-severity modes are proposed first. The finite directional difference is \(\Delta_z L_D(\theta_s) = L_D(\theta_s \oplus z) - L_D(\theta_s)\); the gate sees only a noisy estimate \(\widehat{\Delta}_z L_D\). The update is \[\theta_s^{t+1} = \theta_s^t \oplus z_t \text{ if } G_t(z_t) = 1, \quad \theta_s^{t+1} = \theta_s^t \text{ otherwise.}\]

\subsection{Descent inequality}\label{descent-inequality}

Write \(\mathcal{F}_t\) for the history up to step \(t\): the failures, corrections, edits, and gate decisions in \(H_t\) together with \(\theta_s^t\). Because the proposal \(Q_t\) depends on the whole history and not on \(\theta_s^t\) alone, every expectation and probability below conditions on \(\mathcal{F}_t\). Assume (A1) positive descent bias on accepted edits, \(\mathbb{E}[\widehat{\Delta}_{z_t} L_D \mid G_t = 1, \mathcal{F}_t] \le -\gamma_t - \tau_t\) for some \(\gamma_t > 0\), and (A2) bounded estimator bias on accepted edits, \(|\mathbb{E}[\Delta_{z_t} L_D - \widehat{\Delta}_{z_t} L_D \mid G_t = 1, \mathcal{F}_t]| \le \varepsilon_t\). With \(p_t = \Pr(G_t = 1 \mid \mathcal{F}_t)\), \[\mathbb{E}[L_D(\theta_s^{t+1}) \mid \mathcal{F}_t] \le L_D(\theta_s^t) - p_t(\gamma_t + \tau_t) + p_t\,\varepsilon_t.\] Per-step expected improvement is the gate's margin minus its estimator bias, weighted by acceptance probability. In the feedback-signal classes of Section~\ref{sec:signal}, \(\varepsilon_t\) is near zero for the check itself in C1, with the sampling error of a finite suite over the patch remaining, bounded by batching for an observable outcome (C2), equal to the judge's bias and bounded only by calibration for a judged signal (C3), and unavailable per edit for a delayed signal (C4).

\subsection{Convergence (informal)}\label{convergence-informal}

What follows is a conditional statement under strong assumptions, included to make gate stability precise; nothing in the survey depends on it. Add (A3) proposal coverage with acceptance: at every non-gate-stable scaffold, \(Q_t\) places probability at least \(q > 0\) on an admissible edit with \(\mathbb{E}[\Delta_z L_D] \le -\delta\), and the gate accepts such an edit with probability at least \(q' > 0\), so that \(p_t(\gamma_t + \tau_t) \ge q q' \delta\) there; (A4) effective compactness of the reachable orbit; and (A5) summable bias, \(\sum_t p_t \varepsilon_t < \infty\); and let \(0 \le L_D \le B\). (A3) is strong: it asks for a uniform lower bound on proposing and accepting an edit that lowers the loss by at least \(\delta\), which needs attribution far more reliable than success with non-zero probability per failure. The one-step inequality is then of the Robbins--Siegmund form, a non-negative process that decreases in expectation up to a summable perturbation \(p_t \varepsilon_t\), so \(L_D(\theta_s^t)\) converges almost surely and \(\sum_t p_t(\gamma_t + \tau_t) < \infty\) almost surely \cite{robbins1971convergence}. The finite sum carries the content: a bounded loss cannot pay for infinitely many accepted edits with a positive expected margin, so under (A3) the process visits non-gate-stable scaffolds only finitely often, and with (A4) the limit set of \(\{\theta_s^t\}\) is gate-stable: no admissible edit clears the gate with negative expected directional loss in the limit. This is convergence of the loss and stability of the gate decision, not convergence to an optimum; a globally suboptimal gate-stable scaffold is consistent with the result, because \(Q_t\) may never propose the improving edit or \(\widehat{\Delta}\) may be biased to reject it. A non-stationary deployment (\(D = D_t\)) falls outside this argument: tracking a moving optimum would need further assumptions on the rate of drift and of adaptation, which are not supplied here. Recency weighting, pruning, expiry, and rollback are the scaffold-level analogues of the machinery continual learning uses for that case.

\subsection{Correspondence}\label{correspondence}

Table~\ref{tab:A-1} pairs each optimization concept with its scaffold analogue. Credit assignment here is attribution, not backpropagation. Scaffold systems do not differentiate through instruction files. They trace an output error to an upstream coordinate, manually or with a judge or verifier. The one-step inequality needs only that accepted edits have positive expected descent; the convergence statement needs attribution reliable enough to supply the uniformly improving proposals that (A3) assumes, which is much stronger than the credit-assignment condition of Section~\ref{sec:loop}, success with non-zero probability per failure.

\subsection{Worked cases}\label{worked-cases}

\emph{Retrieval.} Failures recur because retrieved context omits the decisive clause. Attribution traces the error to the retrieval coordinate: chunking, query rewriting, metadata filter, embedding model, reranker, or context-packing rule. The candidate edit tightens chunk boundaries or adds a metadata constraint, and the gate checks that recall and answer accuracy improve on the patch evaluation without degrading adjacent cases. Signal class C1 or C2.

\emph{Pitch review.} The system repeatedly overrates decks that claim a large market without numbers, and the failure cluster points at an under-specified rubric coordinate. The edit changes ``evaluate market size'' into ``require a numeric estimate and a source; if absent, cap the score''; the gate runs the revised rubric against held-out decks with human scores. What the edit changed was the gate that will judge the next edit: the reflexive gate of Section~\ref{sec:signal}, class C3.

\emph{Tool use.} Calls fail because optional parameters are under-specified. The responsible coordinate may be the tool schema, the call policy, or the clarification rule. The edit adds required fields or a pre-call uncertainty check; the gate checks that tool-call failures fall without raising refusals or latency. Class C2.

\emph{Memory.} A stale customer preference is repeatedly retrieved and causes bad decisions. The responsible coordinate is a memory entry together with its provenance, priority, and expiry policy. The edit corrects, expires, or version-tags the entry; the gate checks that future behavior improves without erasing useful history. Class C2, with the correction itself observable only when a later outcome reveals it.
