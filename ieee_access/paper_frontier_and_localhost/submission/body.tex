\section{Introduction}\label{sec:intro}

The standard mental model of a system built on a large language model (LLM) is the model. Pre-training fixes the weights, fine-tuning nudges them, and deployment wraps a thin layer of prompts and tools around the result. Production in 2025 and 2026 has stopped behaving this way. Frontier weights change on a cycle of months; the systems built on them change daily, in instruction files checked into repositories, memories that persist across sessions, skills loaded on demand, registered tools, evaluation suites that block a merge, agent topologies, and pull-request gates on shared rule repositories. A growing share of the adaptation that makes a deployed system reliable now happens outside the weights, in a fast-changing local scaffold wrapped around a slow-changing frontier model.

Read one at a time, these artifacts look like unrelated engineering. A skill file is a procedure the model did not have. A repository rule is a local parameter for one project's conventions. A retrieval connector is memory access specific to one workflow. A tool registry provisions a capability the base model cannot reach. A pull-request review against a shared rule repository is a promotion gate, and an evaluation suite that blocks a merge is a validation check before promotion. Read together, they are one adaptation surface, the non-model part of what has been called a compound AI system \cite{zaharia2024compound}. The question this survey asks is what optimization discipline that surface needs. The answer we find is that the field has built an external adaptation layer for LLMs but not the optimizer that should govern it. Most deployments maintain the layer as patchwork: a failure happens, someone adds a rule, the pile grows, nobody knows which addition helped, and fixes leak into contexts that never validated them.

The disciplined alternative runs two loops, and only the first is routine. The local loop, which turns a recurring failure into a tested edit, closes under an automatic gate in most research systems and a growing number of production ones. The governed second loop, which would carry a validated edit across organizations under versioned lineage, access control, and rollback, appears in none of the 256 systems surveyed. What separates them is the signal the gate receives. The class of that signal fixes which loop a deployment can close: an exact check or an observed outcome can gate an edit automatically, a judgment only once the judge is calibrated against people, and a delayed reward not edit by edit at all.

This article makes five contributions.

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  The loop that turns patchwork into optimization, in plain language and as a gated update rule, with the five conditions under which it is an optimizer.
\item
  Four classes of feedback signal, from an exact check to a delayed reward, each fixing what the gate can be, which gate pairings are reachable, and which failure dominates.
\item
  A survey of 256 production and research systems, scored on six substrates against a published rubric, with the scores released.
\item
  A design space indexed by the gate on each loop, read structurally, and the convergence of five research families on the same loop as evidence that the architecture is real.
\item
  A four-property audit criterion for governed cross-organization scaffold optimization, which no surveyed system meets, and the failure surface its absence leaves open.
\end{enumerate}

Section~\ref{sec:why} argues that adaptation belongs in the scaffold, Section~\ref{sec:loop} states the loop, and Section~\ref{sec:signal} classifies its signal; Sections~\ref{sec:method} to \ref{sec:families} report the survey, and Sections~\ref{sec:gap} to \ref{sec:open} name the missing architecture, its failure surface, and the open problems.

The survey runs no experiments. Its evidence is the published behavior of 256 systems, scored on a released table.

\section{Why adaptation lives outside the weights}\label{sec:why}

\subsection{Breadth in the weights, depth in the scaffold}\label{breadth-in-the-weights-depth-in-the-scaffold}

Frontier training optimizes for breadth. The weights are tuned to generalize across millions of unseen deployments, and the objective smooths over exactly what one deployment cares about: local naming conventions, contradictory preferences between customers, rare workflow-specific failures. Reinforcement learning from human feedback reduces output diversity and homogenizes preferred style across users \cite{kirk2024understanding, padmakumar2023diversity}, and instruction-tuning data rewards patterns that generalize across the annotator pool, so the frontier model is trained to disfavor one customer's idiosyncrasies. Tiwari et al. \cite{tiwari2026fastandslow} reach the same place from the optimization side: in-context adaptation is cheap but capacity-bounded, in-weights adaptation is expressive but induces forgetting and loss of plasticity \cite{dohare2024loss}, so a two-timescale system, one that learns slowly in the weights and fast outside them, needs a cheap outer layer that absorbs what context can carry.

Production reliability is achieved in depth, inside one deployment, and it turns on what global training had to smooth away. Encoding every deployment in the weights is ruled out three times over: fine-tuning per customer multiplies the training, evaluation, and serving lifecycle by the number of deployments; weights ship quarterly at best, while the deployment wants daily updates; and overfitting the weights to one customer degrades the neighbors whose preferences contradict. Per-customer adapters \cite{hu2021lora}, distilled models, and learned routing could absorb some of the residual, the failures that remain after training, but in practice they are rare. Adaptation lands in the scaffold, the one substrate that is cheap, inspectable, reversible, scoped to one customer, and updatable daily.

\subsection{Why the scaffold is the right architecture: the two earlier results}\label{why-the-scaffold-is-the-right-architecture-the-two-earlier-results}

The case for learning outside the weights does not rest on cost alone; it is the conclusion of the two papers that precede this one in the series. \emph{Beyond Exponential Decay} \cite{arbuzov2025beyond} finds that long LLM outputs do not fail at the rate a uniform per-token error model predicts, because reliability hinges on a sparse set of key decisions, which make up under a tenth of tokens by the available long-context measurement. \emph{The Architecture of Errors} \cite{arbuzov2026architecture} finds that inside a bounded deployment those decisions fail in a finite catalogue of recurring modes whose size grows only slowly with the number of observed failures, so a small, targeted budget of interventions covers the residual.

Together they say where a deployment's errors are and that they are few enough to fix one at a time. This article asks where the fixes live, and the corpus answers: in persistent artifacts outside the weights, where a fix for a recurring, deployment-specific mode is cheap to make, inspect, and reverse. Gated and scoped, that layer is not a workaround for an inadequate model. It is the architecture the error structure calls for: a frontier model that generalizes, a local scaffold that specializes, and reliability that comes from governing the specialization.

Existing surveys of self-evolving agents, agent memory, context engineering, skills, and harness design catalogue mechanisms by what they edit and when. None classifies systems by loop closure, gate type, or signal class; two carry a governance axis, and none covers promotion across organizations. One of those two, Ding et al.'s survey of persistent-state agents, finds that literature concentrated on accumulating and retrieving state rather than on governing, recovering, or relinquishing it \cite{ding2026alwayson}.

A reader will expect the prompt-optimization lineage here: OPRO, EvoPrompt, Promptbreeder, DSPy, and TextGrad \cite{yang2023opro, guo2023evoprompt, fernando2023promptbreeder, khattab2023dspy, yuksekgonul2024textgrad}. That lineage optimizes a prompt or program once against a development set and is not a deployed loop. The evolving playbook of agentic context engineering \cite{ace2025agentic} persists its artifact but keeps it inside one context and never promotes it.

The closest precedents optimize the scaffold itself. Agent symbolic learning updates prompts, tools, and pipeline as symbolic parameters from textual feedback \cite{zhou2024symbolic}; in STOP, a scaffolding program recursively improves its own improvement code \cite{zelikman2023stop}; and a coding agent edits its own harness to raise its benchmark score \cite{robeyns2025sica}. Each runs one deployment's loop under a benchmark score. What changes here is that the edited artifact persists in a deployment and must clear a second gate before it earns any scope beyond that deployment (Supplementary Material S7).

\section{The loop: artifact-layer descent}\label{sec:loop}

\subsection{The loop in plain language}\label{the-loop-in-plain-language}

The disciplined version of scaffold maintenance is one loop, which we call artifact-layer descent, run again and again over the life of a deployment. It does not react to single failures. As the deployment runs, it logs what went wrong: failed outputs, user corrections, rejected answers, evaluation regressions, tool-call errors. Reflecting over that record, it clusters the failures into recurring modes and takes up the ones that matter most, ranked by how often each recurs and how badly it fails. For such a mode it locates the scaffold coordinate responsible, which may be a stale memory entry, an under-specified instruction, a missing tool argument, a brittle retrieval rule, or a misrouted agent edge. It then synthesizes one candidate edit to that coordinate. A deployment serves one \textbf{patch}: the slice of users, tasks, and conventions it handles. The failure rate on that patch's recurring tasks is the \textbf{patch loss}; the loop measures whether the edit lowers it, and a gate accepts or rejects the edit on that measurement. An accepted edit stays in the scaffold; one that a later check shows made things worse is pruned or rolled back.

Then comes the step most systems skip. The loop decides how far the edit should travel, promoting it to other deployments only as far as the evidence reaches; we call that limit the edit's \textbf{evidence radius}. The check that belongs at this step is \textbf{receiving-side evaluation}: a check run where the edit arrives, not where it was made. Fig.~\ref{fig:descent} draws the loop.

\subsection{Two loops, two knobs}\label{two-loops-two-knobs}

An engineer notices that a coding agent keeps misnaming a class in one repository. The fix is a one-line rule in that repository's instruction file. The edit is small and its scope is one project. The same engineer could promote the rule to a team-wide template, to the company's core instructions, or to a skill registry shared across companies. The edit did not change; the scope did. And the gate that should let it through gets stricter at each step, because the loss it is tested against is now an average over more deployments, and a fix that helps one repository can hurt another.

Loop 1 is the local fix: a recurring failure produces a candidate edit, the edit is tested, and an accepted edit changes one deployment's scaffold. Loop 2 is the separate decision of whether that fix should be shared. In optimizer terms, Loop 1 sets the analogue of a step size: how much one accepted edit changes the local scaffold. Loop 2 sets how many deployments the edit applies to, which leaves the step alone and changes the target: the average failure rate the scaffold is tuned to reduce.

The scopes nest, USER within PROJECT within STACK within TENANT within CORE, and each level's loss is the average failure rate over the deployments it contains (Fig.~\ref{fig:scope}). USER is one person's account or fork; PROJECT, one repository, workflow, or product workspace; STACK, a curated bundle of projects under one team; a \textbf{tenant} is one organization or customer; CORE is the scope every tenant shares. Promotion that reaches CORE crosses tenants, and we call it cross-tenant promotion; reaching TENANT applies an edit across one tenant's deployments. Governance is therefore not administrative overhead. It is the regularization that keeps a small fix from being aimed at the wrong target.

\subsection{When the loop is an optimizer}\label{when-the-loop-is-an-optimizer}

The loop is an optimization process, rather than a description of good practice, when five conditions hold:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  a measurable patch loss, such as a failure rate, a correction rate, or an evaluation score;
\item
  captured residuals, so that failures are logged rather than lost;
\item
  credit assignment, so that a failure can be traced, at least sometimes, to the scaffold coordinate that caused it;
\item
  a synthesized candidate edit to that coordinate; and
\item
  a gate that checks whether the edit lowers the loss before the edit is kept or promoted.
\end{enumerate}

The conditions presuppose frozen frontier weights, edits that persist as inspectable artifacts rather than transient prompts, and promotion that widens an artifact's scope under a gate rather than averaging comparable updates as weight-space federated learning does.

Write the patch loss of deployment \(D\) as \[L_D(\theta_s) = \mathbb{E}_{x \sim D}\!\left[\ell(\pi(\theta_M, \theta_s, x))\right],\] where \(\theta_M\) are the frontier weights, fixed during deployment, \(\theta_s\) is the scaffold, a structured object over the six substrate coordinates of Section~\ref{sec:method}, and \(\ell\) is an operational loss. A failure yields no analytic gradient. It yields a candidate edit \(z_t\), proposed by reflecting over the accumulated failure history, with modes taken in order of how often and how badly each fails. The gate accepts the edit when its noisy estimate of the change in loss clears a margin, \[G_t(z_t) = 1 \iff \widehat{\Delta}_{z_t} L_D(\theta_s^t) + \lambda\,\Omega(z_t) \le -\tau_t,\] where \(\Omega \ge 0\) penalizes the complexity of the edit and the breadth of its promotion, and \(\tau_t \ge 0\) is the required margin. An accepted edit is applied; a rejected one leaves the scaffold unchanged.

Production systems implement this inequality without writing it: an evaluation blocks a merge on regression, a reviewer rejects a vague rule, a governance system holds an artifact back until evidence accumulates. Under further assumptions on the gate's bias and the proposal process, the update satisfies a one-step descent inequality and converges, informally, to a gate-stable scaffold, where no admissible edit that would lower the loss clears the gate (Appendix~\ref{app:formal}). Where a condition fails, the picture is an analogy, and the survey marks which systems meet which conditions.

Each loop has a gate, and we name three kinds by who decides. A gate is \textbf{Auto} when a program makes the decision, whether by an evaluation score, a verifier, a reinforcement-learning threshold, a language-model judge \cite{zheng2023judge} with a quantified agreement rate, or, at the degenerate end, an unconditional rule that accepts every candidate. It is \textbf{Human} when a person decides. It is \textbf{None} when the loop is absent. We write a system's two gates as a pair, Loop 1 first: {[}Auto × Human{]} means an algorithmic local gate and a human promotion gate. These pairs index the design space of Section~\ref{sec:design}.

Condition 1 says the loss must be measurable. It does not say what measures it, and that turns out to be the question that sorts the corpus.

\subsection{Three stages of scaffold maintenance}\label{three-stages-of-scaffold-maintenance}

Three stages of scaffold maintenance recur across the corpus (Table~\ref{tab:II-1}). They differ in how candidate updates are produced, whether credit assignment is explicit, and whether promotion is bounded by evidence. A patchwork loop becomes Stage 3, artifact-layer descent, once the five conditions hold. \section{Where the signal comes from: four classes of feedback}\label{sec:signal}

Four scaffolds all run the loop of Section~\ref{sec:loop}. A coding agent changes one line in its repository rule file; the test suite runs and reports pass or fail within seconds. A scheduling assistant changes how it phrases a booking request; the appointment either appears on the calendar or it does not, and the system learns which an hour later. A marketing assistant changes the tone rule in its instructions; nobody can say whether the next draft is better, only whether a reviewer prefers it. A research assistant changes how it chooses which direction to pursue; whether the choice was good becomes visible months later, after many other edits have landed. All four produce a candidate edit \(z_t\). They differ in what the gate \(G_t\) can know about it.

The gate accepts an edit when its estimate \(\widehat{\Delta}_{z_t} L_D\) of the loss change clears a margin. Condition 1 asks for a measurable patch loss without saying what produces that estimate. We distinguish four classes of feedback signal by what produces it, and the class fixes three things at once: what the gate can be, which pairings of gate types a deployment can reach, and which failure dominates (Table~\ref{tab:IV-1}).

\textbf{C1, exact.} A deterministic checker returns pass or fail, or an exact score, immediately and repeatably: unit tests, compilers, type checkers, exact-match answer keys, proof checkers, schema validators. DGM accepts a self-modification only after it passes in a sandbox on coding benchmarks \cite{zhang2025darwin}; AlphaEvolve scores candidate programs with a cascade of exact evaluators \cite{alphaevolve2025}; SkillOpt gates a skill edit on a held-out exact-match split of a math benchmark \cite{yang2026skillopt}. The estimator bias \(\varepsilon_t\) is close to zero, the margin \(\tau_t\) can sit near zero, and accepting on a single evaluation is defensible, because repeating the check would return the same answer. Two things stay hard. A failing test localizes the output, not the scaffold coordinate that caused it, so credit assignment remains open; and a checker that is also the training target can be gamed. The dominant failures are test overfitting and scaffold bloat, because cheap acceptances accumulate.

\textbf{C2, observable outcome.} The environment or the user emits an outcome after an episode: a booked appointment, a closed ticket, a merged pull request, a tool call that returns without error, a retrieved document that contains the answer. The signal is real but one episode late, noisy, and confounded, since a user can accept a wrong answer and reject a right one. Gates of this class include Devin's merged pull requests \cite{cognition2025devinreview}, SAGE's task success on AppWorld \cite{wang2025sage}, SkillRL's success-rate threshold \cite{skillrl2026}, and PACE's failure signals from a deployed small model \cite{ling2026pace}. The gate becomes a reinforcement-learning threshold or a held-out task suite with a strictly positive margin, and the noise is absorbed by batching episodes or by requiring agreement across samples (Appendix~\ref{app:gates}). Credit assignment takes its hardest form: the outcome says \emph{that} the episode failed, not \emph{why}. Most production deployments live in this class, and its signal arrives through a channel an attacker can control, which is why poisoned memory and tool-output injection dominate.

\textbf{C3, judged.} There is no fact of the matter. An essay, a marketing page, a blog post, a design, a pitch deck, or a code review for style can be scored only by a judge: a human rater, a language-model judge, a rubric, or a comparison against references. SkillForge accepts a skill diff when its judge agrees with human engineers more than nine times in ten \cite{skillforge2026}; CASCADE consolidates memory under a human-and-agent gate \cite{huang2025cascade}; Anthropic's skills repository promotes a skill when a reviewer approves the pull request. Three things change. The estimator bias \(\varepsilon_t\) becomes the judge's bias, bounded only by calibration against people, so the bounded-bias assumption of Appendix~\ref{app:formal} has to be bought rather than assumed. Residuals are captured only when someone objects, so condition 2 depends on complaint channels rather than instrumentation.

The third change defines the class: the rubric that sets the loss is itself a scaffold coordinate. Suppose a pitch-review system keeps overrating decks that claim a large market without numbers. It traces the failure to its rubric and edits ``evaluate market size'' into ``require a numeric estimate and a source''. That edit changes the gate that will judge the next edit. We call this the \emph{reflexive gate}. Its dominant failure is Goodhart's law in the form measured for reward models, where optimizing a proxy past a point lowers the true score \cite{gao2023overoptimization}: once the judge is the target, the scaffold learns the judge. Nor is a human judge stable; evaluators' criteria drift as they grade more outputs \cite{shankar2024validators}.

\textbf{C4, delayed and sparse.} The outcome arrives after weeks or months, once per many edits, in a world that has moved on. Research programs, product strategy, and open-ended discovery are of this kind. The clearest instances are automated research pipelines such as the AI Scientist, which generates ideas, runs experiments, and writes the paper \cite{lu2024aiscientist}. NanoResearch merges candidate skills by semantic compatibility rather than by a measured loss change \cite{xu2026nanoresearch}; CORAL promotes findings into shared memory on a heartbeat rather than on an evaluation \cite{qu2026coral}; AlphaEvolve's MAP-Elites archive keeps candidates for their diversity, not their score \cite{alphaevolve2025}. With no per-edit estimate to gate on, \(G_t\) degenerates to proposal pruning plus proxy milestones, and the descent argument covers only the composition of pruning and whatever gate exists at the horizon (Appendix~\ref{app:gates}). Temporal credit assignment across many edits is open. The dominant failure is drift: the scaffold ages faster than the signal that would correct it. An optimizer in this class also cannot be told from random search by its outcomes alone; Ong et al. \cite{ong2026harnesseval} report the same indistinguishability for harness optimizers.

\textbf{The same classes on the weight side.} Reinforcement learning from verifiable rewards trains weights on exact signals and lies outside the scored corpus, but pushing it into writing and other open-ended tasks has forced the construction of judged gates, the only ones a C3 scaffold loop can borrow. One group holds the gate fixed while the policy learns, as an instance-specific checklist, a pairwise judge trained on writing principles, a reference-anchored judge, or a fixed rubric of binary items \cite{gunjal2025rubrics, jia2025writingzero, shi2026references, jin2026rlaes}. A second group lets the gate move with the policy, scoring by the policy's own probability of a fixed reference or updating the rubric or judge during training \cite{yu2025rlpr, xu2026rubricarm, ding2026evorubrics, zhu2026score, li2026rubricem}. Fixed versus co-evolved is exactly the reflexive-gate question. Of the co-evolving methods, only RLPR, whose reward is a probability rather than a rubric, reports agreement with human labels; none that co-evolves a rubric or judge does (Supplementary Material S6). On the scaffold side three systems report judge calibration \cite{skillforge2026, hu2026skillchain, zhu2026skillcoach}, and none calibrates a judge that is itself being edited.

\textbf{What the class predicts.} If the class fixes the gate, the occupancy of the design space is no accident, and three predictions follow, which Section~\ref{sec:design} checks. First, an {[}Auto × Auto{]} system whose gate estimates the loss change per edit should run on a C1 signal or a simulated C2 environment, where outcomes are cheap to observe, and one that works on a C4 signal should prune proposals rather than estimate. Second, {[}Auto × Human{]} should hold only C2 and C3 systems, because the human on Loop 2 substitutes for the exact signal that Loop 1 lacks. Third, no scaffold system should yet calibrate a judged gate under the reflexive condition.

\subsection{How the corpus was assembled}\label{how-the-corpus-was-assembled}

The corpus holds systems that either wrap a foundation model with at least one persistent artifact updated from deployment signal or are described in public as self-improving, scaffolded, or agentic. They were found in arXiv, vendor documentation, and public repositories between January 2023 and the October 2026 cutoff. The corpus was assembled in two passes, the second adding 126 systems up to the cutoff (Supplementary Material S2). Each was scored from its own method section or documentation, never from a secondary summary.

Two filters structure the corpus (Fig.~\ref{fig:corpus}). The patch-local discriminator admits a system to the core corpus when it scores at least 3 on at least one substrate, that is, when some artifact persists across scope or is updated from feedback. Systems that carry the labels but fail it form a contrast corpus, kept so that the boundary can be audited rather than asserted. A stricter composite two-loop audit then asks whether Loop 1 modifies a persisted artifact from session signal and whether Loop 2 has an explicit cross-context promotion mechanism with versioning or lineage; only systems that pass both are counted as occupying the design space, and systems that fail it appear in the matrix as contrast entries, marked as such. Of the 256 systems, 204 form the core corpus and 52 the contrast corpus; 14 research systems (13 of them rows of the released table, and SkillOpt) and 3 industry exemplars (Sierra Agent OS 2.0, Cognition Devin, and Letta's Context Repositories) pass the composite audit. The text also treats ten further systems at mechanism level: SkillOpt, GEPA, Meta-Harness, CORAL, PACE, MOSS, RCL, FederatedSkill, SkillClaw, and ChronoMem. They were classified from their papers after the first pass closed and are not rows of the released table, so the corpus counts above exclude them. SkillOpt is the only one of them in the design matrix.

Two kinds of system are excluded: those whose only update mechanism is weight-level fine-tuning or reinforcement learning, which are model-side and belong to the self-evolution literature this survey positions against; and those with no public evidence of deployment or release.

\subsection{Evidence and scoring discipline}\label{evidence-and-scoring-discipline}

Every classification rests on public evidence of uneven strength and on one rater. Each system carries one or more evidence tiers (T1 to T5 in the released table: peer-reviewed publication, arXiv preprint, production claim with metrics, open-source artifact, industry blog or interview). Peer-reviewed papers and open-source artifacts weigh most in cluster-level statements; a production claim counts when it names a benchmark or integration target; a blog post or interview counts only when a higher tier corroborates it; and production claims are never pooled with peer-reviewed evidence in a cluster-level statistic. Industry systems evaluated from vendor documentation rather than a paper are flagged wherever they appear. Scoring is single-rater: one author scored every system, used half-scores only when one criterion was clearly met and another partially, and rounded ambiguous cases down. The complete score table, with a one-line justification per row, is released so that every scored classification can be re-derived (Supplementary Material S1).

The counts of the findings move under two natural relaxations of the composite audit: counting any of versioning, lineage, or rollback as Loop-2 governance, or admitting as Loop 1 an update that persists only optimizer state. The qualitative findings survive both (Supplementary Material S2).

On the three substrates that hold adaptable content, only two systems reach the top mark, and both reach it inside one research environment. Instruction files persist across IDEs and agents (Claude Code, Cursor, AGENTS.md \cite{agentsmd2025}, Windsurf, Continue.dev) and appear in a fifth to a quarter of coding-agent projects \cite{robbes2026agenticmuch, galster2026harnessconfig}, yet in a controlled study they raise inference cost by about a fifth without raising task success \cite{gloaguen2026agentsmd}. Skills are the most active research substrate: SAGE and COSPLAY close both loops \cite{wang2025sage, wu2026cosplay}, and Loop 1 is routinely automated. SkillChain's judge-monotone edits pass a human reflection gate before they enter its skill bank: a two-stage local gate rather than a promotion loop \cite{hu2026skillchain}. Eleven skill systems treat retirement as a gated operation \cite{zhang2026librarydrift, wei2026skillsmith, pu2026skillops, wang2026assay}, and the public skill repositories are merged by hand \cite{shen2026whomaintains}. On orchestration, automated workflow search came first, in optimizable agent graphs \cite{zhuge2024gptswarm} and tree search over code-represented workflows \cite{zhang2024aflow}. Topologies evolve under evaluation \cite{cheng2026optimas, chu2026agentgrad, chen2026harnessforge}, TOCOMAS alone keeps a topology change only when it satisfies a structural invariant \cite{zhao2026tocomas}, and Evo2Team promotes routing skills across teams \cite{wang2026evo2team}.

Memory carries lineage without enforced correction. Production memory records its own history, in Letta's git-backed Context Repositories \cite{letta2026memfs}, Mem0's per-memory history \cite{mem02026history}, and Zep's bitemporal facts \cite{zep2026facts}. Research memory splits into write-gating and provenance on one side \cite{wang2026toki, xu2026ppmf, margalit2026governed} and verifier-gated failure loops on the other \cite{yu2026recuris, wang2026memguard, sun2026vermem}. Among the memory systems that gate writes or correct from failures, only Cuadros et al.~does both, which is why it alone reaches the top mark.

Tools and governance hold the machinery of a second loop without the first, which is how they reach the top mark with no inner loop (Section~\ref{sec:method}). MCP registries split into two kinds: catalogues such as the official registry, with namespaces and version records but no scanning and no private servers; and control planes, with scanning, access control, and quarantine \cite{agenticcommunity2026mcpgateway, microsoft2026apicentermcp, truefoundry2026mcpgateway}. None has evaluation-gated promotion. The governance registries bring lineage and rollback \cite{kang2026registry, quessadavial2026acm, qin2026governed}, and none of them has an inner loop.

No system matures all six substrates at once. Research systems learn fast and lack enterprise governance; production systems govern well and learn slowly; open standards solve artifact portability but not adaptation. This pattern is not a quirk of the corpus: it tracks which constraints each kind of system was built to satisfy.

\subsection{Five absences, read by signal class}\label{five-absences-read-by-signal-class}

Five pieces of the loop are missing or rare across the core corpus, and each sits in a particular feedback-signal class, or in all of them.

\begin{itemize}
\tightlist
\item
  \textbf{Failure-triggered memory is rare in production} (C2). Deployed memory systems record preferences and successful facts, not residuals. The one field report of stores written from dead-ends to prevent recurrence describes a single, self-reported deployment \cite{helwig2026memory}.
\item
  \textbf{Cross-customer promotion is nearly absent} (all classes). ShareMem, EvolveNet, XRepoSkill, and RASO promote across users, clients, or repositories inside one operator \cite{hu2026sharemem, nie2026evolvenet, guo2026xreposkill, chu2026raso}. No system promotes across customers or organizations with evidence.
\item
  \textbf{Memory is versioned, but correction is not enforced} (C2, C3). Git-backed and bitemporal memory ship in products. Five production backends still return facts that were revoked \cite{shen2026revoked}.
\item
  \textbf{Scaffold-level curriculum is unspecified in nearly every system} (C2). Which sessions inform the next edit is left to the order in which they arrive. Task-CoEvolve's variance-weighted task sampling and AutoSaddler's mini-batch failure signals are the exceptions \cite{miyai2026taskcoevolve, park2026autosaddler}.
\item
  \textbf{Receiving-side evaluation at promotion is rare} (C1, C2). ShareMem gives evaluation tasks to a different user, XRepoSkill verifies in at least two repositories, Evo2Team confirms at the target team, and VACE evaluates the candidate with the receiving model held fixed \cite{qi2026vace}. Even Evo2Team's confirmation lets nearly a fifth of its transfers fail on new graphs. EvolveNet has no such check, and the federated optimization framework that proposes a receiving-client gate has not implemented it \cite{yang2026fao}.
\end{itemize}

\emph{Research full-auto} systems show that the architecture works when both gates are algorithmic \cite{xu2026nanoresearch, wang2026autoagent, romeraparedes2024funsearch, alphaevolve2025, zhang2025darwin, hu2024adas, wang2023voyager}. \emph{Production hybrid} systems show that the production-viable pairing is an algorithmic gate on Loop 1 with a reviewer on Loop 2. \emph{Open standards and registries} converge across vendors on format and attachment. What the cluster lacks is adaptation: its registries govern admission and access but do not evaluate, and in the repositories that run autonomous loops, the runtime state of those loops sits outside version control \cite{lulla2026loopengineering}.

\section{The two-loop design space}\label{sec:design}

Indexing systems by the gate on each loop gives a 3×3 matrix, and its occupancy is lopsided (Fig.~\ref{fig:design}).

\begin{figure}[!t]
\centering
\includegraphics[width=0.9\columnwidth]{fig3_design_space_ieee}
\caption{The two-loop design space. Rows give the Loop 1 gate and columns the Loop 2 gate, so a cell [Loop 1 $\times$ Loop 2] such as [Auto $\times$ Human] pairs an algorithmic local gate with a human promotion gate. Two cells hold every system that passes the composite audit; a third holds the governance-first platforms, which have the gated second loop but no inner loop; the human-authored cells are occupied only by registries and curation workflows that have no session-signal loop. \label{fig:design}

{[}Auto × Auto{]} holds the research full-auto systems, machine-evaluated on both loops, and Letta's Context Repositories, which push shared memory across agents automatically, with git lineage and no evaluation gate. That push is unconditional, an algorithmic promotion with no evaluation threshold, so it sits in the Auto column of Loop 2; the composite audit admits it on lineage, not on a gate. {[}Auto × Human{]}, the production-viable cell, holds SkillForge, CASCADE, Sierra Agent OS 2.0, and Cognition Devin: Loop 1 fires at machine speed under an algorithmic criterion, and Loop 2 waits for a person. {[}None × Auto{]} holds the governance-first platforms, which gate promotion on evaluation but generate no candidates from failures; they pass only the Loop-2 half of the audit and enter the matrix as contrast entries (Supplementary Material S4).

Seven systems promote across users, clients, teams, or repositories without versioning or lineage. Six of them would enter the matrix if any of versioning, lineage, or rollback counted as Loop-2 governance, landing in {[}Auto × Auto{]} except Spotify's production loop, which lands in {[}Auto × Human{]}. The seventh, Future AGI's prompt lifecycle, rests on a vendor blog alone (tier T5), which the tier rule does not count, and is not admitted under any rule. None opens a new cell (Supplementary Material S2).

The other cells, where occupied at all, hold only systems that fail the composite audit. {[}Human × Auto{]} is empty: nobody authors candidates by hand and promotes them automatically, because automating the promotion of hand-written candidates buys little. {[}Human × Human{]} holds MCP registries and a community hub \cite{agenticcommunity2026mcpgateway, microsoft2026apicentermcp, truefoundry2026mcpgateway, jiang2026buildrix}, where a person registers an artifact and a person approves its use. The field study of five public skill repositories finds the same shape in practice, with every substantive edit human-merged and one deprecation in 254 edits \cite{shen2026whomaintains}. {[}Human × None{]} is the curation cell. An agent drafts, a person fact-checks, and the result is frozen \cite{nguyen2025verificagent}. These are single-loop by construction. The Loop 1 label in these cells, as in {[}None × Auto{]}, records who supplies each candidate: a person who registers an artifact for a specific use (Human) or an engineer who authors a version at a desk for no particular failure (None); the distinction is one of convention, and the supplementary matrix records it (Supplementary Material S4).

Read by signal class, the occupancy bears out the first two predictions of Section~\ref{sec:signal}. Every {[}Auto × Auto{]} system whose gate estimates the loss change per edit runs on an exact signal or a simulated outcome, and those that work on delayed signals prune proposals instead. {[}Auto × Human{]} holds only systems whose signal is an observed outcome or a judgment; no exact-signal system sits there. The third is the scaffold-side finding that section already records, that three systems report judge calibration and none calibrates a judge under edit, and no system in the matrix changes it.

Evidence is batched before acceptance, whereas earlier systems accepted an edit on one evaluation and absorbed estimator noise through the per-edit margin alone. A paired per-item test commits an edit only when its wins are reliable \cite{wang2026sagegate}; a merge is accepted only when it fixes at least as many held-out items as it breaks \cite{nie2026evolvenet}; three heterogeneous critics must all pass \cite{shang2026vag}; mini-batch failure signals feed validation-based selection \cite{park2026autosaddler}. Requiring agreement among independent proposals and averaging over them are different operations, and they reduce error at different rates (Appendix~\ref{app:gates}).

Multi-layer hierarchies remain rare. AlphaEvolve is the only system that combines a cascade evaluator with a diversity archive; the other systems that keep archives use them for lineage, not for staged evaluation.

\section{Convergent research families}\label{sec:families}

The loop is not a prescription the field has yet to adopt. Five research families, starting from different substrates and under different names, have arrived independently at parts of it, which we read as evidence that the loop is a shared attractor rather than one group's local optimum. The vendors' convergence on one artifact format and tool attachment (Section~\ref{sec:findings}) is independent evidence of the same kind. Convergence does not show that the design is optimal, only that the same constraints keep producing the same shape.

The clearest single instance is SkillOpt \cite{yang2026skillopt}. It treats one markdown skill document as the trainable external state of a frozen agent and edits it with explicit optimizer controls: rollout and reflection batches, add/delete/replace edits, a bounded textual learning rate with cosine decay, a held-out selection gate that accepts only a strictly better score, a rejected-edit buffer kept as negative feedback, and an epoch-wise slow update. Across six benchmarks, seven target models, and three harnesses it is best or tied on every cell its authors evaluate. It also reports transfer across models, harnesses, and benchmarks, which reads as an empirical measurement of evidence radius rather than as a governance mechanism. Its own follow-up, SkillOpt-Lite \cite{shen2026skilloptlite}, removes the buffer, the slow update, and the schedule, keeps the held-out gate and a consensus filter across rollouts, and matches or beats it. The gate and a consensus form of credit assignment are load-bearing; the rest are stabilizers.

The five families instantiate complementary parts of the loop (Table~\ref{tab:VIII-1}), and each was pushed into its part by the constraint it started from. Reflective evolution started from trajectories and proposes edits by reflecting over them, with a two-timescale argument for keeping those edits outside the weights \cite{agrawal2025gepa, tiwari2026fastandslow}. Reflective context learning, the most direct independent formalization, started from the observation that credit assignment, overfitting, forgetting, and high-variance signals persist whether the learned object lies in parameter space or context space. Its generalization penalty is the complexity term \(\Omega\) of the gate \cite{vassilyev2026rcl}. Harness optimization started from orchestration rather than skills and names credit assignment as its bottleneck; it is the largest family in the corpus, with roughly two hundred papers citing its founding entries and a dozen scored here \cite{lee2026metaharness, lin2026ahe, cai2026moss, zehle2026cantante, nguyen2026harnessevo, chen2026harnessforge, li2026growingharness}. The lifecycle family started from artifact pools that bloat and found hygiene to be a precondition for descent \cite{zhang2026ratchet}: the complexity penalty becomes a constraint frontier once platform limits bind \cite{tanjim2026mocha}, each outcome is attributed to skill, exploration, or environment before an update is admitted \cite{liu2026skillsvote}, and eleven systems make retirement a gated operation \cite{zhang2026librarydrift, wei2026skillsmith, pu2026skillops, wang2026assay}. The transfer family started from how far an edit travels and instruments Loop 2, from measuring evidence radius one task at a time to federating skill patches across clients or deployments \cite{shalev2026ict, li2026combee, qu2026coral, ling2026pace, yang2026federatedskill, nie2026evolvenet}.

\item

AHE, CANTANTE, Meta-Harness, HARNESSEVO, SkillsVote, and the harness-optimizer evaluation of Ong et al. \cite{ong2026harnesseval} all name the same step as what separates descent from trial-and-error: attributing a system-level failure to one scaffold coordinate. \item

\item
  No surveyed system combines automated local adaptation with governed cross-organization promotion. FederatedSkill and EvolveNet each narrow the gap on different properties, and neither meets the four that Section~\ref{sec:gap} sets out.

\section{The missing architecture: governed cross-tenant scaffold optimization}\label{sec:gap}

Four properties define an architecture that no surveyed system instantiates:

\tightlist

  \tightlist

    \textbf{auto-gated Loop 1}: the commit criterion is an algorithmic threshold;
  \end{enumerate}
\item

  \def\labelenumi{(\alph{enumi})}
  \setcounter{enumi}{1}
  \tightlist
  \item
    \textbf{cross-organization promotion}: Loop 2 routes artifacts between organizations (we use \emph{cross-tenant} and \emph{cross-organizational} interchangeably);

\item
  \begin{enumerate}

Row by row, the partition is plain: the systems with a local loop carry the automatic gate and part of the promotion, the registries carry lineage and rollback without an inner loop, and the control planes carry access control alone. No system rolls back a promotion that has crossed an organization boundary, because none makes such a promotion (Supplementary Material S4).

In machine-learning terms, what is missing is a cross-tenant aggregator with an automated evaluation gate at the scaffold layer. It would carry five parts: per-tenant artifact pools, each tagged with provenance; an aggregation step across tenants that respects tenant isolation; a held-out evaluation at the receiving tenant that blocks a promotion whenever it does not lower that tenant's patch loss; versioned lineage with access control; and a rollback envelope on every promoted artifact. The federated-learning analogy \cite{mcmahan2017fedavg, mcmahan2018dpfedavg, kairouz2021federated} is useful only in the limit where artifacts are mergeable update representations; federated prompt tuning, in which participants learn a shared prompt rather than shared weights \cite{guo2022promptfl}, is the weight-side precedent closest to that limit. In surveyed practice Loop 2 is selection and merge, and the nearest systems aggregate program edits with a language model, not by averaging.

Whether the architecture \emph{should} be built depends on the feedback-signal class, not on the application domain (Section~\ref{sec:signal}). Where the signal is exact, automatically gated cross-tenant promotion of a test-validated skill would be low-risk, and receiving-side evaluation is cheap to add. Where it is an observable outcome, the sending side's outcome does not transfer, so promotion should be automated only behind receiving-side evaluation, the check that would catch a scaffold over-fitted to one deployment before it propagates to another. Even that check is necessary rather than sufficient: some of Evo2Team's transfers still fail on new graphs after target-side confirmation \cite{wang2026evo2team}. Where it is judged, a human gate on Loop 2 is a design feature, and governance means lineage and rollback around a human decision. Where it is delayed, property (a) cannot be met, and what remains is lineage and rollback without an automatic gate. Safety-critical domains, the usual case for human gates, are judged or delayed domains with high stakes. Naming the four properties turns a vague gap into an audit criterion that any future system can be measured against; naming the signal class says which of the four a given deployment should expect to meet.

Bloat is a signal-quality problem as well as a latency problem. Ratchet reports that LLM-authored skills gain nothing over a no-skill baseline while human-curated ones show a double-digit gain, and it attributes the gap to lifecycle management \cite{zhang2026ratchet}. In the vocabulary of Section~\ref{sec:loop}, that means residual capture and mode discovery cannot work on a messy artifact pool.

Evaluation fragility compounds because the evaluation suite is itself a patch-local artifact rather than a fixed instrument. It is optimized against: once a metric becomes the target, it is gamed. It is read non-independently, because the gate scores path-dependent agent trajectories whose readings do not compose like ordinary test-set statistics. It goes stale, because the suite adapts on the same cadence as the scaffold it gates. And because failures concentrate in a finite catalogue of recurring modes, a suite that samples tasks at random under-weights exactly the families that drive the failure rate. The response in the table follows from those four facts: held-out and scoped, mode-weighted, re-read, and checked against attribution rather than only against score.

The failure surface is real, quantified in the cited measurements, and largely unmitigated in production. Every row names a piece of the optimizer that current systems do not yet have.

\section{Open problems and conclusion}\label{sec:open}

Five open problems follow from the survey, one per feedback-signal class and one for the architecture.

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Exact signals: credit assignment from a failing check to a scaffold coordinate.} A test tells the loop that an output failed, not which instruction, skill, or tool binding caused it. Slot attribution \cite{nguyen2026harnessevo}, intervention-based attribution \cite{chu2026agentgrad}, and contrastive multi-agent attribution \cite{zehle2026cantante} each solve one substrate's case; a general method is the bottleneck the harness-optimization family names.
\item
  \textbf{Observable outcomes: receiving-side evaluation before promotion.} The outcome that justified an edit on the sending side does not transfer, and even where a promoted edit is checked on arrival, some transfers still fail (Section~\ref{sec:findings}). The gate a federated scaffold optimizer needs, a held-out test at the receiving tenant, has been proposed but not built \cite{yang2026fao}.
\item
  \textbf{Judged signals: calibrating a gate that is itself being edited.} When the rubric is a scaffold coordinate, each accepted edit to it moves the instrument that judges the next edit. No method that co-evolves a rubric or judge reports agreement with human judgment, and no scaffold system calibrates a judge under edit (Section~\ref{sec:signal}); the nearest measurement is on the human side, where evaluators' criteria drift as they grade \cite{shankar2024validators}.
\item
  \textbf{Delayed signals: telling descent from search.} Where the outcome arrives after many edits, an optimizer's gains cannot be distinguished from trial-and-error by outcome alone \cite{ong2026harnesseval}; evaluating harness optimizers against their attribution claims rather than their scores is the open method.
\item
  \textbf{The governed cross-organization loop.} The architecture of Section~\ref{sec:gap}, properties (a) through (d), remains unbuilt; the receiving-side gate of problem 2 is the piece that would make cross-organization promotion safe in the two classes where it should be automatic.
\end{enumerate}

The field has built an external adaptation layer for language models but not the optimizer that should govern it. The two earlier papers of this series showed why the layer belongs where it is: errors concentrate in a few key decisions; inside a bounded deployment, those decisions fail in a small and recurring catalogue of modes; and such a catalogue can be fixed one mode at a time in a persistent, inspectable, reversible artifact outside the weights. Gated and scoped, that artifact layer is the architecture the error structure calls for, not a workaround.

The survey shows how far practice has come toward that optimizer, and the distance is uneven. The local loop closes automatically in most research systems and in a growing number of production ones; evidence is batched before acceptance; retirement and expiry are first-class operations; production memory carries lineage. What has not moved is the second loop. No surveyed system promotes a validated edit across an organization boundary under an automatic gate with lineage, access control, and rollback. The signal-class analysis says this is not one gap but four, each with its own reachable answer. The frontier model generalizes. The local scaffold specializes. Reliability comes from governing that specialization. Because the instruments that judge each edit are themselves part of the moving scaffold, the same evidence-radius and lifecycle discipline the optimizer needs must extend to the gates that judge it.

\subsection{Setup}\label{setup}

Let the frontier model have fixed parameters \(\theta_M\) and let the scaffold be a structured object \(\theta_s \in \Theta_s = \Theta_1 \times \cdots \times \Theta_6\) over the six substrate coordinates of Section~\ref{sec:method}; \(\Theta_s\) is discrete, symbolic, and versioned. For a deployment \(D\), \(L_D(\theta_s) = \mathbb{E}_{x \sim D}[\ell(\pi(\theta_M, \theta_s, x))]\). A candidate edit \(z_t \sim Q_t(z \mid H_t, \theta_s^t)\) is drawn from a proposal process conditioned on the accumulated history \(H_t\) of failures, corrections, rejected outputs, evaluation regressions, and prior accepted edits. \(Q_t\) is not uniform: for a mode \(m\) that recurs with frequency \(f_m\) and carries per-occurrence loss \(s_m\), its expected contribution to the failure rate is \(f_m s_m\), so high-frequency or high-severity modes are proposed first. The finite directional difference is \(\Delta_z L_D(\theta_s) = L_D(\theta_s \oplus z) - L_D(\theta_s)\); the gate sees only a noisy estimate \(\widehat{\Delta}_z L_D\). The update is \[\theta_s^{t+1} = \theta_s^t \oplus z_t \text{ if } G_t(z_t) = 1, \quad \theta_s^{t+1} = \theta_s^t \text{ otherwise.}\]

\subsection{Descent inequality}\label{descent-inequality}

Assume (A1) positive descent bias on accepted edits, \(\mathbb{E}[\widehat{\Delta}_{z_t} L_D \mid G_t = 1, \theta_s^t] \le -\gamma_t - \tau_t\) for some \(\gamma_t > 0\), and (A2) bounded estimator bias on accepted edits, \(|\mathbb{E}[\Delta_{z_t} L_D - \widehat{\Delta}_{z_t} L_D \mid G_t = 1, \theta_s^t]| \le \varepsilon_t\). With \(p_t = \Pr(G_t = 1 \mid \theta_s^t)\), \[\mathbb{E}[L_D(\theta_s^{t+1}) \mid \theta_s^t] \le L_D(\theta_s^t) - p_t(\gamma_t + \tau_t) + p_t\,\varepsilon_t.\] Per-step expected improvement is the gate's margin minus its estimator bias, weighted by acceptance probability. In the feedback-signal classes of Section~\ref{sec:signal}, \(\varepsilon_t\) is near zero for an exact check (C1), bounded by batching for an observable outcome (C2), equal to the judge's bias and bounded only by calibration for a judged signal (C3), and unavailable per edit for a delayed signal (C4).

\subsection{Convergence (informal)}\label{convergence-informal}

Add (A3) proposal coverage, that at every non-gate-stable scaffold \(Q_t\) places probability at least \(q > 0\) on an admissible edit with \(\mathbb{E}[\Delta_z L_D] \le -\delta\); (A4) effective compactness of the reachable orbit; and (A5) persistent acceptance with summable bias, \(\sum_t p_t(\gamma_t + \tau_t) = \infty\) and \(\sum_t p_t \varepsilon_t < \infty\); and let \(0 \le L_D \le B\). Then \(L_D(\theta_s^t)\) is a non-negative supermartingale up to summable noise, it converges almost surely, and the limit set of \(\{\theta_s^t\}\) is gate-stable: no admissible edit clears the gate with negative expected directional loss in the limit. This is convergence of the loss and stability of the gate decision, not convergence to an optimum; a globally suboptimal gate-stable scaffold is consistent with the result, because \(Q_t\) may never propose the improving edit or \(\widehat{\Delta}\) may be biased to reject it. In a non-stationary deployment (\(D = D_t\)) the same mechanism tracks a moving optimum rather than converging once, which is why recency weighting, pruning, expiry, and rollback are the scaffold-level analogues of continual-learning machinery rather than optional hygiene.

\subsection{Correspondence}\label{correspondence}

Table~\ref{tab:A-1} pairs each optimization concept with its scaffold analogue. Credit assignment here is attribution, not backpropagation. Scaffold systems do not differentiate through instruction files; they trace an output error to an upstream coordinate, manually or with a judge or verifier. The descent argument needs only that this attribution succeeds with non-zero probability per failure, which is the credit-assignment condition of Section~\ref{sec:loop}.

\subsection{Worked cases}\label{worked-cases}

\emph{Retrieval.} Failures recur because retrieved context omits the decisive clause. Attribution traces the error to the retrieval coordinate: chunking, query rewriting, metadata filter, embedding model, reranker, or context-packing rule. The candidate edit tightens chunk boundaries or adds a metadata constraint, and the gate checks that recall and answer accuracy improve on the patch evaluation without degrading adjacent cases. Signal class C1 or C2.

\emph{Pitch review.} The system repeatedly overrates decks that claim a large market without numbers. The failure cluster points at an under-specified rubric coordinate. The edit changes ``evaluate market size'' into ``require a numeric estimate and a source; if absent, cap the score''. The gate runs the revised rubric against held-out decks with human scores. The edit changed the gate that will judge the next edit: the reflexive gate of Section~\ref{sec:signal}, class C3.

\emph{Tool use.} Calls fail because optional parameters are under-specified. The responsible coordinate may be the tool schema, the call policy, or the clarification rule. The edit adds required fields or a pre-call uncertainty check; the gate checks that tool-call failures fall without raising refusals or latency. Class C2.

\emph{Memory.} A stale customer preference is repeatedly retrieved and causes bad decisions. The responsible coordinate is a memory entry together with its provenance, priority, and expiry policy. The edit corrects, expires, or version-tags the entry; the gate checks that future behavior improves without erasing useful history. Class C2, with the correction itself observable only when a later outcome reveals it.
