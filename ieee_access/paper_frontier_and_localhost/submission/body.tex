\section{Introduction}\label{sec:intro}

The standard mental model of a system built on a large language model (LLM) is the model. Pre-training fixes the weights, fine-tuning nudges them, and deployment wraps a thin layer of prompts and tools around the result. Production in 2025 and 2026 has stopped behaving this way. Frontier weights change on a cycle of months. The systems built on them change daily, in instruction files checked into repositories, in memories that persist across sessions, in skills loaded on demand, in registered tools, in evaluation suites that block a merge, in agent topologies, and in pull-request gates on shared rule repositories. A growing share of the adaptation that makes a deployed system reliable now happens outside the weights, in a fast-changing local scaffold wrapped around a slow-changing frontier model.

Read one at a time, these artifacts look like unrelated engineering. A skill file is a procedure the model did not have. A repository rule is a local parameter for one project's conventions. A retrieval connector is memory access specific to one patch of work. A tool registry provisions a capability the base model cannot reach. A pull-request review against a shared rule repository is a promotion gate. An evaluation suite that blocks a merge is a validation check before promotion. Read together, they are one adaptation surface, and the question this survey asks is what optimization discipline that surface needs. The answer we find is that the field has built an external adaptation layer for LLMs but not the optimizer that should govern it. Most deployments maintain the layer as patchwork: a failure happens, someone adds a rule, the pile grows, nobody knows which addition helped, and fixes leak into contexts that never validated them.

This article makes five contributions.

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  It states the loop that turns patchwork into optimization in plain language, then as a gated update rule, with the five conditions under which the rule is a mechanism rather than a metaphor (Section~\ref{sec:loop}).
\item
  It introduces a classification of the feedback signal available to that loop, from an exact check to a delayed and sparse reward, and shows that the class fixes what the gate can be, which design-space cells are reachable, and which failure dominates (Section~\ref{sec:signal}).
\item
  It surveys 256 production and research systems from January 2023 to October 2026, scores each on six substrates with a published rubric and a released score table, and reports where maturity is uneven (Sections~\ref{sec:method} and \ref{sec:findings}).
\item
  It places every system that closes both loops in a design space indexed by gate type and reads the empty cells structurally (Section~\ref{sec:design}), and it reads the convergence of five research families on the same loop as evidence that the architecture is real rather than one group's local optimum (Section~\ref{sec:families}).
\item
  It names, as a four-property audit criterion, the architecture no surveyed system instantiates, namely governed cross-tenant scaffold optimization with versioned lineage, access control, and rollback, and it maps the failure surface that the gap leaves open (Sections~\ref{sec:gap} and \ref{sec:failure}).
\end{enumerate}

The survey runs no experiments. Its evidence is the published behavior of the systems it scores, the released score table, and the audit of every absolute claim against the October-2026 literature (Supplementary Material).

\section{Why adaptation lives outside the weights}\label{sec:why}

\subsection{Breadth in the weights, depth in the scaffold}\label{breadth-in-the-weights-depth-in-the-scaffold}

Frontier training optimizes for breadth. The weights are tuned to generalize across millions of unseen deployments, and the training objective smooths over exactly the things one deployment cares about: local naming conventions, contradictory tenant preferences, rare workflow-specific failures. Reinforcement learning from human feedback reduces output diversity and homogenizes preferred style across users \cite{kirk2024understanding, padmakumar2023diversity}, and instruction-tuning data rewards patterns that generalize across the annotator pool rather than patterns specific to any one deployment. The frontier model is therefore trained in a way that systematically disfavors encoding one tenant's idiosyncrasies as preferred behavior. Tiwari et al. \cite{tiwari2026fastandslow} reach the same place from the optimization side: in-context adaptation is cheap and rapid but capacity-bounded, while in-weights adaptation is expressive but induces forgetting and loss of plasticity, so a two-timescale system needs a cheap outer layer that absorbs what context can carry.

Production reliability, by contrast, is achieved in depth. Inside one deployment, reliability is determined by what global training had to smooth away. Encoding every deployment in the weights is ruled out three times over: per-tenant fine-tuning multiplies the training, evaluation, and serving lifecycle by the number of deployments; weights ship quarterly at best while the deployment wants daily updates; and overfitting the weights to one tenant degrades adjacent tenants whose preferences contradict. Per-tenant adapters, distilled models, and learned routing each absorb some residual in principle. In practice the scaffold dominates, because it is the one substrate that is cheap, inspectable, reversible, tenant-scoped, and updatable on a daily cadence at once.

\subsection{Why the scaffold is the right architecture, not a workaround: three papers}\label{why-the-scaffold-is-the-right-architecture-not-a-workaround-three-papers}

The case that learning belongs outside the weights does not rest on cost alone. It is the conclusion of three papers, of which this is the third. The first, \emph{Beyond Exponential Decay} \cite{arbuzov2025beyond}, asks why long LLM outputs do not fail at the rate a uniform per-token error model predicts, and finds that reliability hinges on a sparse set of key decisions, under a tenth of tokens by the available long-context measurement, rather than on uniform per-token accuracy. The second, \emph{The Architecture of Errors} \cite{arbuzov2026architecture}, asks what those key-decision failures look like inside a bounded deployment and finds that they cluster into a finite catalogue of recurring modes whose size grows only slowly with the number of observed failures, so a small, targeted budget of interventions covers the residual. Together they say where a deployment's errors are and that they are few enough to fix one at a time. This article asks where the fixes live. The answer the corpus gives is: in persistent artifacts outside the weights, which is where a small catalogue of recurring, tenant-specific modes can be addressed cheaply, inspected, and reversed. Once the loop that edits those artifacts is gated and scoped, the arrangement is not a patch on an inadequate model. It is the architecture that the error structure of the first two papers calls for: a frontier model that generalizes, a local scaffold that specializes, and reliability that comes from governing the specialization.

\subsection{Three stages of scaffold maintenance}\label{three-stages-of-scaffold-maintenance}

\section{The loop: artifact-layer descent}\label{sec:loop}

\subsection{The loop in plain language}\label{the-loop-in-plain-language}

The disciplined version of scaffold maintenance is one loop, run again and again over the life of a deployment. It does not react to single failures. As the deployment runs, it logs what went wrong: failed outputs, user corrections, rejected answers, evaluation regressions, tool-call errors. Reflecting over that record, it clusters the failures into recurring modes and takes up the ones that matter most, where a mode earns attention in proportion to how often it recurs and how badly it fails. For such a mode it locates the single scaffold coordinate responsible, which may be a stale memory entry, an under-specified instruction, a missing tool argument, a brittle retrieval rule, or a misrouted agent edge, and it synthesizes one candidate edit to that coordinate. It measures whether the edit lowers the deployment's failure rate on its own recurring tasks, which we call the patch loss, and a gate accepts or rejects the edit on that measurement. An accepted edit stays in the scaffold; one that a later check shows made things worse is pruned or rolled back. Then comes the step most systems skip: the loop decides how far the edit should travel, promoting it to other deployments only as far as the evidence reaches. That limit is the edit's evidence radius. Fig.~\ref{fig:descent} draws the loop.

\subsection{Two loops, two knobs}\label{two-loops-two-knobs}

Consider a concrete case. An engineer notices that a coding agent keeps misnaming a class in one repository. The fix is a one-line rule in that repository's instruction file. The edit is small and its scope is one project. The same engineer could promote the rule to a team-wide template, to the company's core instructions, or to a cross-tenant skill registry. The edit did not change; the scope did. And the gate that should let it through gets stricter at each step, because the loss it is tested against is now an average over more deployments, and a fix that helps one repository can hurt another.

Loop 1 is the local fix: a recurring failure produces a candidate edit, the edit is tested, and an accepted edit changes one deployment's scaffold. Loop 2 is the separate decision of whether that fix should be shared. The two loops turn different knobs. Loop 1 sets how much one accepted edit changes the local scaffold, the analogue of a step size. Loop 2 sets how many deployments the edit applies to, which does not change the step but changes the target: which average failure rate the scaffold is being tuned to reduce. The scopes nest, USER within PROJECT within STACK within TENANT within CORE, and each level has its own loss, the average failure rate over the deployments it contains (Fig.~\ref{fig:scope}). ``Cross-tenant promotion'' means reaching the TENANT or CORE level. This is why governance is not administrative overhead. It is the regularization that keeps a small fix from being aimed at the wrong target.

\subsection{When the loop is an optimizer}\label{when-the-loop-is-an-optimizer}

The loop is an optimization process, rather than a description of good practice, when five conditions hold:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  a measurable patch loss, such as a failure rate, a correction rate, or an evaluation score;
\item
  captured residuals, so that failures are logged rather than lost;
\item
  credit assignment, so that a failure can be traced, at least sometimes, to the scaffold coordinate that caused it;
\item
  a synthesized candidate edit to that coordinate; and
\item
  a gate that checks whether the edit lowers the loss before the edit is kept or promoted.
\end{enumerate}

Write the patch loss of deployment \(D\) as \[L_D(\theta_s) = \mathbb{E}_{x \sim D}\!\left[\ell(\pi(\theta_M, \theta_s, x))\right],\] where \(\theta_M\) are the frontier weights, fixed during deployment, \(\theta_s\) is the scaffold, a structured object over the six substrate coordinates of Section~\ref{sec:method}, and \(\ell\) is an operational loss. A failure yields no analytic gradient. It yields a candidate edit \(z_t\), proposed by reflection over the accumulated failure history in order of how often and how badly each mode fails. The gate accepts the edit when its noisy estimate of the change in loss clears a margin, \[G_t(z_t) = 1 \iff \widehat{\Delta}_{z_t} L_D(\theta_s^t) + \lambda\,\Omega(z_t) \le -\tau_t,\] where \(\Omega \ge 0\) penalizes the complexity of the edit and the breadth of its promotion and \(\tau_t \ge 0\) is the required margin. An accepted edit is applied; a rejected one leaves the scaffold unchanged. Production systems implement this inequality without writing it: an evaluation blocks a merge on regression, a reviewer rejects a vague rule, a governance system holds a local artifact back until evidence accumulates.

Each loop has a gate, and we name three kinds. A gate is \textbf{Auto} when the decision is an algorithmic criterion: an evaluation score, a verifier, a reinforcement-learning threshold, or a language-model judge with a quantified agreement rate. It is \textbf{Human} when the decision is reviewer judgment. It is \textbf{None} when the loop is absent. These labels index the design space of Section~\ref{sec:design}.

\subsection{Assumptions}\label{assumptions}

The descent reading holds when (i) the frontier weights stay frozen while the scaffold adapts; (ii) each edit is a persistent, inspectable artifact rather than a transient prompt; (iii) the deployment exposes a loss that can be measured; (iv) the proposal process can, at least sometimes, trace a failure to the responsible coordinate; (v) the gate is a noisy estimator of whether an edit helps, not an oracle; and (vi) promotion widens an artifact's scope under a gate rather than averaging comparable updates the way weight-space federated learning does. Under these assumptions Appendix~\ref{app:formal} states a one-step descent inequality and an informal convergence proposition to a gate-stable scaffold. Where a condition fails, the same picture should be read as an analogy, and the survey marks which systems meet which conditions. Condition (iii) says the loss must be measurable; Section~\ref{sec:signal} asks what measures it.

\section{Where the signal comes from: four classes of feedback}\label{sec:signal}

Consider four scaffolds that all run the loop of Section~\ref{sec:loop}. A coding agent changes one line in its repository rule file; the test suite runs and reports pass or fail within seconds. A scheduling assistant changes how it phrases a booking request; the appointment either appears on the calendar or it does not, and the system learns which an hour later. A marketing assistant changes the tone rule in its instructions; nobody can say whether the next draft is better, only whether a reviewer prefers it. A research assistant changes how it chooses which direction to pursue; whether the choice was good becomes visible months later, after many other edits have landed. All four produce a candidate edit \(z_t\). They differ in what the gate \(G_t\) can know about it.

That difference is the subject of this section. The gate of Section~\ref{sec:loop} accepts an edit when its estimate \(\widehat{\Delta}_{z_t} L_D\) of the loss change clears a margin. Condition (iii) of the loop says a patch loss must be measurable; it does not say how. We distinguish four classes of feedback signal by what produces the estimate, and the class turns out to fix three things at once: what the gate can be, which cells of the two-loop design space of Section~\ref{sec:design} a deployment can reach, and which entry of the failure surface of Section~\ref{sec:failure} dominates. Table~\ref{tab:IV-1} summarizes; the paragraphs that follow give one example per class from the corpus.

\textbf{C1, exact.} A deterministic checker returns pass or fail, or an exact score, immediately and repeatably. Unit tests, compilers, type checkers, exact-match answer keys, proof checkers, and schema validators are all of this kind. DGM accepts a self-modification only after it passes in a sandbox on coding benchmarks \cite{zhang2025darwin}; AlphaEvolve scores candidate programs with a cascade of exact evaluators \cite{alphaevolve2025}; SkillOpt gates a skill edit on a held-out exact-match split of a math benchmark \cite{yang2026skillopt}. In the formalism the estimator bias \(\varepsilon_t\) is close to zero, the margin \(\tau_t\) can be set near zero, and accepting on a single evaluation (\(n = 1\), Section~\ref{sec:design}) is defensible because repeating the check would return the same answer. Two of the five conditions still need work even here: a failing test localizes the output, not the scaffold coordinate that caused it, so credit assignment remains open; and a checker that is also the training target can be gamed. The dominant failures are test overfitting and scaffold bloat, because cheap acceptances accumulate.

\textbf{C2, observable outcome.} The environment or the user emits an outcome after an episode: the appointment is booked, the ticket is closed, the pull request is merged, the tool call returns without error, the retrieved document contains the answer. The signal is real but it arrives one episode late, it is noisy, and it is confounded, because a user can accept a wrong answer and reject a right one. Devin's merged pull requests \cite{cognition2025devinreview}, SAGE's task success on AppWorld \cite{wang2025sage}, SkillRL's success-rate threshold \cite{skillrl2026}, and PACE's failure signals from a deployed small model \cite{ling2026pace} are gates of this class. The gate becomes a reinforcement-learning threshold or a held-out task suite; \(\tau_t\) must be strictly positive, and the noise is absorbed by batching episodes or by requiring agreement across samples (Appendix~\ref{app:gates}) rather than by the per-edit check alone. The bottleneck is credit assignment in its hardest form: the outcome says \emph{that} the episode failed, not \emph{why}, so tracing it to one coordinate is an inference the loop must make on its own. This is the class most production deployments live in, and it is also the class in which the signal arrives through the same channel an attacker controls, which is why poisoned memory and tool-output injection (Section~\ref{sec:failure}) dominate here.

\textbf{C3, judged.} There is no fact of the matter. An essay, a marketing page, a blog post, a design, a pitch deck, or a code review for style can be scored only by a judge: a human rater, a language-model judge, a rubric, or a comparison against references. SkillForge accepts a skill diff when its judge agrees with human engineers more than nine times in ten \cite{skillforge2026}; CASCADE consolidates memory under a human-and-agent gate \cite{huang2025cascade}; Anthropic's skills repository promotes a skill when a reviewer approves the pull request. Three things change. The estimator bias \(\varepsilon_t\) is now the judge's bias, which is bounded only by calibration against people, so assumption (A2) of Appendix~\ref{app:formal} has to be bought rather than assumed. Residuals are captured only when someone objects, so condition (ii) depends on complaint channels rather than on instrumentation. And the rubric that defines the loss is itself a scaffold coordinate: when the pitch-review worked case of Appendix~\ref{app:formal} edits the rubric from ``evaluate market size'' to ``require a numeric estimate and a source'', the edit changes the gate that will judge the next edit. We call this the \emph{reflexive gate}. Its dominant failure is Goodhart's law in the form the eval-fragility entry of Section~\ref{sec:failure} describes: once the judge is the target, the scaffold learns the judge.

\textbf{C4, delayed and sparse.} The outcome exists but arrives after weeks or months, once per many edits, in a world that has moved on. Research programs, product strategy, and open-ended discovery are of this kind. NanoResearch merges candidate skills by semantic compatibility rather than by a measured loss change \cite{xu2026nanoresearch}; CORAL promotes findings into shared memory on a heartbeat rather than on an evaluation \cite{qu2026coral}; AlphaEvolve's MAP-Elites archive keeps candidates for their diversity, not their score \cite{alphaevolve2025}. There is no per-edit estimate to gate on, so \(G_t\) degenerates to proposal pruning plus proxy milestones, and the descent argument applies only to the composition of pruning and whatever gate exists at the horizon (Appendix~\ref{app:gates}). Temporal credit assignment across many edits is open. The dominant failure is drift: the scaffold ages faster than the signal that would correct it, and an optimizer in this class cannot be distinguished from random search by its outcomes alone, which is the indistinguishability \cite{ong2026harnesseval} report for harness optimizers.

\textbf{The same four classes on the weight side.} Reinforcement learning from verifiable rewards trains model weights on C1 signals: a math answer matches or it does not. The effort to push that recipe into writing and other open-ended tasks has had to build C3 gates, and the constructions are worth naming because they are the only gates a C3 scaffold loop can borrow. Rubrics as Rewards scores a response against an instance-specific checklist generated before training and judged by a fixed model \cite{gunjal2025rubrics}; Writing-Zero trains a pairwise generative judge on writing principles and then holds it fixed while the policy learns \cite{jia2025writingzero}; reference-anchored judging improves agreement with human labels where no verifier exists \cite{shi2026references}; an essay scorer trained against a fixed rubric of binary items reaches the agreement of a single human rater \cite{jin2026rlaes}. A second group lets the gate move with the policy: RLPR scores a response by the policy's own probability of a fixed reference, so the scorer co-evolves by construction \cite{yu2025rlpr}; Rubric-ARM alternates updates of a rubric generator and a judge before freezing them for policy training \cite{xu2026rubricarm}; EvoRubrics, SCORE, and RubricEM update rubrics adversarially or from a rubric buffer within training \cite{ding2026evorubrics, zhu2026score, li2026rubricem}. Of fourteen such papers we checked, eight hold the rubric or judge fixed during policy optimization and five co-evolve it; five report agreement with human judgment, and none of the co-evolving ones does (Supplementary Material S6). These are weight-space methods and this survey does not score them. The point is narrower: whether the rubric is fixed or co-evolved with the policy is exactly the reflexive-gate question, and a co-evolved rubric is a gate under descent whose calibration nobody has yet measured. On the scaffold side, three systems report judge calibration, SkillForge's agreement with engineers, SkillChain's judge-human kappa, and SkillCoach's trajectory-filter consistency against human gold \cite{skillforge2026, hu2026skillchain, zhu2026skillcoach}, and none of them calibrates a judge that is itself being edited.

\textbf{What the class does to the design space.} Read the matrix of Section~\ref{sec:design} by class and its empty cells stop being accidents. Every system in the {[}Auto × Auto{]} cell whose gate is a per-edit estimator runs on a C1 signal or on a simulated C2 environment where the outcome is cheap to observe; the {[}Auto × Auto{]} systems that work in C4 domains gate by pruning, not by an estimate (Claim IV-1). The production-viable cell {[}Auto × Human{]} is populated only by C2 and C3 systems: the human on Loop 2 substitutes for the exact signal that Loop 1 lacks (Claim IV-2). And the weight-side rubric work supplies gate constructions that no scaffold-side system has yet calibrated under the reflexive condition (Claim IV-3). The claims audit in the Supplementary Material checks all three against the rescored corpus; the first two hold without exception and the third is sharpened by the three scaffold-side calibration figures named above.

The class also settles a question Section~\ref{sec:gap} leaves open: whether the missing cross-tenant architecture \emph{should} be filled. The answer is by class rather than by domain. In C1 an automatically gated cross-tenant promotion of a test-validated code skill is low-risk, and the held-out receiving-side evaluation that Section~\ref{sec:findings} finds absent is cheap to add. In C2 the corner should be filled only with that receiving-side evaluation, because the sending side's outcome signal does not transfer. In C3 a human gate on Loop 2 is a design feature, not a defect, and governance means lineage and rollback around a human decision. In C4 property (a) of Section~\ref{sec:gap} cannot be met, so what remains of governance is lineage and rollback without an automatic gate. Safety-critical domains, which Section~\ref{sec:gap} names as the case for human gates, are C3 or C4 domains with high stakes; the class, not the domain, is what carries the argument.

\subsection{How the corpus was assembled}\label{how-the-corpus-was-assembled}

The corpus was built in two passes with one rubric. The first pass (January 2023 to May 2026) searched arXiv, vendor documentation, and public repositories for systems described as self-improving, scaffolded, or agentic, and kept those that wrap a foundation model with at least one persistent artifact updated from deployment signal. The second pass (June to October 2026) ran query families for self-evolving skills and skill lifecycle, harness and context optimization, agent memory governance, prompt-as-code and evaluation-gated promotion, federated or multi-tenant skill sharing, and multi-agent topology evolution, and followed citations of the systems the first pass had identified as closest to the gap of Section~\ref{sec:gap}. Every system admitted in either pass was scored from its own method section or documentation, never from a secondary summary. The first pass scored 130 systems; the second added 126, for 256 unique systems and 269 substrate-level rows. The cutoff is October 2026.

Two filters structure the corpus (Fig.~\ref{fig:corpus}). The patch-local discriminator admits a system to the core corpus when it scores at least 3 on at least one substrate, that is, when some artifact persists across scope or is updated from feedback; systems that carry the labels but fail it are kept as a contrast corpus so the boundary is auditable rather than rhetorical. A stricter composite two-loop audit then asks whether Loop 1 modifies a persisted artifact from session signal and Loop 2 has an explicit cross-context promotion mechanism with versioning or lineage; only systems passing both enter the design space of Section~\ref{sec:design}. Of the 256 systems, 204 pass the discriminator and 52 form the contrast corpus; 14 research systems and 3 industry exemplars pass the composite audit, and 7 systems added in 2026 promote across contexts without versioning or lineage and enter only under the relaxations below. Industry systems evaluated from vendor documentation rather than from a paper are flagged as such wherever they appear.

Exclusions. Systems whose only update mechanism is weight-level fine-tuning or reinforcement learning are model-side and belong to the self-evolution literature this survey positions against; systems with no public evidence of deployment or release are excluded.

\subsection{Evidence and scoring discipline}\label{evidence-and-scoring-discipline}

Each system carries one or more evidence tiers: T1 peer-reviewed publication; T2 arXiv preprint; T3 production claim with metrics; T4 open-source artifact; T5 industry blog or interview. T1 and T4 carry the most weight in cluster-level statements; T3 is admissible when the claim is concrete (a named benchmark or integration target); T5 only when corroborated by a higher tier. Production claims are never pooled with peer-reviewed evidence when a cluster-level statistic is computed. Scoring is single-rater: one author scored every system, half-scores were used only when one criterion was clearly met and another partially, and ambiguous cases were rounded down. The complete score table, with a one-line justification per row, is released as Supplementary Material S2 so that every classification can be re-derived. The counts reported in Section~\ref{sec:findings} move under two natural relaxations of the composite criterion, counting any of versioning, lineage, or rollback as Loop-2 governance, or admitting updates that persist only optimizer state as Loop 1; the qualitative findings survive both (Supplementary Material S2).

Three things stand out. First, the field has converged on the six substrates: every mature system has a recognizable instance of each, under different names. Second, no system matures all six at once. Research systems learn fast and lack enterprise governance; production systems govern well and learn slowly; open standards solve artifact portability but not adaptation. Third, the 2026 sweep added 126 systems, 92 of its 102 core systems close Loop 1 under an automatic gate, and not one of them reaches the top mark on any substrate: the local loop has become routine and the governed second loop has not moved. The maturity gradient is not a quirk of the corpus. It tracks which constraints each kind of system was built to satisfy.

\subsection{Five absences, read by signal class}\label{five-absences-read-by-signal-class}

Five absences fall out of the discriminator, and each sits in a particular feedback-signal class (Section~\ref{sec:signal}).

\begin{itemize}
\tightlist
\item
  \textbf{Failure-triggered memory is rare in production} (C2). Deployed memory systems record preferences and successful facts, not residuals; the one field report of anti-recurrence stores written from dead-ends is a single self-reported deployment \cite{helwig2026memory}.
\item
  \textbf{Cross-customer promotion is nearly absent} (all classes). ShareMem, EvolveNet, XRepoSkill, and RASO promote across users, clients, or repositories inside one operator \cite{hu2026sharemem, nie2026evolvenet, guo2026xreposkill, chu2026raso}; no system promotes across customers or organizations with evidence.
\item
  \textbf{Versioned memory has arrived; enforced correction has not} (C2, C3). Git-backed and bitemporal memory ship in products, and five backends still return revoked facts \cite{shen2026revoked}.
\item
  \textbf{Scaffold-level curriculum is unspecified in nearly every system} (C2). Which sessions inform the next edit is left to the order they arrive in; Task-CoEvolve's variance-weighted task sampling and AutoSaddler's mini-batch failure signals are the exceptions \cite{miyai2026taskcoevolve, park2026autosaddler}.
\item
  \textbf{Receiving-side evaluation at promotion is rare} (C1, C2). It now exists in ShareMem (evaluation tasks belong to a different user), XRepoSkill (verification in at least two repositories), Evo2Team (target-side confirmation, which still misses four of twenty-two transfers on new graphs), and VACE (candidate evaluated with the receiving model held fixed) \cite{qi2026vace}; EvolveNet has none, and the federated optimization framework that proposes a receiving-client gate has not implemented it \cite{yang2026fao}. This is the missing piece that would catch a scaffold over-fitting one deployment before it propagates to another.
\end{itemize}

\emph{Production hybrid} systems pair an algorithmic Loop-1 gate with a reviewer on Loop 2. \emph{Governance-first} systems automate Loop 2 alone. The prompts-as-code platforms and the 2026 registries \cite{kang2026registry, quessadavial2026acm, qin2026governed} have immutable versions, evaluation thresholds, and rollback; they lack a Loop 1 because candidates are authored by engineers rather than triggered by session feedback. Convergence across vendors is independent evidence, complementary to the research-side convergence of Section~\ref{sec:families}, that the architecture is real rather than any one vendor's local optimum. Two measured facts temper the optimism: context files raise cost without raising success in a controlled study \cite{gloaguen2026agentsmd}, and the runtime state of autonomous loops sits outside version control in the repositories that run them \cite{lulla2026loopengineering}.

\section{The two-loop design space}\label{sec:design}

Systems that pass the composite audit sit in a 3×3 matrix indexed by the gate type on each loop (Fig.~\ref{fig:design}); Supplementary Material S4 lists the named membership of every cell.

\begin{figure}[!t]
\centering
\includegraphics[width=0.9\columnwidth]{fig3_design_space_ieee}
\caption{The two-loop design space. Three cells hold every system that passes the composite audit; the human-authored cells are occupied only by registries and curation workflows that have no session-signal loop. No populated system adds governed cross-tenant promotion.}

Three cells hold every system that passes the composite audit. {[}Auto × Auto{]} holds the research full-auto systems, twelve from the May corpus with machine-evaluated criteria on both loops. {[}Auto × Human{]} is the production-viable cell: Loop 1 fires at machine speed under an algorithmic criterion and Loop 2 waits for a person. {[}None × Auto{]} holds the governance-first platforms with evaluation-gated promotion and no failure-triggered candidate generation. The 2026 sweep did not add a cell: its seven cross-context promoters land in {[}Auto × Auto{]} without versioning or lineage and so enter the strict audit only under relaxation, and its one production loop lands in {[}Auto × Human{]}.

The other cells are not empty, but they are occupied only by systems that fail the composite audit, and the pattern of occupancy is itself a finding. {[}Human × Auto{]} remains empty: nobody authors candidates by hand and promotes them automatically, because manual authorship offers automated promotion little leverage. {[}Human × Human{]} is occupied by MCP registries and a community hub \cite{agenticcommunity2026mcpgateway, microsoft2026apicentermcp, truefoundry2026mcpgateway, jiang2026buildrix}, where a person registers an artifact and a person approves its use; the field study of five public skill repositories finds the same shape in practice, with every substantive edit human-merged and one deprecation in 254 edits \cite{shen2026whomaintains}. {[}Human × None{]} is the curation cell: an agent drafts, a person fact-checks, and the result is frozen \cite{nguyen2025verificagent}. These are single-loop by construction. Read by signal class, the occupancy is what Section~\ref{sec:signal} predicts: automatic gates on both loops appear only where the signal is exact or cheaply observable, and the human cells fill where it is not.

Two cross-cutting findings sharpen the picture. \emph{Evidence is now batched before acceptance.} In the May corpus nearly every automatic gate fired on a single evaluation, absorbing estimator noise through the per-edit margin alone. By mid-2026 statistical acceptance is common: a paired per-item test that commits an edit only when its wins are reliable \cite{wang2026sagegate}, a merge accepted only when the held-out items it fixes outnumber those it breaks \cite{nie2026evolvenet}, three heterogeneous critics that must all pass \cite{shang2026vag}, and mini-batch failure signals with validation-based selection \cite{park2026autosaddler}. The agreement form of batching, where \(k\) independent proposals must converge, shrinks the false-accept rate as \(p^k\) rather than shrinking variance as \(1/k\), and the two should not be conflated (Appendix~\ref{app:gates}). \emph{Multi-layer hierarchies remain rare.} AlphaEvolve is still the only system that combines a cascade evaluator with a diversity archive; the 2026 systems that keep archives use them for lineage, not for staged evaluation.

\section{Convergent research families}\label{sec:families}

The loop of Section~\ref{sec:loop} is not a prescription the field has yet to adopt. It is the limit that research is converging on from several directions at once, under different names and for different substrates, and the convergence is evidence that the architecture is real rather than one group's local optimum.

The clearest single instance is SkillOpt \cite{yang2026skillopt}. It treats one markdown skill document as the trainable external state of a frozen agent and edits it with explicit optimizer controls: rollout and reflection batches, add/delete/replace edits, a bounded textual learning rate with cosine decay, a held-out selection gate that accepts only a strictly better score, a rejected-edit buffer kept as negative feedback, and an epoch-wise slow update. Across six benchmarks, seven target models, and three harnesses it is best or tied on every cell its authors evaluate, and it reports transfer across models, harnesses, and benchmarks that reads as an empirical measurement of evidence radius rather than as a governance mechanism. Its own follow-up, SkillOpt-Lite \cite{shen2026skilloptlite}, removes the buffer, the slow update, and the schedule, keeps the held-out gate and a consensus filter across rollouts, and matches or beats it: the gate and a consensus form of credit assignment are load-bearing, and the rest are stabilizers.

Five research families instantiate complementary parts of the loop (Table~\ref{tab:VIII-1}). The \emph{reflective-evolution} family proposes edits by reflecting over trajectories \cite{agrawal2025gepa} and supplies the two-timescale motivation \cite{tiwari2026fastandslow}. \emph{Reflective context learning} \cite{vassilyev2026rcl} is the most direct independent formalization: it observes that credit assignment, overfitting, forgetting, and high-variance signals persist whether the learned object lies in parameter space or context space, and its generalization penalty is the complexity term \(\Omega\) of Section~\ref{sec:loop}. The \emph{harness-optimization} family targets orchestration rather than skills (Meta-Harness~\cite{lee2026metaharness}; AHE~\cite{lin2026ahe}; MOSS~\cite{cai2026moss}; CANTANTE~\cite{zehle2026cantante}; HARNESSEVO~\cite{nguyen2026harnessevo}) and names credit assignment as the bottleneck; by October 2026 it is the largest family in the corpus, with roughly two hundred papers citing its founding entries and a dozen scored here. The \emph{lifecycle} family shows that hygiene is a precondition for descent: LLM-authored skills add nothing over no skill until retirement and a bounded active set are in place \cite{zhang2026ratchet}, and eleven 2026 systems make retirement a gated operation \cite{zhang2026librarydrift, wei2026skillsmith, pu2026skillops, wang2026assay}. The \emph{transfer} family instruments Loop 2: measuring evidence radius one task at a time \cite{shalev2026ict}, pooling evidence across parallel agents \cite{li2026combee}, promoting through shared memory on a heartbeat \cite{qu2026coral}, consolidating across a deployment's own episodes \cite{ling2026pace}, and, in 2026, federating skill patches across clients with an auditable decision log \cite{yang2026federatedskill} or across deployments with a held-out merge gate and round rollback \cite{nie2026evolvenet}.

\item

\item
  Credit assignment is the central engineering bottleneck. AHE, CANTANTE, Meta-Harness, HARNESSEVO, SkillsVote, and the harness-optimizer evaluation of Ong et al. \cite{ong2026harnesseval} all identify attributing a system-level failure to one scaffold coordinate as what separates descent from trial-and-error, and it remains unsolved in the general multi-substrate case.
\item
  Lifecycle hygiene is a precondition for descent, not an alternative to it. A dirty artifact pool starves the gate of signal; the 2026 retirement mechanisms are the field's answer, and the one negative result cuts deeper: once a contaminated skill has descendants, rolling it back recovers little, so gating must happen before commit \cite{shang2026vag}.
\item
  No surveyed system combines automated local adaptation with governed cross-organization promotion. FederatedSkill and EvolveNet narrow the gap on different properties and close it on none.
\end{enumerate}

\section{The missing architecture: governed cross-tenant scaffold optimization}\label{sec:gap}

Four properties define an architecture that no surveyed system instantiates:

\begin{itemize}
\tightlist
\item
  \begin{enumerate}
  \def\labelenumi{(\alph{enumi})}
  \tightlist
  \item
    \textbf{auto-gated Loop 1}: the commit criterion is an algorithmic threshold;
  \end{enumerate}
\item
  \begin{enumerate}
  \def\labelenumi{(\alph{enumi})}
  \setcounter{enumi}{1}
  \tightlist
  \item
    \textbf{cross-organization promotion}: Loop 2 routes artifacts between organizations (we use \emph{cross-tenant} and \emph{cross-organizational} interchangeably);
  \end{enumerate}
\item
  \begin{enumerate}
  \def\labelenumi{(\alph{enumi})}
  \setcounter{enumi}{2}
  \tightlist
  \item
    \textbf{versioned lineage with access control}: promoted artifacts carry versions, audit trails, and role-based access policies;
  \end{enumerate}
\item
  \begin{enumerate}
  \def\labelenumi{(\alph{enumi})}
  \setcounter{enumi}{3}
  \tightlist
  \item
    \textbf{rollback}: a bad promotion can be reverted without redeploy.
  \end{enumerate}
\end{itemize}

The closest approaches partition the requirements, and the October-2026 sweep sharpened the partition without closing it. FederatedSkill has (a), the strongest partial (b) in the corpus (privacy-preserving aggregation of skill patches across heterogeneous clients that sit under one operator), and partial (c) through an auditable per-modification decision log \cite{yang2026federatedskill}. EvolveNet has (a), a held-out merge gate at the aggregator, and (d) in the form of a rollback to the previous shared harness after a failed round, with no lineage, no access control, and clients that are benchmark partitions rather than organizations \cite{nie2026evolvenet}. SkillForge has (a) and (b) within one enterprise with partial (c) \cite{skillforge2026}. The governance-first registries have (c) without access control and (d) with evidence \cite{kang2026registry, qin2026governed, quessadavial2026acm}, and the MCP control planes have access control without evaluation-gated promotion \cite{agenticcommunity2026mcpgateway}. Rollback now appears inside single deployments, as edit-level reversal \cite{wei2026skillsmith, gao2026skillaudit} and as an admission test that rejects edits which cannot be undone \cite{sah2026evoundo}, and inside one federated round; no system rolls back a promotion that has crossed an organization boundary, because none makes such a promotion. Supplementary Material S4 gives the per-system enumeration.

In machine-learning terms, what is missing is a cross-tenant aggregator with an automated evaluation gate at the scaffold layer. It would carry five parts: per-tenant artifact pools, each tagged with provenance; an aggregation step across tenants that respects tenant isolation; a held-out evaluation at the receiving tenant that blocks a promotion whenever it does not lower that tenant's patch loss; versioned lineage with access control; and a rollback envelope on every promoted artifact. The federated-averaging analogy \cite{mcmahan2017fedavg, mcmahan2018dpfedavg} is useful only in the limit where artifacts are mergeable update representations; in surveyed practice Loop 2 is selection and merge, and the nearest systems aggregate program edits with a language model, not by averaging.

Whether the architecture \emph{should} be built is a question the feedback-signal class answers (Section~\ref{sec:signal}). Where the signal is exact, an automatically gated cross-tenant promotion of a test-validated skill is low-risk and the receiving-side evaluation is cheap. Where the signal is an observable outcome, the corner should be filled only with that receiving-side evaluation, because the sending side's outcome does not transfer; Evo2Team's four failed transfers out of twenty-two after target-side confirmation show that even a receiving-side check is necessary rather than sufficient \cite{wang2026evo2team}. Where the signal is judged, a human gate on Loop 2 is a design feature, and governance means lineage and rollback around a human decision. Where the signal is delayed, property (a) cannot be met and what remains is lineage and rollback without an automatic gate. Naming the four properties converts a vague gap into an audit criterion that any future system can be measured against; naming the signal class says, for a given deployment, which of the four it should expect to meet.

Two rows deserve a sentence beyond the table. Every row names a piece of the optimizer that current systems do not yet have.

\section{Open problems and conclusion}\label{sec:open}

Five open problems follow from the survey, one per feedback-signal class and one for the architecture.

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Exact signals: credit assignment from a failing check to a scaffold coordinate.} A test tells the loop that an output failed, not which instruction, skill, or tool binding caused it. Slot attribution \cite{nguyen2026harnessevo}, intervention-based attribution \cite{chu2026agentgrad}, and contrastive multi-agent attribution \cite{zehle2026cantante} each solve one substrate's case; a general method is the bottleneck named by every harness-optimization paper.
\item
  \textbf{Observable outcomes: receiving-side evaluation before promotion.} Four systems now evaluate at the receiving side and one of them still misses a fifth of its transfers; the gate that a federated scaffold optimizer needs is a held-out test at the receiving tenant, proposed but not yet built \cite{yang2026fao}.
\item
  \textbf{Judged signals: calibrating a gate that is itself being edited.} Fourteen weight-side rubric-reward papers include five that co-evolve the rubric with the policy, and none of those five reports agreement with human judgment; on the scaffold side three systems report judge calibration and none calibrates a judge under edit. The reflexive gate of Section~\ref{sec:signal} has no measured instance.
\item
  \textbf{Delayed signals: telling descent from search.} Where the outcome arrives after many edits, an optimizer's gains cannot be distinguished from trial-and-error by outcome alone \cite{ong2026harnesseval}; evaluation of harness optimizers against their attribution claims rather than their scores is the open method.
\item
  \textbf{The governed cross-tenant corner.} Properties (a) through (d) of Section~\ref{sec:gap}, with the receiving-side gate of problem 2 as the piece that would make cross-organization promotion safe in the two classes where it should be automatic.
\end{enumerate}

The field has built an external adaptation layer for language models but not the optimizer that should govern it. The reason the layer belongs where it is was established by the two papers this article completes: reliability over long outputs hinges on a sparse set of key decisions, and inside a bounded deployment those decisions fail in a small, recurring catalogue of modes that a targeted budget of fixes can cover. The place to spend that budget is a persistent, inspectable, reversible artifact outside the weights, and once the loop that edits it is gated and scoped, the arrangement is not a patch on an inadequate model but the architecture that the error structure calls for. The survey shows how far practice has come toward that loop. The local loop closes automatically in most research systems and in a growing number of production ones; evidence is batched before acceptance; retirement and expiry have become first-class; lineage has reached production memory. What has not moved is the second loop. No surveyed system promotes a validated edit across an organization boundary under an automatic gate with lineage, access control, and rollback, and the signal-class analysis says this is not one gap but four, each with its own reachable answer. The frontier model generalizes. The local scaffold specializes. Reliability comes from governing that specialization, and the instruments that judge each edit are themselves part of the moving scaffold, so the same evidence-radius and lifecycle discipline the optimizer needs must extend to the gates that judge it.

\section{Appendix: Formal statement of artifact-layer descent}\label{app:formal}

This appendix states the setup behind Section~\ref{sec:loop}, a one-step descent inequality under a noisy gate, an informal convergence proposition, the optimization-analogy correspondence, and four worked cases. No new theorem is claimed; the proposition is the ordinary target of local stochastic optimization under noisy estimators, restated for a discrete, versioned parameter.

\subsection{Setup}\label{setup}

Let the frontier model have fixed parameters \(\theta_M\) and let the scaffold be a structured object \(\theta_s \in \Theta_s = \Theta_1 \times \cdots \times \Theta_6\) over the six substrate coordinates of Section~\ref{sec:method}; \(\Theta_s\) is discrete, symbolic, and versioned. For a deployment \(D\), \(L_D(\theta_s) = \mathbb{E}_{x \sim D}[\ell(\pi(\theta_M, \theta_s, x))]\). A candidate edit \(z_t \sim Q_t(z \mid H_t, \theta_s^t)\) is drawn from a proposal process conditioned on the accumulated history \(H_t\) of failures, corrections, rejected outputs, evaluation regressions, and prior accepted edits. \(Q_t\) is not uniform: for a mode \(m\) that recurs with frequency \(f_m\) and carries per-occurrence loss \(s_m\), its expected contribution to the failure rate is \(f_m s_m\), so high-frequency or high-severity modes are proposed first. The finite directional difference is \(\Delta_z L_D(\theta_s) = L_D(\theta_s \oplus z) - L_D(\theta_s)\); the gate sees only a noisy estimate \(\widehat{\Delta}_z L_D\). The update is \[\theta_s^{t+1} = \theta_s^t \oplus z_t \text{ if } G_t(z_t) = 1, \quad \theta_s^{t+1} = \theta_s^t \text{ otherwise.}\]

\subsection{Descent inequality}\label{descent-inequality}

Assume (A1) positive descent bias on accepted edits, \(\mathbb{E}[\widehat{\Delta}_{z_t} L_D \mid G_t = 1, \theta_s^t] \le -\gamma_t - \tau_t\) for some \(\gamma_t > 0\), and (A2) bounded estimator bias on accepted edits, \(|\mathbb{E}[\Delta_{z_t} L_D - \widehat{\Delta}_{z_t} L_D \mid G_t = 1, \theta_s^t]| \le \varepsilon_t\). With \(p_t = \Pr(G_t = 1 \mid \theta_s^t)\), \[\mathbb{E}[L_D(\theta_s^{t+1}) \mid \theta_s^t] \le L_D(\theta_s^t) - p_t(\gamma_t + \tau_t) + p_t\,\varepsilon_t.\] Per-step expected improvement is the gate's margin minus its estimator bias, weighted by acceptance probability. In the feedback-signal classes of Section~\ref{sec:signal}, \(\varepsilon_t\) is near zero for an exact check (C1), bounded by batching for an observable outcome (C2), equal to the judge's bias and bounded only by calibration for a judged signal (C3), and unavailable per edit for a delayed signal (C4).

\subsection{Convergence (informal)}\label{convergence-informal}

Add (A3) proposal coverage, that at every non-gate-stable scaffold \(Q_t\) places probability at least \(q > 0\) on an admissible edit with \(\mathbb{E}[\Delta_z L_D] \le -\delta\); (A4) effective compactness of the reachable orbit; and (A5) persistent acceptance with summable bias, \(\sum_t p_t(\gamma_t + \tau_t) = \infty\) and \(\sum_t p_t \varepsilon_t < \infty\); and let \(0 \le L_D \le B\). Then \(L_D(\theta_s^t)\) is a non-negative supermartingale up to summable noise, it converges almost surely, and the limit set of \(\{\theta_s^t\}\) is gate-stable: no admissible edit clears the gate with negative expected directional loss in the limit. This is convergence of the loss and stability of the gate decision, not convergence to an optimum; a globally suboptimal gate-stable scaffold is consistent with the result, because \(Q_t\) may never propose the improving edit or \(\widehat{\Delta}\) may be biased to reject it. In a non-stationary deployment (\(D = D_t\)) the same mechanism tracks a moving optimum rather than converging once, which is why recency weighting, pruning, expiry, and rollback are the scaffold-level analogues of continual-learning machinery rather than optional hygiene.

\subsection{Worked cases}\label{worked-cases}

\emph{Retrieval.} Failures recur because retrieved context omits the decisive clause. Attribution traces the error to the retrieval coordinate: chunking, query rewriting, metadata filter, embedding model, reranker, or context-packing rule. The candidate edit tightens chunk boundaries or adds a metadata constraint, and the gate checks that recall and answer accuracy improve on the patch evaluation without degrading adjacent cases. Signal class C1 or C2.

\emph{Pitch review.} The system repeatedly overrates decks that claim a large market without numbers. The failure cluster points at an under-specified rubric coordinate. The edit changes ``evaluate market size'' into ``require a numeric estimate and a source; if absent, cap the score''. The gate runs the revised rubric against held-out decks with human scores. The edit changed the gate that will judge the next edit: the reflexive gate of Section~\ref{sec:signal}, class C3.

\emph{Tool use.} Calls fail because optional parameters are under-specified. The responsible coordinate may be the tool schema, the call policy, or the clarification rule. The edit adds required fields or a pre-call uncertainty check; the gate checks that tool-call failures fall without raising refusals or latency. Class C2.

\emph{Memory.} A stale customer preference is repeatedly retrieved and causes bad decisions. The responsible coordinate is a memory entry together with its provenance, priority, and expiry policy. The edit corrects, expires, or version-tags the entry; the gate checks that future behavior improves without erasing useful history. Class C2, with the correction itself observable only when a later outcome reveals it.
