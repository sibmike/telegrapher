## Where the signal comes from: four classes of feedback {#sec:signal}

Four scaffolds all run the loop of Section REF(sec:loop). A coding agent changes one line in its repository rule file; the test suite runs and reports pass or fail within seconds. A scheduling assistant changes how it phrases a booking request; the appointment either appears on the calendar or it does not, and the system learns which an hour later. A marketing assistant changes the tone rule in its instructions; nobody can say whether the next draft is better, only whether a reviewer prefers it. A research assistant changes how it chooses which direction to pursue; whether the choice was good becomes visible months later, after many other edits have landed. All four produce a candidate edit. They differ in what the gate can know about it.

That difference is the whole of this section. The gate needs an estimate of one quantity, whether the edit lowered the patch loss, and the estimate comes from a feedback signal. Signals differ in three ways: how soon they arrive, how exact they are, and whether there is a fact of the matter at all. Those three differences sort every surveyed system into four classes (Table REF(tab:IV-1)), and the class fixes what the gate can be, which half of the loop can close automatically, and which failure dominates.

| Class | The signal the gate receives | What the gate can be | What stays hard | Corpus examples |
|---------|------------------------|--------------------|----------------------|--------------|
| C1 exact | A check that returns pass or fail, or an exact score, at once and repeatably: tests, compilers, answer keys | An automatic check; one run suffices | The check names the failed output, not the coordinate that caused it; a check that is also the target can be gamed | DGM, AlphaEvolve, SkillOpt |
| C2 observable outcome | A real result one episode later: a booked slot, a merged pull request, a closed ticket; noisy and confounded | An automatic threshold over batched episodes; a person at promotion | The outcome says *that* the episode failed, not *why*; the channel can be poisoned | Devin, Sierra, SAGE, SkillRL, PACE, Voyager |
| C3 judged | A rater, a rubric, or a model judge; no ground truth | A judge calibrated against people; a person at promotion | The rubric is itself a scaffold coordinate, so the gate judges edits to itself; the proxy gets optimized past the point where it tracks quality | SkillForge, CASCADE, skills-repository review |
| C4 delayed | An outcome weeks or months later, once per many edits | No per-edit gate; proposals are pruned and milestones stand in | Credit across many edits; drift; the loop cannot be told from random search | NanoResearch, CORAL, AlphaEvolve's archive |

**C1, exact.** A deterministic checker returns pass or fail, or an exact score, immediately and repeatably: unit tests, compilers, type checkers, exact-match answer keys, proof checkers, schema validators. DGM accepts a self-modification only after it passes in a sandbox on coding benchmarks [@zhang2025darwin]; AlphaEvolve scores candidate programs with a cascade of exact evaluators [@alphaevolve2025]; SkillOpt gates a skill edit on a held-out exact-match split of a math benchmark [@yang2026skillopt]. The gate can be a program, its margin can sit near zero, and accepting on a single evaluation is defensible, because repeating the check would return the same answer. Two things stay hard. A failing test localizes the output, not the scaffold coordinate that caused it, so credit assignment remains open; and a checker that is also the training target can be gamed. The dominant failures are test overfitting and scaffold bloat, because cheap acceptances accumulate.

**C2, observable outcome.** The environment or the user emits an outcome after an episode: a booked appointment, a closed ticket, a merged pull request, a tool call that returns without error, a retrieved document that contains the answer. The signal is real but one episode late, noisy, and confounded, since a user can accept a wrong answer and reject a right one. Devin's merged pull requests [@cognition2025devinreview], SAGE's task success on AppWorld [@wang2025sage], SkillRL's success-rate threshold [@skillrl2026], and PACE's failure signals from a deployed small model [@ling2026pace] are gates of this class. The gate can still be a program, a reinforcement-learning threshold or a held-out task suite, but it needs a positive margin, and it absorbs the noise by batching episodes or by requiring agreement across samples (Appendix REF(app:gates)). Credit assignment takes its hardest form: the outcome says *that* the episode failed, not *why*. Most production deployments live in this class, and its signal arrives through a channel an attacker can control, which is why poisoned memory and tool-output injection dominate.

**C3, judged.** There is no fact of the matter. An essay, a marketing page, a design, a pitch deck, or a code review for style can be scored only by a judge: a human rater, a language-model judge, a rubric, or a comparison against references. SkillForge accepts a skill diff when its judge agrees with human engineers more than nine times in ten [@skillforge2026]; CASCADE consolidates memory under a human-and-agent gate [@huang2025cascade]; Anthropic's skills repository promotes a skill when a reviewer approves the pull request. The gate can be a program only after the judge has been calibrated against people, because the judge's bias is now the estimator's bias; and residuals are captured only when someone objects, so condition 2 depends on complaint channels rather than instrumentation. The dominant failure is Goodhart's law in the form measured for reward models: optimizing a proxy past a point lowers the true score [@gao2023overoptimization]. Once the judge is the target, the scaffold learns the judge. Nor is a human judge stable; evaluators' criteria drift as they grade more outputs [@shankar2024validators].

**C4, delayed and sparse.** The outcome arrives after weeks or months, once per many edits, in a world that has moved on. Research programs, product strategy, and open-ended discovery are of this kind; the clearest instances are automated research pipelines such as the AI Scientist, which generates ideas, runs experiments, and writes the paper [@lu2024aiscientist]. NanoResearch merges candidate skills by semantic compatibility rather than by a measured loss change [@xu2026nanoresearch]; CORAL promotes findings into shared memory on a heartbeat rather than on an evaluation [@qu2026coral]; AlphaEvolve's MAP-Elites archive keeps candidates for their diversity, not their score [@alphaevolve2025]. With no per-edit estimate to gate on, the gate degenerates to proposal pruning plus proxy milestones, and the descent argument covers only the composition of pruning and whatever gate exists at the horizon (Appendix REF(app:gates)). Temporal credit assignment across many edits is open. The dominant failure is drift: the scaffold ages faster than the signal that would correct it. An optimizer in this class also cannot be told from random search by its outcomes alone; Ong et al. [@ong2026harnesseval] report the same indistinguishability for harness optimizers.

**The judge is part of the scaffold.** One feature of the judged class deserves its own paragraph, because it returns in the findings and in the open problems. The rubric that sets the loss is itself a scaffold coordinate. Suppose a pitch-review system keeps overrating decks that claim a large market without numbers. It traces the failure to its rubric and edits "evaluate market size" into "require a numeric estimate and a source". That edit changes the gate that will judge the next edit. We call this the *reflexive gate*, and nothing in the corpus calibrates one: three scaffold systems report judge calibration [@skillforge2026; @hu2026skillchain; @zhu2026skillcoach], and none calibrates a judge that is itself being edited. The weight side faces the same question. Reinforcement learning from verifiable rewards lies outside the scored corpus, but pushing it into writing and other open-ended tasks has forced the construction of judged gates. One group holds the gate fixed while the policy learns, as a checklist, a pairwise judge, a reference-anchored judge, or a fixed rubric [@gunjal2025rubrics; @jia2025writingzero; @shi2026references; @jin2026rlaes]; a second group lets the gate move with the policy, scoring by the policy's own probability of a reference or updating the rubric or judge during training [@yu2025rlpr; @xu2026rubricarm; @ding2026evorubrics; @zhu2026score; @li2026rubricem]. Fixed versus co-evolved is exactly the reflexive-gate question, and of the co-evolving methods only RLPR, whose reward is a probability rather than a rubric, reports agreement with human labels (Supplementary Material S6).

**What the class decides.** Read down the table and three consequences follow. First, which half of the loop can close automatically. An exact check or an observed outcome can gate a local edit by program, a judgment only once the judge is calibrated, and a delayed reward not edit by edit at all; and only the exact class can gate promotion by program without a person on the receiving side, because only there does the sending side's evidence mean the same thing on arrival. Second, which gate pairings a deployment can reach. [Auto × Auto] belongs to exact signals and simulated outcomes; [Auto × Human] belongs to observed outcomes and judgments, where the person on Loop 2 does the work the missing exact signal cannot; and the delayed class has no per-edit gate on either half. Third, which failure dominates, as the last column of the table records and Section REF(sec:failure) develops. Each consequence is a prediction about the corpus, and Section REF(sec:design) checks all three.
